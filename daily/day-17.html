삭제 흔적은 왜 남고,
probe는 왜 길어지는가

Probe coverage → EMPTY/DELETED semantics → clustering → compaction trigger · 110분

한 줄 요약
open addressing에서 EMPTY는 “여기 뒤에는 이 key가 없다”는 증명 표식이고 DELETED는 “값은 없지만 탐색은 계속하라”는 흔적이다. live α만 낮아져도 tombstone과 cluster가 남으면 성능은 회복되지 않는다.

1. 초보자를 위한 용어 사전

Home slotkey의 첫 후보 위치 p(k,0). 충돌이 없으면 여기 저장된다.
Probe sequence한 key가 차례로 검사하는 slot 순서 p(k,0),…,p(k,m-1).
Coverageprobe sequence가 필요한 모든 slot, 이상적으로 table 전체를 중복 없이 방문하는 성질.
Linear probingp(k,j)=(h(k)+j) mod m. 연속 주소라 locality가 좋지만 primary clustering이 생긴다.
Quadratic probingoffset을 j²·삼각수 등으로 키워 연속 cluster를 피하는 방식. m과 계수에 따라 coverage가 달라진다.
Double hashingp(k,j)=(h₁(k)+j·h₂(k)) mod m. 두 번째 hash가 step을 정한다.
EMPTY한 번도 점유되지 않았거나 compaction 후 비어 있는 slot. lookup이 여기서 안전하게 종료된다.
Tombstone / DELETEDpayload는 제거됐지만 기존 probe 경로를 끊지 않기 위한 삭제 표식.
Primary clusteringlinear probing의 연속 FULL/DELETED 덩어리가 더 많은 home key를 끌어들여 커지는 현상.
Secondary clustering같은 home을 가진 key가 같은 probe sequence를 공유해 함께 충돌하는 현상.
Live αsize/m. 실제 mapping이 차지한 비율.
Used α(size+deleted)/m. probe가 EMPTY로 보지 못하는 slot 비율. 운영상 별도 추적해야 한다.
Backshift deletion삭제 뒤 후속 entry를 조건에 맞게 당겨 tombstone을 남기지 않는 방식. probe 불변식 증명이 필요하다.

2. Architecture / operation flow

① Hash splithome·step 또는 group fingerprint 계산
↓ p(k,j), j=0..m-1 · 반드시 유한 coverage
② State scanFULL은 equality, DELETED는 통과, EMPTY는 종료
↓ get / put(first tombstone 기억) / delete(mark or shift)
③ Commitpayload lifetime과 control state를 올바른 순서로 변경
↓ live α·used α·probe p95/max·tombstone ratio 관측
④ Maintenancegrow / same-size rehash / backshift / reject 결정

핵심: 삭제는 단일 slot 변경이 아니라 미래 lookup의 증명 경로를 유지하는 작업이다. 운영 지표가 threshold를 넘으면 새 table을 준비하고 모든 live entry를 다시 삽입해 tombstone과 cluster를 제거한다.

3. 문제·입출력·제약 mental model

문제: 64-bit request ID를 retry state에 연결하는 bounded open-addressing map을 운영한다. m=131,072, peak live α=0.8, 60% lookup·20% insert/update·20% delete이며 timeout으로 삭제 churn이 크다.

질문이 사례의 계약

틀리기 쉬운 판단: delete 뒤 live α가 0.4가 됐으니 table이 가벼워졌다고 판단하면 안 된다. tombstone이 0.4m이면 used α는 여전히 0.8이고 unsuccessful lookup은 EMPTY를 만날 때까지 같은 긴 경로를 걷는다.

4. Map ADT와 representation invariant

ADT: 유한 부분함수 M: K ⇀ V. put은 key를 유일하게 삽입/교체하고, get은 정확한 value 또는 NOT_FOUND, delete는 해당 mapping만 제거한다. probing 방식과 tombstone은 외부 계약이 아닌 표현이다.

  1. RI-1 count: 0≤size, 0≤deleted, size+deleted≤m. FULL/DELETED slot 수와 counter가 일치한다.
  2. RI-2 uniqueness: equality 기준 같은 key는 FULL slot에 최대 하나다.
  3. RI-3 reachability: FULL key k의 home부터 저장 위치까지 probe prefix에 EMPTY가 없다.
  4. RI-4 coverage: probe는 최대 m회에 종료하며 요구한 후보 집합을 중복 없이 방문한다.
  5. RI-5 state/lifetime: FULL만 constructed payload를 갖고 EMPTY/DELETED payload는 읽지 않는다.
  6. RI-6 insertion: 첫 DELETED를 재사용 후보로 기억하되, EMPTY 또는 m회까지 동일 key가 뒤에 없는지 확인한 후 commit한다.

왜 첫 tombstone에 즉시 넣으면 안 되나? 같은 key의 기존 entry가 probe 뒤쪽에 있을 수 있다. 즉시 넣으면 RI-2를 깨고 같은 key가 두 개 생긴다. update/insert를 구분하려면 탐색을 계속해야 한다.

5. Probe 전략과 coverage 조건

전략식장점·전제·위험
Linearh+j mod m모든 slot coverage, 연속 locality; primary cluster
Quadratich+c₁j+c₂j² mod m연속 cluster 완화; m·계수에 따라 일부 slot만 방문, secondary cluster
Double hashh₁+j·h₂ mod mgcd(h₂,m)=1이면 permutation; locality는 약해질 수 있음
Group probingcontrol-byte group + next groupfingerprint/SIMD로 후보 축소; library 구현 세부·계약 확인

수론 체크: double hashing에서 m=2ʳ이면 step을 홀수로 만들면 m과 서로소라 전체 slot을 방문한다. step=0 또는 gcd(step,m)>1이면 빈 slot이 있어도 닿지 못하고 거짓 FULL이 될 수 있다. quadratic probing도 “quadratic이면 전체 방문”이 아니므로 검증된 공식과 load threshold를 사용한다.

6. Search·delete·insert 정당성

Search: probe 순서대로 FULL이면 equality를 검사하고 DELETED면 계속한다. EMPTY에서 종료한다. k가 저장돼 있다면 RI-3 때문에 k 이전에 EMPTY가 있을 수 없으므로 반드시 k에 도달한다. EMPTY를 먼저 만났다면 이후에 k가 저장됐다는 가정이 삽입 규칙과 모순이다.

Delete: target FULL을 DELETED로 바꾸면 추상 mapping만 제거된다. DELETED는 후속 lookup을 중단하지 않으므로 다른 key의 reachability가 보존된다. size--, deleted++로 RI-1을 유지한다.

Insert: probe 중 동일 key면 value만 교체한다. 첫 DELETED를 기억하고 EMPTY를 만나면 그 DELETED 또는 EMPTY에 새 payload를 만든 뒤 마지막에 FULL을 공개한다. EMPTY가 없지만 DELETED가 있으면 m회 후 그곳을 재사용한다. 둘 다 없으면 FULL이다.

최소 반례: m=8, A와 B의 linear home이 1이라 A@1, B@2다. A를 EMPTY로 지우면 get(B)는 slot 1에서 멈춰 거짓 NOT_FOUND를 반환한다. A를 DELETED로 바꾸면 slot 2까지 진행해 B를 찾는다.

7. Clustering의 양의 피드백

Primary: linear probing에서 길이 L의 연속 cluster 앞 어느 home에 도착해도 새 key는 cluster 끝에 붙는다. cluster가 길수록 다음 key를 흡수하는 home 구간도 넓어져 더 빨리 성장한다. 좋은 첫 hash만으로 이 동역학이 사라지지 않는다.

Secondary: quadratic probing처럼 같은 home이 같은 offset sequence를 쓰면 그 key들이 계속 같은 후보에서 만난다. 연속 cluster는 줄여도 같은 home 그룹의 충돌은 남는다.

Double hashing: 같은 home이라도 두 번째 hash가 다른 step을 만들면 probe sequence가 갈라진다. 다만 두 hash의 품질·independence, coverage 조건, random memory access 비용을 함께 본다.

8. Complexity: live α보다 used α가 중요한 순간

연산좋은 상태나쁜 상태

putexpected O(1)중복 확인 때문에 첫 tombstone 뒤도 탐색

uniform hashing의 unsuccessful probe 상한 1/(1-α)에서 tombstone은 EMPTY가 아니므로 실무 추정에는 live α만 대입할 수 없다. used α와 실제 probe histogram을 함께 본다. rehash 비용을 연산열에 상각할 수 있어도 단일 p99 pause는 남는다.

9. 직접 구현: tombstone-safe put

bool put(Map *t, Key k, Value v, Result *r) {
  size_t i = home(k), step = odd_step(k);   // m=2^r
  size_t first_deleted = SIZE_MAX;

  for (size_t probes = 0; probes < t->m; ++probes) {
    Slot *s = &t->slots[i];
    if (s->state == FULL && equal(s->key, k)) {
      replace_value_failure_atomically(s, v);
      *r = REPLACED; return true;
    }
    if (s->state == DELETED && first_deleted == SIZE_MAX)
      first_deleted = i;                    // 아직 commit 금지
    if (s->state == EMPTY) {
      size_t dst = first_deleted == SIZE_MAX ? i : first_deleted;
      construct_payload_or_fail(&t->slots[dst], k, v);
      publish_full(&t->slots[dst]);         // payload 완성 뒤 state
      t->size++;
      if (dst == first_deleted) t->deleted--;
      *r = INSERTED; return true;
    }
    i = (i + step) & (t->m - 1);
  }
  if (first_deleted != SIZE_MAX) { /* 동일 key 없음이 확인됨 */
    construct_and_publish(&t->slots[first_deleted], k, v);
    t->size++; t->deleted--; *r = INSERTED; return true;
  }
  *r = FULL; return false;
}

production 주의: construct_payload_or_fail가 실패하면 state/counter가 바뀌지 않아야 한다. concurrent reader가 있다면 payload와 control byte publication의 atomicity·memory ordering·linearization point를 별도로 설계한다.

10. 테스트: 최소 반례부터 전수 상태까지

  1. m=8에서 같은 home인 A/B/C를 insert→중간 delete→뒤 key lookup해 EMPTY/DELETED 오류를 잡는다.
  2. first tombstone 뒤 동일 key가 있는 table에서 put해 size가 늘지 않고 value만 교체되는지 본다.
  3. double hash의 모든 key step에 대해 gcd(step,m)=1, m회 동안 방문 slot 수가 m인지 검사한다.
  4. 작은 m의 임의 put/get/delete sequence를 reference dict와 비교하고 매 prefix에서 count·uniqueness·reachability RI를 검사한다.
  5. EMPTY 0개·DELETED 존재, 완전 FULL, wrap-around, key 0, invalid capacity, counter overflow를 넣는다.
  6. payload construction 실패·rehash allocation 실패 뒤 snapshot이 동일한지 확인한다.

이번 검증: C11 linear/double-hash map에 104,857개 insert, 절반 delete, same-size rehash를 수행했다. 매 phase에서 모든 FULL key reachability와 count RI를 검사했고 Apple clang 21.0.0 ASan/UBSan을 통과했다.

11. Benchmark: 삭제해도 probe가 줄지 않는다

환경: Apple clang 21.0.0 -O3, arm64 macOS 26.5.2, m=131,072, 초기 n≈0.8m, 같은 64-bit mixer, 각 시간 5회 median. after-delete의 lookup은 원래 key 전체를 질의하므로 절반 hit·절반 deleted-key miss인 churn workload다.

해석: delete는 live value만 줄였고 EMPTY를 늘리지 않아 miss probe가 그대로다. same-size rehash는 tombstone을 제거해 성능을 회복했다. double hashing은 linear cluster를 줄였지만 random access와 두 hash 계산 비용이 있으며, 이 한 workload의 승자가 보편적 승자는 아니다.

benchmark 주의: hit·deleted-key miss·never-seen miss를 분리하고 live/used α, tombstone, probe p50/p95/p99/max를 함께 기록한다. warm-up·RNG·build·rehash를 timed region에서 분리하고, latency뿐 아니라 cache miss·branch miss·bytes/entry·peak rehash memory를 본다.

12. Memory·locality·maintenance trade-off

  • Linear: 연속 slot으로 hardware prefetch와 cache line 활용이 좋다. 긴 cluster는 같은 locality를 이용하면서도 읽는 byte 자체를 폭증시킨다.
  • Double: cluster 상관을 줄이지만 넓은 주소로 뛰어 cache/TLB locality가 약해질 수 있다. probe 수와 cycle을 모두 측정한다.
  • Control bytes: EMPTY/DELETED/7-bit fingerprint를 payload와 분리하면 한 vector load로 여러 slot 후보를 거를 수 있다. Abseil Swiss table은 deleted가 probe를 끝내지 않고 empty가 끝내는 의미를 metadata에 담는다.
  • Tombstone: payload는 파괴해도 control byte 한 개가 미래 probe 비용을 보존한다. 작은 memory 표식이 큰 CPU debt가 될 수 있다.
  • Rehash: same-size는 tombstone/cluster 정리, grow는 capacity와 EMPTY를 함께 늘린다. 둘 다 새 table과 구 table이 겹치는 peak memory·pointer invalidation·pause가 있다.
  • Backshift: extra table 없이 tombstone을 줄이지만 이동 범위·value move 비용·iterator/reference 계약·동시 reader가 복잡해진다.

14. 실무 best practice

  • live α와 used α를 분리하고 deleted/m, probe p95/max를 dashboard와 alert에 둔다.
  • grow threshold와 same-size compaction threshold를 따로 둔다. tombstone이 많다고 항상 capacity를 늘릴 필요는 없다.
  • probe 공식·capacity 조합을 property test하고 검증된 container 구현을 우선한다.
  • delete-heavy·miss-heavy 실제 trace로 benchmark한다. insert-only microbenchmark로 운영 선택을 끝내지 않는다.
  • rehash의 peak memory, failure atomicity, pointer/iterator invalidation, shutdown·concurrency를 API 계약화한다.
  • control state를 payload sentinel로 겸용하지 않는다. 모든 key/value bit pattern을 저장 가능하게 한다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. open addressing에서 삭제를 EMPTY로 바꾸면 왜 안 되나요?
EMPTY는 lookup 종료 증거다. 같은 home에서 밀려난 뒤 key의 probe prefix를 끊어 거짓 NOT_FOUND를 만든다. 최소 A@1/B@2 반례, DELETED 통과 규칙, tombstone debt와 backshift/rehash 대안을 설명한다.
Q2. live load factor가 낮은데 lookup이 느린 이유는?
tombstone은 EMPTY가 아니므로 used α가 높고 cluster가 남을 수 있다. live/used α, deleted ratio, probe p95/max를 확인하고 same-size rehash 전후를 비교한다. 평균 size만으로 판단하지 않는다.
Q3. linear, quadratic, double hashing을 어떻게 선택하나요?
coverage 증명 → clustering 종류 → locality/hash 비용 → α·hit/miss/delete trace → implementation optimization을 비교한다. double hash는 gcd(step,m)=1, m=2ʳ이면 odd step을 확인하고, 검증된 group-probing library도 후보로 둔다.
