같은 key는 같은 곳으로,
공격 key는 예측 못 하게

Equality law → hash implication → mutable-key failure → hash flooding defense · 120분

한 줄 요약
hash map의 정당성은 equal(a,b) ⇒ hash(a)=hash(b)와 key의 안정성에 달려 있고, 성능은 공격자가 collision을 예측하지 못하게 하는 keyed hash·최악 비용 제한·입력 예산을 함께 적용해야 지킬 수 있다.

1. 초보자를 위한 용어 사전

Identity두 reference가 바로 같은 객체를 가리키는가. 값 동등성 equality와 다르다.
Equality도메인에서 두 key를 같은 것으로 볼지 결정하는 관계. 예: 같은 tenant와 user ID.
Equivalence relationreflexive·symmetric·transitive한 관계. map의 “동일 key”는 이 수학적 성질을 요구한다.
Reflexivea=a. NaN의 원시 부동소수점 ==처럼 이 성질이 없으면 별도 key 정책이 필요하다.
Symmetrica=b ⇒ b=a. 서로 다른 타입을 비교할 때 한쪽만 true면 안 된다.
Transitivea=b ∧ b=c ⇒ a=c. 근사 실수 비교가 흔히 깨뜨린다.
Hash codekey를 고정 폭 정수로 요약한 값. 먼저 후보 bucket을 고를 뿐 equality를 대체하지 않는다.
Collision서로 다른 key가 같은 hash 또는 bucket에 도착하는 필연적 현상. correctness는 유지하되 비용이 늘 수 있다.
Hash contract동등한 key는 반드시 같은 hash를 내야 한다는 단방향 의무. 같은 hash라고 같은 key일 필요는 없다.
Canonicalization대소문자·Unicode·공백 등 허용한 여러 표현을 하나의 표준 표현으로 바꾸는 과정.
Mutable key삽입 뒤 equality/hash에 쓰는 필드가 바뀔 수 있는 key. 원래 bucket에 남아 lookup에서 사라진다.
Hash flooding공격자가 충돌 key를 대량 주입해 hash table을 선형 구조로 퇴화시키는 algorithmic-complexity DoS.
Keyed hashprocess 비밀 seed를 포함해 공격자가 bucket을 예측하기 어렵게 하는 hash. MAC·암호화와 목적이 다르다.
Treeification긴 collision chain을 balanced tree로 바꿔 lookup 최악 비용을 O(log n)으로 제한하는 전략.

4. Map ADT와 representation invariant

ADT: Map<K,V>는 equality가 만든 key equivalence class마다 최대 하나의 value를 연결한다. object identity나 hash integer 자체가 key 의미를 결정하지 않는다.

  1. RI-1 equivalence: equality는 reflexive·symmetric·transitive하고 map 안에 있는 동안 결과가 일관된다.
  2. RI-2 implication: eq(a,b) ⇒ h(a)=h(b). 역은 요구하지 않는다.
  3. RI-3 stability: 삽입된 key의 equality/hash 관찰값은 제거될 때까지 변하지 않는다.
  4. RI-4 uniqueness: 같은 equivalence class의 live entry는 최대 하나다.
  5. RI-5 reachability: 저장 시 계산한 bucket/probe 경로와 조회 시 경로가 같아 해당 class에 도달한다.
  6. RI-6 field framing: composite key hash는 field type·length 또는 안전한 구분자를 포함해 tuple 경계를 보존한다.
  7. RI-7 secret scope: keyed hash seed는 map 수명 동안 안정적이고 외부에 노출·직렬화되지 않는다.
자주 틀리는 방향: 좋은 contract는 “hash가 같으면 equals”가 아니다. hash 출력은 유한하므로 서로 다른 무한/거대 key 공간에는 충돌이 반드시 있다. correctness는 collision 후보를 equality로 구분해 얻는다.

5. Lookup 정당성 증명과 최소 반례

정당성: key a를 삽입한 위치는 bucket(h(a))다. 조회 key b가 a와 동등하면 RI-2로 h(a)=h(b), 따라서 같은 bucket/probe 후보를 방문한다. 그 후보에서 equality가 true이므로 value를 찾는다.

최소 contract 반례: equality는 (tenant,id)만 비교하지만 hash는 (tenant,id,displayName)를 모두 사용한다고 하자. displayName만 다른 a,b는 equal인데 hash가 다르다. a를 넣고 b로 찾으면 다른 bucket을 보아 거짓 NOT_FOUND, b를 put하면 duplicate equivalence class가 생겨 RI-4가 깨진다.

최소 mutable-key 반례: id=7 객체 reference를 bucket 7에 넣은 뒤 id를 8로 바꾼다. get은 bucket 8을 보지만 entry는 7에 남아 있다. 같은 객체인데도 사실상 잃어버린 entry가 되며 delete도 실패할 수 있다.

6. Equality가 equivalence relation이어야 하는 이유

깨진 법칙예map에서 생기는 문제
reflexiveIEEE NaN: x!=x삽입한 key 자신을 못 찾거나 중복 정책 불명확
symmetricBase는 Sub와 같지만 Sub는 Base와 다름조회 방향에 따라 결과 변화
transitive|a-b|<ε 근사 equalitya=b, b=c인데 a≠c인 겹치는 class
consistent현재 시간·DB 조회가 equality에 개입같은 lookup이 매번 다른 결과

Rust의 Eq는 reflexivity를 추가한 equivalence relation을 요구하며 f32/f64는 NaN 때문에 Eq를 구현하지 않는다. Java Double.equals는 raw == 대신 bit-based 규칙으로 NaN을 자기 자신과 동등하게 다뤄 Object equality 계약을 맞춘다. 언어마다 정책이 다르므로 “float를 key로 써도 되나?”보다 어떤 equivalence class를 원하는지 먼저 답한다.

7. Canonicalization·Unicode·composite key

  • Unicode: 화면상 같은 “é”가 precomposed U+00E9와 e + U+0301로 올 수 있다. 업무상 같다면 둘 다 NFC로 만든 뒤 equality/hash한다.
  • Case: tenant만 case-insensitive라면 tenant에만 명시한 locale-independent 규칙을 적용한다. user ID까지 임의 lower-case하면 다른 계정을 합칠 수 있다.
  • Tuple framing: 단순 byte 연결은 ("ab","c")와 ("a","bc")를 구분하지 못한다. type tag와 length-prefix를 hash stream에 넣는다.
  • Version: canonicalization 규칙 변경은 key identity migration이다. 새 규칙을 조용히 배포하면 old/new key가 공존할 수 있어 schema version과 backfill이 필요하다.
  • Cost: 매 lookup마다 normalize·allocate하지 말고 ingress에서 검증·정규화한 immutable key를 재사용한다.

8. 직접 구현: equality와 hash의 단일 schema

typedef struct {
  Bytes tenant_ascii_lower;  // ingress에서 canonicalized
  Bytes user_id_nfc;         // immutable owned bytes
} UserKey;

bool user_key_equal(const UserKey *a, const UserKey *b) {
  return bytes_equal(a->tenant_ascii_lower, b->tenant_ascii_lower) &&
         bytes_equal(a->user_id_nfc, b->user_id_nfc);
}

uint64_t user_key_hash(const UserKey *k, Secret128 seed) {
  SipState s = siphash_init(seed);     // process-local secret
  siphash_u8(&s, 1);                   // field type/domain tag
  siphash_u64(&s, k->tenant_ascii_lower.len);
  siphash_bytes(&s, k->tenant_ascii_lower);
  siphash_u8(&s, 2);
  siphash_u64(&s, k->user_id_nfc.len);
  siphash_bytes(&s, k->user_id_nfc);
  return siphash_finish(&s);
}

BuildResult build_user_key(Input in, UserKey *out) {
  if (in.tenant_len > 63 || in.user_len > 256) return KEY_TOO_LONG;
  if (!valid_utf8(in.user)) return INVALID_ENCODING;
  return canonicalize_and_copy_immutably(in, out); // 실패 시 out 불변
}

설계 포인트: display name·마지막 접속 시각처럼 identity가 아닌 mutable field는 두 함수에서 모두 제외한다. equality와 hash를 별도 팀이 손으로 중복 구현하지 말고 record/derive/schema-generated code와 property test로 drift를 막는다.

9. Hash flooding의 비용 증명

chaining table의 한 bucket에 n개가 모두 충돌하고 중복 검사를 위해 기존 chain을 순회하면 i번째 insert는 i−1회 equality를 수행한다. 총 비교는 0+1+…+(n−1)=n(n−1)/2=Θ(n²). 이후 hit/miss lookup도 Θ(n)이다.

open addressing도 모든 key가 같은 probe 시작·경로를 공유하면 cluster가 길어져 같은 최악 차수로 악화될 수 있다. load factor를 낮추거나 resize해도 공격 hash가 계속 같은 bucket/probe를 만들면 근본 해결이 아니다.

공격 mental model: 공격자는 서버 binary를 깨지 않아도 된다. 공개되거나 추론 가능한 hash에 맞춘 작은 key 집합을 반복 전송해 네트워크 bandwidth보다 훨씬 큰 CPU 작업을 유발한다. 이것이 algorithmic-complexity amplification이다.

12. Memory·locality·production trade-off

  • Keyed hash: 단순 정수 hash보다 CPU가 들지만 collision chain의 pointer chase·branch·equality 폭증을 예방한다. 짧은 untrusted string에서는 안전 비용을 request budget으로 본다.
  • Cached hash: 긴 immutable key의 재hash를 줄이지만 entry당 bytes가 늘고 seed rotation·serialization과 결합하면 위험하다.
  • Tree bin: worst bound는 좋아지지만 node pointer·color·parent 정보로 memory와 cache locality가 나빠진다.
  • Canonical bytes: normalize 결과를 소유하면 비교가 빨라지지만 원본+정규화본 peak memory가 든다. size limit와 interning 정책이 필요하다.
  • Seed scope: process별 seed는 반복 실행 iteration order를 바꿀 수 있다. deterministic test·wire format·persistent index에 runtime hash/order를 의존하지 않는다.

13. 테스트: example보다 law와 adversary

  1. Equality law: 생성 가능한 key에 reflexive·symmetric·transitive property test를 건다.
  2. Contract: 모든 sampled a,b에 eq(a,b)이면 같은 seed의 hash가 같은지 검사한다.
  3. Field drift: identity field 하나씩 바꾸면 equality/hash가 함께 반응하고 비identity field 변경에는 둘 다 반응하지 않는지 본다.
  4. Canonical pair: Unicode composed/decomposed, tenant 대소문자, 경계 length tuple이 의도한 equivalence class를 만드는지 확인한다.
  5. Mutation: API가 key를 복사하거나 immutable type만 받는지, 외부 buffer 변경 뒤에도 lookup이 안전한지 테스트한다.
  6. Adversarial: known collision corpus와 generated same-bucket 입력에서 max chain/probe·CPU budget·fallback을 검증한다.
  7. Seed: 같은 process에서는 안정적이고 다른 seed에서는 분포가 달라지며 secret이 log/core/metric label에 노출되지 않는지 점검한다.

이번 검증: C11 chaining 구현은 size·chain reachability를 검사했고 Apple clang 21.0.0 -Wall -Wextra -Werror 및 ASan/UBSan에서 정상·공격·seeded-demo 입력을 각각 5회 통과했다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. equals를 override하면 왜 hashCode도 바꿔야 하나요?
equal key가 다른 hash면 다른 bucket을 방문해 거짓 miss·duplicate가 생긴다. 단방향 equal⇒same hash, collision 시 equality 필요, 최소 tenant/id/displayName 반례로 정당성을 설명한다.
Q2. mutable object를 hash key로 쓰면 무슨 일이 생기나요?
hash/equality field 변경 뒤 entry는 old bucket에 남고 lookup은 new bucket을 본다. immutable snapshot, stable ID, remove-mutate-reinsert, API ownership 계약을 제시한다.
Q3. hash collision DoS를 어떻게 방어하나요?
n개 충돌 insert의 Θ(n²) 증명 후 keyed hash로 예측을 어렵게 하고 tree/fallback으로 worst를 제한하며 key-count/bytes·rate limit·deadline·collision metric으로 자원을 격리한다. resize만으로 해결되지 않음을 강조한다.
