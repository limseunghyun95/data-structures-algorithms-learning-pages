production hash map은 평균 O(1)이라는 문장이 아니라 도달 가능성·유일성·failure atomicity를 검사하는 구현, reference model과 실패 주입 테스트, 실제 key 분포와 tombstone debt를 드러내는 probe 지표까지 합친 시스템이다.

1. 초보자를 위한 용어 사전

ADT자료의 사용 계약. Map은 key별 value를 put/get/delete하며 내부 배열 방식은 감춘다.
Representation invariant(RI)모든 공개 연산 전후에 내부 상태가 반드시 만족해야 하는 명제.
Open addressingentry를 별도 node가 아니라 table slot 안에 저장하고 충돌 시 다른 slot을 탐사하는 표현.
Probe원하는 key를 찾기 위해 slot을 한 번 확인하는 일. probe 수는 cache·branch 비용의 좋은 대리 지표다.
Tombstone삭제된 자리를 나타내는 DELETED 표식. 탐사 경로는 유지하지만 누적되면 miss가 느려진다.
Live/used load factorsize/capacity와 (FULL+DELETED)/capacity. 공간과 탐사 압력을 서로 다르게 보여준다.
Oracle / reference model결과 비교의 기준이 되는 단순하고 신뢰하기 쉬운 구현. 이 랩은 작은 선형 map을 쓴다.
Differential testing같은 연산열을 시험 대상과 oracle에 실행해 모든 관찰 결과를 비교하는 테스트.
Property test몇 개 예제 대신 광범위한 입력에서 법칙·불변식이 계속 성립하는지 검사하는 방식.
Seed난수 연산열을 재현하는 시작값. 실패 로그에 남기되 보안용 hash secret과 혼동하지 않는다.
Fault injectionOOM·I/O 실패처럼 드문 실패를 의도적으로 발생시켜 error path를 검증하는 기법.
Failure atomicity연산이 실패하면 호출 전 상태가 그대로 보존되는 성질. “성공 아니면 무변경”이다.
Sanitizer실행 중 out-of-bounds, use-after-free, undefined behavior 등을 잡는 계측 도구.
Corpus실제 traffic이나 장애에서 모은 대표·적대 입력 모음. 균등 난수만으로 놓치는 분포를 보존한다.

3. 문제·입출력·제약 mental model

과제: 64-bit key/value를 저장하는 single-threaded open-addressing map을 C11로 구현한다. key는 모든 uint64_t를 허용하므로 sentinel key를 예약하지 않고 slot state를 별도로 둔다.

입력·사건정확한 계약관찰값

get(k)FULL key만 hit, 첫 EMPTY에서 missfound/value/probes

제약을 먼저 묻자: 동시 접근인가, key/value ownership은 누구에게 있는가, 실패 시 retry가 안전한가, iterator 순서가 API인가, 최대 resident memory와 p99 latency budget은 얼마인가? 이 답이 달라지면 같은 “hash map”도 다른 설계다.

4. ADT와 representation invariant

Map ADT: 각 key에는 최대 한 value가 대응하며 put은 그 대응을 만들거나 갱신하고, get은 현재 대응을 관찰하며, delete는 대응을 제거한다.

  1. RI-1 shape: capacity ≥ 8, 2의 거듭제곱이며 slots != NULL.
  2. RI-2 counts: size = #FULL, used = #FULL + #DELETED, size ≤ used ≤ capacity.
  3. RI-3 uniqueness: 같은 key를 가진 FULL slot은 최대 하나다.
  4. RI-4 reachability: 모든 FULL key는 자기 home slot부터 탐사할 때 먼저 만나는 EMPTY 이전에 도달한다.
  5. RI-5 deletion: delete는 중간 slot을 EMPTY로 만들지 않는다. 그렇지 않으면 뒤 key가 거짓 miss가 된다.
  6. RI-6 insertion: 검색 중 첫 DELETED를 기억하되 동일 key가 뒤에 있는지 EMPTY까지 확인한 후 재사용한다.
  7. RI-7 bounded progress: 모든 탐사는 최대 capacity개 slot 뒤 종료한다.
  8. RI-8 failure atomicity: 재할당·rehash가 실패하면 기존 table의 모든 observable byte와 ADT mapping이 그대로다.
왜 first tombstone에서 바로 insert하면 안 될까? 그 뒤 probe 경로에 같은 key가 있을 수 있다. 즉시 삽입하면 중복 FULL entry가 생긴다. 첫 DELETED 위치는 “후보”로만 저장하고 EMPTY 또는 기존 key를 만날 때까지 계속 탐사한다.

5. 정당성 증명과 최소 반례

get의 정당성: key가 존재하면 RI-4에 의해 home에서 그 key까지 EMPTY가 없다. get은 같은 hash와 probe 순서를 쓰므로 key에 도달해 반환한다. 반대로 EMPTY를 먼저 만났다면 그 자리는 해당 경로에서 한 번도 점유되지 않았으므로 key가 이후에 존재할 수 없다. capacity번 모두 보아도 없으면 miss다.

delete의 정당성: 찾은 FULL만 DELETED로 바꾸면 삭제 key의 대응은 사라진다. DELETED는 탐사를 중단시키지 않으므로 뒤 key의 reachability는 보존된다. size--, used 유지로 RI-2도 성립한다.

rehash의 정당성: 새 빈 table에 모든 old FULL entry를 같은 Map put 의미로 정확히 한 번 삽입하면 mapping·유일성이 보존된다. 전부 성공한 뒤 pointer를 swap하므로 중간 OOM은 old table을 관찰 가능하게 바꾸지 않는다.

최소 반례깨지는 성질수정

첫 DELETED에 즉시 duplicate key 삽입key 유일성probe 끝까지 equality 확인
old slot을 옮기며 바로 EMPTY 처리 후 OOMmapping 유실새 table 완성 후 commit
EMPTY가 없는데 무한 for(;;)terminationcapacity probe budget

6. 직접 구현: 탐사와 two-phase rehash

typedef enum { EMPTY, FULL, DELETED } State;
typedef struct { uint64_t key, value; State state; } Slot;
typedef struct { Slot *slots; size_t capacity, size, used; } Map;

Locate locate(const Map *m, uint64_t key) {
  size_t mask = m->capacity - 1;
  size_t first_deleted = SIZE_MAX;
  for (size_t step = 0; step < m->capacity; step++) {
    size_t i = (mix64(key) + step) & mask;
    Slot *s = &m->slots[i];
    if (s->state == FULL && s->key == key) return found(i);
    if (s->state == DELETED && first_deleted == SIZE_MAX)
      first_deleted = i;              // 후보만 기억
    if (s->state == EMPTY)
      return absent(first_deleted == SIZE_MAX ? i : first_deleted);
  }
  return absent(first_deleted);       // finite probe; SIZE_MAX면 정말 full
}

Status rehash(Map *m, size_t new_capacity) {
  Map candidate;
  if (!map_init(&candidate, new_capacity)) return OOM;
  for (size_t i = 0; i < m->capacity; i++) {
    if (m->slots[i].state == FULL)
      put_without_resize(&candidate, m->slots[i].key, m->slots[i].value);
  }
  Map old = *m;
  *m = candidate;                     // commit point
  map_destroy(&old);
  return OK;
}

실제 랩 구현: 별도 allocation hook으로 N번째 allocation을 실패시키고, resize 직전 table bytes를 snapshot해 OOM 뒤 capacity/size/used/slots가 정확히 같은지 비교했다. 단순히 “기존 key가 몇 개 조회된다”만 확인하면 metadata 손상은 놓칠 수 있다.

7. 테스트 설계: 예제에서 상태 공간으로

  1. Unit: empty miss, insert, update, delete, duplicate, zero/max key, wrap-around cluster.
  2. Minimal regression: 버그 하나마다 가장 작은 연산열과 seed를 고정한다.
  3. Differential: 512-key domain에서 put/get/delete 320만 회를 32 seeds로 생성하고 선형 oracle과 매 결과·전체 mapping을 비교한다.
  4. RI checker: count, uniqueness, probe reachability를 실행 중 주기적으로 전수 검사한다.
  5. Fault injection: grow allocation을 정확히 실패시키고 OOM 반환과 byte-for-byte 무변경을 검사한다.
  6. Sanitizer: ASan으로 out-of-bounds/use-after-free, UBSan으로 정수·shift 등 undefined behavior를 검사한다.
  7. Distribution: uniform, stride/same-bucket, duplicate-heavy, delete churn, miss-heavy corpus를 각각 측정한다.

재현 로그: 실패 시 seed, operation index, key/value, capacity, size/used, probe trace를 남긴다. 보안 hash의 비밀 seed 자체는 log에 남기지 말고 테스트 전용 결정적 hasher를 주입한다.

9. Complexity: expected·worst·amortized를 분리하라

연산좋은 분포·α 제한단일 최악공간
get/deleteexpected O(1)O(n)O(1)
put without resizeexpected O(1)O(n)O(1)
one resizeO(n)O(n²), 분포 악화 시peak O(n)
put sequenceamortized expected O(1)공격 입력은 보장 안 됨O(capacity)

geometric growth에서 entry는 capacity가 8,16,32…일 때 다시 이동한다. n개까지 총 이동은 8+16+…+n < 2n이므로 좋은 hash 분포 아래 resize 이동의 총 expected cost는 O(n), put당 amortized expected O(1)이다. amortized는 확률이 아니고 expected는 worst bound가 아니다.

10. Memory·locality·production trade-off

  • Flat slots: 연속 배열은 chaining node보다 pointer chase와 allocation이 적어 cache locality가 좋다. 대신 낮은 α를 유지하는 빈 slot memory가 필요하다.
  • State layout: 이 교육 구현은 slot마다 enum padding을 낭비한다. production Swiss table 계열은 control bytes를 별도로 묶고 SIMD로 후보를 여럿 검사한다.
  • Tombstone debt: live α가 낮아도 used α가 높으면 miss가 길다. 둘을 따로 metric으로 내고 same-capacity rehash 조건을 둔다.
  • Stop-the-world resize: 구현은 단순하지만 한 요청이 O(n) migration과 약 2배 peak memory를 부담한다. 큰 table은 incremental rehash나 shard를 검토한다.
  • Pointer stability: resize는 slot 주소를 바꾼다. 내부 value pointer를 외부에 장기 대여하지 않거나 stable indirection을 명시한다.
  • Concurrency: 이 map은 thread-safe가 아니다. mutex를 둘러도 iterator·rehash·callback 재진입 계약까지 설계해야 한다.

11. Benchmark를 믿기 전에

  • compiler·flags·CPU·capacity·key corpus·seed·warm-up·반복 횟수를 기록한다.
  • wall time 하나만 보지 말고 avg/max/p50/p99 probe, equality count, resize count, bytes, allocation을 함께 본다.
  • insert와 lookup을 섞으면 resize가 어느 구간에 들어갔는지 숨는다. steady-state와 lifecycle을 분리한다.
  • benchmark 자체의 hash/key 생성 비용이 측정 구간에 섞이지 않게 corpus를 미리 만든다.
  • 평균 난수뿐 아니라 production cardinality skew, common prefix, stride, duplicate, miss, churn, 공격 corpus를 넣는다.
  • microbenchmark의 0.x ms를 API p99로 외삽하지 않는다. allocator, lock, NUMA, cache contention, GC가 실제 경로를 바꾼다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. open addressing에서 삭제를 EMPTY로 바꾸면 왜 안 되나요?
home이 같은 A 뒤에 B가 밀린 최소 cluster를 그린다. A를 EMPTY로 만들면 B lookup이 그 자리에서 조기 종료해 거짓 miss다. tombstone, backward-shift deletion의 proof 조건, live/used α trade-off까지 연결한다.
Q2. resize 중 OOM에도 map을 안전하게 유지하려면?
old table은 read-only로 두고 candidate를 allocate→모든 FULL 재삽입→검증→pointer swap하는 two-phase commit을 설명한다. capacity overflow 사전 검사, exact-state fault test, peak 2× memory와 incremental migration 대안까지 말한다.
Q3. “hash map은 O(1)”을 검증하는 benchmark를 설계해보세요.
expected/amortized/worst를 먼저 분리한다. production·adversarial corpus, hit/miss/update/churn, α sweep, probe histogram·p99/max·allocation·resize를 측정하고 differential/RI/fault/sanitizer로 correctness gate를 앞에 둔다. 이번 stride 반례의 10,000.5 probe를 예로 든다.

  • 내 서비스의 실제 key corpus와 p99 budget으로 threshold를 결정했는가?
