한 줄 요약
“배열이 빠르다”, “연결 리스트 삽입은 O(1)”가 아니라, 실제 요청에서 어떤 연산이 몇 번 발생하고 위치를 이미 알고 있는지 세어 전체 비용·locality·reference 안정성·overflow 정책을 함께 비교해야 한다.

1. 초보자를 위한 용어 사전

Sequence값 자체가 아니라 외부에서 정한 순서와 rank를 보존하는 ADT. 첫째·마지막·i번째가 의미를 갖는다.
Operation mixread, append, prepend, erase, iterate가 각각 몇 번·어느 위치에서 일어나는지 나타낸 빈도 벡터.
Position discovery삽입·삭제할 node나 index를 찾는 비용. mutation 자체와 분리해야 한다.
Random access앞 원소를 거치지 않고 i번째 원소에 접근하는 능력.
Contiguous원소 저장 영역이 주소상 연속이라는 뜻. array index 공식과 cache locality의 기반이다.
Iterator/reference stabilitycontainer mutation 뒤에도 보관한 위치·원소 참조가 계속 유효한 성질.
Invalidationresize·insert·erase 뒤 기존 pointer/iterator가 더 이상 안전하지 않은 상태.
Locality곧 사용할 데이터가 가까운 cache line/page에 함께 있어 memory stall이 줄어드는 성질.
Amortized드문 비싼 resize 비용을 충분히 긴 연산열 전체에 나눈 평균 상한. 한 번의 tail latency 보장은 아니다.
Boundedcapacity 상한이 정해져 overflow 시 block/reject/drop 같은 명시적 결과를 갖는 상태.
Weighted cost연산별 비용에 실제 빈도를 곱해 합산한 workload 전체 비용 모델.

3. 문제·입출력·제약 mental model

문제: 하나의 in-memory 작업 목록에 아래 100만 연산이 반복된다. 올바른 sequence 표현을 고르고 선택을 방어한다.

연산빈도위치·계약
get(i)600ki는 균일 random, 현재 n은 10k~200k
append(x)220k오른쪽 끝, 실패 시 기존 값 보존
pop_front()150kempty는 정상 오류 결과
erase(handle)20k유효 handle이 이미 주어짐
scan()10k전체 순서대로 읽고 합산

입력: 64-bit task ID와 payload reference. 출력: 요청 결과와 순서 보존. 제약: 256MiB budget, p99 5ms, 동시에 읽는 thread가 존재, raw pointer를 외부에 오래 보관하지 않는다.

첫 결론: 한 표현으로 모든 연산을 최적화하려는 질문 자체가 잘못될 수 있다. random access와 유효 handle erase가 모두 중요하면 stable slot store + order index처럼 두 구조를 합성해야 한다.

4. Sequence ADT와 표현 불변식

ADT 계약: 유한한 값 열 S=⟨x₀,…,xₙ₋₁⟩. get(i)는 0≤i<n에서 xᵢ, append/prepend는 순서를 보존해 길이를 1 늘리고, erase는 지정 원소를 정확히 한 번 제거한다. invalid index·empty·full·allocation failure를 서로 다른 결과로 둔다.

표현Abstraction function핵심 RI
Dynamic arraydata[0:size]0≤size≤capacity, live prefix 연속, 나머지 미사용
Sentinel DLLsentinel.next부터 순회한 값양방향 link 대칭, cycle은 sentinel에서만 닫힘, count 일치
Segmented deque논리 index를 block+offset으로 사상양끝 위치가 유효 block 범위, 논리 길이와 slot 수 일치
Bounded ringbuf[(head+i)%C]C>0, 0≤size≤C, tail=(head+size)%C

계약과 표현을 분리해야 하는 이유: Stack/Queue는 허용 연산을 줄인 ADT이고 array/list/deque/ring은 표현이다. “queue는 linked list”가 아니라 bounded 여부·양끝 연산·random access·memory 정책에 맞춰 표현을 선택한다.

6. 가중 비용으로 1차 탈락시키기

위 workload에서 dynamic array는 150k번의 front shift가 있고, DLL은 600k번의 random traversal이 있다. 둘 다 선형 항의 계수가 너무 크다. deque는 양끝에는 맞지만 중앙 random access가 많아 불리하고, fixed-capacity ring은 random access와 양끝에 맞지만 arbitrary stable handle erase를 순서 보존하면서 Θ(1)로 할 수 없다.

합성안: payload는 generation이 붙은 stable slot array에 저장하고, 순서는 block/ring index로 유지한다. external handle은 (slot,generation)으로 stale handle을 검출한다. erase는 slot 회수와 order index 갱신을 분리하며, order를 엄격히 유지하면 여전히 이동 비용이 있음을 숨기지 않는다.

요구사항을 바꾸는 질문: erase 뒤 순서가 중요하지 않다면 dynamic array의 swap-with-last로 Θ(1) 삭제가 가능하다. 그러나 abstract sequence를 바꾸므로 API 계약 승인 없이 적용하면 버그다.

7. 정당성: weighted choice와 최소 반례

  1. 후보 적격성: 먼저 각 후보 구현이 같은 ADT postcondition과 failure contract를 만족해야 한다. 틀린 후보의 빠른 benchmark는 무의미하다.
  2. 비용 상한: trace의 각 연산을 해당 후보의 증명된 cost에 대응시키고 합한다. 빈도가 음수가 아니므로 각 항의 upper bound 합은 전체 upper bound다.
  3. 교차점: workload가 바뀌면 가중치가 바뀌므로 최적 후보도 바뀔 수 있다. 선택 결과가 아니라 입력 vector와 가정을 저장한다.
최소 반례 1: linked list에서 index 500 삭제를 “O(1)”이라고 말하면, handle 없이 head부터 찾는 Θ(n)을 누락했다. 최소 반례 2: [A,B,C]에서 B를 swap-with-last로 삭제하면 [A,C]는 값 집합은 맞지만 원래 상대 순서를 보존하는 Sequence postcondition을 어긴다.

8. 직접 구현: trace를 증거로 바꾸는 profiler

from collections import Counter
from dataclasses import dataclass

ALLOWED = {"get", "scan", "push_front", "push_back",
           "pop_front", "pop_back", "erase_handle"}

@dataclass(frozen=True)
class Op:
    name: str
    n: int
    position: str  # front/back/middle/random/already_known

def profile(trace):
    counts = Counter()
    max_n = 0
    for op in trace:
        if op.name not in ALLOWED:
            raise ValueError(f"unknown operation: {op.name}")
        if op.n < 0:
            raise ValueError("negative size")
        counts[(op.name, op.position)] += 1
        max_n = max(max_n, op.n)
    return counts, max_n

instrumentation은 request path에서 매번 lock을 잡지 말고 thread-local counter나 sampling을 사용한다. key·payload 같은 민감 값은 기록하지 않고 operation, size bucket, position class, latency, error만 남긴다. trace가 profile overhead로 workload를 바꾸지 않는지 검증한다.

9. 직접 테스트와 property

  1. 모든 후보를 Python list reference model과 동일 operation sequence로 differential test한다.
  2. empty, capacity 1, wrap, duplicate, invalid index, stale handle, allocation failure를 포함한다.
  3. 각 prefix 뒤 representation invariant와 논리 sequence equality를 검사한다.
  4. dynamic array resize 실패 전후 snapshot이 같아야 한다. 새 buffer 완성 후 commit한다.
  5. iterator invalidation이 있는 API는 mutation 전후 iterator를 재사용하지 못하게 test·type/API로 제한한다.
  6. concurrent 구현이라면 linearization point와 memory ordering을 별도 증명한다. 단일 thread 복잡도 표는 thread safety를 말하지 않는다.

최소 property: 임의의 유효 operation sequence에 대해 iterate(candidate)==reference, len(candidate)==len(reference), invalid operation은 상태를 바꾸지 않는다.

11. Memory, locality, lifetime deep dive

  • Array: 주소는 base+i×sizeof(T). hardware prefetch와 SIMD에 유리하지만 growth reallocation이 모든 참조를 무효화할 수 있다.
  • Linked list: node마다 link·allocator metadata·padding이 들고 다음 주소가 load 결과에 의존해 memory-level parallelism이 낮다. O(1) relink가 cache miss보다 싸다는 보장은 없다.
  • Deque: 여러 연속 block을 map으로 잇는 구현은 양끝 성장과 일부 locality를 절충한다. 언어별 구현 세부와 reference/iterator 규칙을 문서에서 확인한다.
  • Ring: capacity가 고정되면 resize tail과 OOM 경로를 제거하고 최대 memory를 계산할 수 있다. 대신 full 정책과 wrap arithmetic이 계약의 일부다.
  • Handle: raw pointer보다 slot index+generation을 쓰면 use-after-free와 ABA형 stale reuse를 검출하기 쉽다. generation overflow 정책도 필요하다.

예상 관찰: 오른쪽 stack workload에서는 list와 deque가 비슷할 수 있지만, 왼쪽 queue workload에서는 deque가 급격히 우세하고, 중앙 random index가 많아지면 list가 다시 유리해진다. cleanup은 생성한 임시 benchmark 파일만 제거하고 원본 자료는 건드리지 않는다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. 배열과 linked list 중 무엇을 고르겠습니까?
ADT 계약 → n과 operation/position 빈도 → position discovery 여부 → 점근 비용 → locality·allocation·bytes/element → iterator 안정성 → OOM/동시성 → 대표 benchmark와 재검토 조건 순으로 답한다. “상황에 따라”에서 멈추지 말고 수치를 가정한다.
Q2. linked list의 중간 삭제는 왜 O(1)이 아닐 수 있습니까?
유효한 node handle이 이미 있고 소유권/lifetime 검증이 끝났을 때 relink만 Θ(1)이다. index/key로 위치를 찾으면 Θ(n), allocator/free와 cache miss도 실제 비용이며 stale handle·iterator 계약을 방어해야 한다.
Q3. random access와 stable handle erase가 모두 많다면?
한 container 선택을 거부하고 slot map/generation handle + order index 같은 합성안을 제시한다. 두 representation의 일관성 RI, partial failure rollback, memory overhead, 순서 보존 삭제 비용, concurrency linearization을 함께 설명한다.
