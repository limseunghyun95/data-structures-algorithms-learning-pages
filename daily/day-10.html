한 줄 요약
linked list의 삽입·삭제가 Θ(1)이라는 말은 그 위치의 유효한 node handle을 이미 가지고 있을 때 pointer 몇 개만 다시 잇는 비용이다. 위치를 찾는 데는 Θ(n), 각 node allocation과 poor locality에는 별도 실무 비용이 든다.

1. 초보자를 위한 용어 사전

Sequence ADT원소의 앞뒤 순서가 의미 있고, 삽입·삭제·순회 같은 연산 계약을 가진 추상 자료형.
Node값(payload)과 다른 node로 가는 link를 함께 저장하는 개별 객체.
Pointer / link다음 또는 이전 node의 주소. 화살표 하나가 배열처럼 물리적으로 붙어 있다는 뜻은 아니다.
Singly linked list각 node가 next만 가져 정방향으로 연결된 list.
Doubly linked list각 node가 prev와 next를 가져 양방향으로 연결된 list.
Head / tail첫 node / 마지막 node를 찾기 위한 list의 진입점.
Sentinelpayload가 아닌 경계용 가짜 node. empty와 양 끝 case를 같은 pointer 연산으로 통일한다.
Circular list마지막의 next가 시작으로, 시작의 prev가 마지막으로 돌아오는 고리 표현.
Cursor / handle특정 node를 직접 가리키는 참조. 유효성과 어느 list 소속인지가 API 계약의 일부다.

Splicenode 구간을 복사하지 않고 link만 바꿔 다른 위치나 list로 옮기는 연산.
Pointer chasing다음 주소를 현재 node에서 읽어야 다음 memory access를 시작할 수 있는 의존적 순회.
Dangling pointer / UAF해제된 node 주소가 남은 참조 / 그 참조를 다시 읽거나 쓰는 use-after-free 오류.
Iterator invalidation구조 변경 뒤 cursor·iterator가 더는 안전한 위치를 나타내지 않는 상태.
Allocatormalloc/free처럼 memory block의 수명과 배치를 관리하는 구성요소.

3. 문제·입출력·제약 mental model

문제: job을 순서대로 보관하고 양 끝 삽입·삭제, 정방향/역방향 순회, scheduler가 이미 가진 job handle의 제거를 지원한다.

  • 입력: int64 job id, 앞/뒤 삽입 명령, pop 명령, 선택적으로 유효한 node handle.
  • 출력: 논리 순서를 유지한 sequence와 pop된 값 또는 구체적인 오류 상태.
  • 성공 계약: push-back(x) 뒤 abstract sequence는 old ⧺ ⟨x⟩, pop-front는 첫 값을 반환하고 나머지 suffix를 보존한다.
  • 실패 계약: invalid argument·empty·size overflow·OOM을 구분하고, 실패 시 list의 link·size·값은 호출 전과 같다.
  • 핵심 제약: handle의 출처와 lifetime, 최대 node 수, allocation rate, scan 비율, reverse traversal, thread 접근, p99 latency.
  • 숨은 질문: “중간 위치”가 index인가 이미 찾은 node인가? 전자는 찾는 데 Θ(n), 후자만 relink가 Θ(1)이다.

4. 두 표현을 그림으로 읽기

Singly, NULL 종료:

head→A | next→B | next→ NULL

Doubly, circular sentinel:

root
sentinel		⇄prev | A | next⇄prev | B | next⇄ root

empty일 때는 root.next == root이고 root.prev == root다. 첫/마지막 node도 일반 node처럼 root와 연결되므로 insert/remove helper에서 NULL과 “마지막 하나” 분기가 사라진다.

5. List ADT, abstraction function, representation invariant

Abstract value: 길이 n의 sequence ⟨x₀,…,xₙ₋₁⟩. AF: root.next에서 next를 따라 root 직전까지 만나는 payload를 순서대로 읽는다.

Representation invariant왜 필요한가
root.next != NULL && root.prev != NULL초기화된 circular list는 NULL 경계를 쓰지 않는다.
u.next.prev == u모든 forward edge의 역방향 edge가 대칭이다.
u.prev.next == u모든 backward edge의 정방향 edge가 대칭이다.
root에서 next로 정확히 size개 후 root끊어진 component, 짧은 cycle, 잘못된 size를 금지한다.
size==0 ⇔ root.next==&root==root.prevempty의 canonical state.
root는 payload가 아니며 각 live node는 정확히 한 번 도달sentinel 노출과 중복 ownership을 막는다.
List64가 모든 live node를 단독 소유destroy는 각 node를 정확히 한 번 free한다.

ADT 연산: init, len, push-front/back, pop-front/back, iterate, 그리고 valid cursor가 있을 때 insert-before/erase/splice. cursor의 소속·유효성을 확인하지 않는 내부 primitive는 public API와 분리한다.

6. 직접 구현: owning doubly list + sentinel

#include <stdbool.h>
#include <stdint.h>
#include <stddef.h>
#include <stdlib.h>

typedef struct Node {
    struct Node *prev, *next;
    int64_t value;
} Node;

typedef struct { Node root; size_t size; } List64;
typedef enum {
    LIST_OK, LIST_INVALID, LIST_EMPTY, LIST_OOM, LIST_OVERFLOW
} ListStatus;
typedef void *(*AllocFn)(size_t);

static void list_init(List64 *list) {
    list->root.next = &list->root;
    list->root.prev = &list->root;
    list->size = 0;
}

// 내부 primitive: position은 이 list의 live node 또는 root여야 한다.
static void link_before(Node *position, Node *node) {
    node->prev = position->prev;
    node->next = position;
    position->prev->next = node;
    position->prev = node;
}

static void unlink_node(Node *node) {
    node->prev->next = node->next;
    node->next->prev = node->prev;
}

static ListStatus list_push_back_with(
    List64 *list, int64_t value, AllocFn alloc
) {
    if (list == NULL || alloc == NULL) return LIST_INVALID;
    if (list->size == SIZE_MAX) return LIST_OVERFLOW;

    Node *candidate = alloc(sizeof(*candidate));
    if (candidate == NULL) return LIST_OOM; // 아직 state를 안 바꿈
    candidate->value = value;
    link_before(&list->root, candidate);
    ++list->size;                          // 성공 뒤 commit
    return LIST_OK;
}

static ListStatus list_push_back(List64 *list, int64_t value) {
    return list_push_back_with(list, value, malloc);
}

static ListStatus list_pop_front(List64 *list, int64_t *out) {
    if (list == NULL || out == NULL) return LIST_INVALID;
    if (list->size == 0) return LIST_EMPTY;

    Node *victim = list->root.next;
    int64_t value = victim->value;
    unlink_node(victim);
    --list->size;
    victim->prev = victim->next = NULL;   // debug에서 stale link 노출
    free(victim);
    *out = value;
    return LIST_OK;
}

static void list_destroy(List64 *list) {
    if (list == NULL) return;
    Node *node = list->root.next;
    while (node != &list->root) {
        Node *next = node->next;           // free 전에 저장
        free(node);
        node = next;
    }
    list_init(list);                       // 재호출 가능한 empty state
}

트랜잭션 경계: allocation과 overflow 검사를 먼저 끝낸다. 성공한 candidate만 link하고 마지막에 size를 늘리므로 OOM이면 old AF와 RI가 그대로다. out은 list가 소유한 node 내부와 alias하지 않는다는 계약도 문서화해야 한다.

7. 정당성: 네 pointer write로 순서를 보존한다

insert-before(position, x): 호출 전 이웃을 a=position.prev, b=position라 하자. RI로 a.next=b이고 b.prev=a다. x.prev=a, x.next=b, a.next=x, b.prev=x를 쓰면 기존의 다른 edge는 그대로이고 구간 a⇄b만 a⇄x⇄b로 바뀐다. 따라서 AF는 정확히 그 위치에 x를 한 번 추가하고 양방향 대칭 RI를 보존한다.

unlink(x): a=x.prev, b=x.next를 먼저 잡고 a.next=b, b.prev=a로 만든다. x 외의 순서는 바뀌지 않고 x만 도달 불가능해지므로 AF에서 x 하나만 제거된다. 이후에만 size 감소와 free를 수행한다.

종료: iterative destroy는 매 반복마다 남은 live node 수를 1 줄이는 variant를 가진다. 유한한 size와 RI 때문에 root에 도달해 종료하며 재귀 stack overflow가 없다.

최소 반례 — 한쪽 link만 수정: A⇄B에서 A.next=C, C.next=B만 쓰고 B.prev와 C.prev를 빼먹으면 forward scan은 보이지만 B.prev.next != B가 된다. reverse scan·erase에서 corruption이 터진다. “앞으로 잘 돈다”는 DLL correctness가 아니다.

10. Memory와 locality: 같은 Θ(n)이 아니다

이 머신의 64-bit layout에서 int64 payload는 8 bytes, SNode는 16 bytes, DNode는 24 bytes였다. 이는 allocator metadata·alignment·fragmentation을 빼도 array의 2배/3배다. node가 흩어지면 hardware prefetcher가 다음 주소를 미리 알기 어렵고 각 next load가 다음 load의 시작을 막는다.

100만 int64 합산, 7회 중 best시간배열 대비
contiguous array0.119 ms1.0×

환경: Apple clang 21, arm64, macOS 26.5.2, -O3. 개별 malloc한 node 100만 개를 allocation order와 deterministic shuffle order로 연결해 합을 계산했다. best-of-7은 noise를 줄이지만 분포·NUMA·allocator·cache warm 상태를 대표하지 않는다. SLL/DLL의 allocation-order 순위 차이처럼 작은 차이를 구조의 보편 법칙으로 읽지 말고, array와 dependent pointer chain 및 배치 변화의 큰 차이를 해석한다.

11. 구현 테스트, invariant checker, fault injection

static bool list_valid(const List64 *list) {
    if (!list || !list->root.next || !list->root.prev) return false;
    const Node *node = &list->root;
    size_t seen = 0;
    do {
        if (!node->next || !node->prev) return false;
        if (node->next->prev != node) return false;
        if (node->prev->next != node) return false;
        node = node->next;
        if (node != &list->root && ++seen > list->size) return false;
    } while (node != &list->root);
    return seen == list->size;
}

static void *fail_alloc(size_t ignored) {
    (void)ignored;
    return NULL;
}

List64 list;
list_init(&list);
assert(list_valid(&list));
assert(list_push_back_with(&list, 7, fail_alloc) == LIST_OOM);
assert(list.size == 0 && list_valid(&list)); // failure atomic

for (int64_t i = 0; i < 10000; ++i) {
    assert(list_push_back(&list, i) == LIST_OK);
    assert(list_valid(&list));
}
for (int64_t i = 0; i < 10000; ++i) {
    int64_t out;
    assert(list_pop_front(&list, &out) == LIST_OK);
    assert(out == i && list_valid(&list));
}
list_destroy(&list);
list_destroy(&list); // 이 구현은 init된 list의 반복 destroy 허용

검증 완료: 위 구현은 -Wall -Wextra -Werror -fsanitize=address,undefined로 10,000회 push/pop, 매 단계 RI, 강제 OOM, empty, 반복 destroy를 통과했다. AddressSanitizer는 UAF·double-free·invalid-free를 찾지만 동시성 correctness와 논리 RI까지 증명하지는 않으므로 checker와 property test가 함께 필요하다.

12. Error handling과 production Best Practice

  • 상태를 구분: empty를 null payload와 섞지 말고 status+out parameter 또는 Result 타입으로 표현한다.
  • allocate → initialize → link → size commit: 실패 가능한 작업 전에는 live graph를 건드리지 않는다.
  • handle 계약: 같은 list의 live non-sentinel node만 받는지, erase 후 어떤 handle이 무효인지 API에 쓴다. 필요하면 owner id·generation을 debug build에 둔다.
  • 삭제 순회: current를 free하기 전에 next를 저장한다. callback가 list를 바꿀 수 있으면 mutation policy와 fail-fast/version 규칙을 정한다.
  • 소유권: payload를 node가 소유하는지 빌리는지, destroy callback과 shallow/deep copy 의미를 명시한다.
  • iterative cleanup: 긴 list를 재귀적으로 free해 call stack을 n에 비례시키지 않는다.
  • allocator 전략: node별 malloc이 hot path면 slab/pool 또는 intrusive 구조를 검토하되 pool의 peak retention과 shutdown을 계측한다.
  • 관측: size, allocation failure, operation rate, scan length, lock wait, retired-but-not-reclaimed node를 metric으로 둔다.
  • 테스트: 0/1/2 node, head/tail/middle, self-splice·empty donor, fault injection, randomized model comparison, ASan/UBSan/TSan을 포함한다.

14. Concurrency와 lifetime: pointer 두 개보다 어려운 부분

writer가 A.next와 B.prev를 따로 쓰는 순간 다른 thread는 반쯤 갱신된 graph를 볼 수 있다. Java의 현재 LinkedList 문서도 구조적 변경이 있는 동시 접근에는 외부 동기화가 필요하고 fail-fast iterator에 correctness를 의존하면 안 된다고 명시한다. Linux kernel 문서는 대부분 lock을 쓰고 read-mostly 특수 case에는 RCU primitive를 권한다.

  • Lock-based: list invariant 전체를 한 critical section에서 바꾸고 iterator의 lock lifetime을 정한다.
  • RCU/epoch/hazard pointer: unlink와 memory reclaim을 분리한다. reader가 stale pointer를 더는 쓸 수 없다는 grace period 뒤 free한다.
  • ABA: 주소 A의 node를 free한 뒤 새 node가 같은 주소 A를 받으면 pointer equality만으로 “같은 node”라 오판할 수 있다. version/tag 또는 안전한 reclamation이 필요하다.
  • Serialization: raw pointer는 process 밖 의미가 없다. 값과 순서를 직렬화하고 load 시 새 link와 RI를 재구성한다.

15. 언어·시스템 구현에서 읽을 것

  • Linux: circular intrusive doubly list와 container_of를 사용한다. 삭제 시 link poison, safe iteration, list_splice_init, lock/RCU 규칙이 교과서의 ownership 빈칸을 채운다.
  • Rust 1.97.1 docs: LinkedList는 owned doubly-linked nodes이며 양 끝 push/pop은 constant time이지만, 공식 문서가 대부분의 경우 Vec/VecDeque의 속도·memory·cache 사용이 낫다고 경고한다.
  • Java SE 26: LinkedList는 List와 Deque의 doubly-linked 구현이고 index access는 가까운 끝에서 순회한다. synchronized가 아니며 fail-fast는 correctness 보장이 아니다.

면접 포인트: 언어의 class 이름을 암기하지 말고 ADT 계약, representation, invalidation, allocator, concurrency guarantee가 서로 다른 층임을 분리해서 말한다.

16. 90분 실습

  1. 0–15분: SLL과 circular-sentinel DLL의 AF·RI를 말로 쓰고 0/1/2 node 그림을 그린다.
  2. 15–40분: 위 List64의 push-front/back, pop-front/back을 구현하고 status를 구분한다.
  3. 40–55분: list_valid를 모든 mutation 뒤 호출하고 한쪽 prev write를 고의로 빼 실패를 관찰한다.
  4. 55–70분: fail allocator, 삭제 중 순회, double destroy, randomized array-model 비교를 테스트한다.
  5. 70–82분: array/SLL/DLL을 allocation order와 shuffled order로 scan하고 median·p95도 기록한다.
  6. 82–90분: “왜 production queue는 LinkedList보다 ring buffer일 수 있는가?”를 locality·allocation·bounded memory로 90초 설명한다.

17. 대기업 면접 질문 3개와 답변 포인트

Q1. Linked list 중간 삭제는 정말 O(1)인가요?
답변 포인트: DLL에서 같은 list의 live node handle을 이미 가졌을 때 predecessor/successor relink는 Θ(1). index/value로 node를 찾으면 Θ(n), SLL은 predecessor가 추가로 필요. allocator·reclamation 비용은 RAM model 밖 실무 비용.

Q2. Sentinel circular DLL이 NULL head/tail보다 좋은 점과 위험은?
답변 포인트: empty·head·tail case를 동일한 4 pointer update로 통일해 branch와 proof case를 줄인다. root는 payload가 아니며 반드시 자기 자신으로 초기화. 잘못된 소속 handle·sentinel erase는 corruption이므로 private primitive와 public validation을 분리.

Q3. Array보다 list를 선택할 production workload를 방어해 보세요.
답변 포인트: stable node address가 필요하고 이미 handle이 있으며 잦은 known-node unlink/range splice, reverse traversal이 핵심일 때. scan/index/queue가 핵심이면 cache·memory·allocation 때문에 array/deque 우선. benchmark는 실제 node 배치와 allocator까지 포함.

18. 퀴즈·누적 리뷰·다음 날 연결

  1. tail pointer가 있는 SLL도 pop-back이 Θ(n)인 이유는?
  2. DLL erase에서 네 pointer 관계 중 두 개만 고치면 어떤 RI가 깨지는가?
  3. owning list push가 OOM일 때 failure-atomic하려면 allocation과 link 중 무엇이 먼저인가?
  4. array와 list scan이 모두 Θ(n)인데 큰 시간 차가 날 수 있는 CS 이유 두 가지는?
  5. 삭제하며 순회할 때 current를 free하기 전 보존할 것은?
정답: ① 마지막 node의 predecessor를 찾으려면 head부터 순회 ② next.prev/prev.next 양방향 대칭 ③ allocation·초기화를 먼저 하고 성공 뒤 link ④ cache-line locality·prefetch/vectorization 대 dependent pointer chasing·node/allocator overhead ⑤ next handle.

누적 리뷰: Day 08의 contiguous locality, Day 09의 dynamic array 성장과 비교하라. array는 위치 계산과 bulk scan에 강하고 resize가 pointer를 무효화한다. list는 node 주소를 유지하며 known position을 relink하지만, 위치 계산 대신 search와 pointer chasing을 낸다.
