worst · average · amortized
complexity를 구분하는 법

“평균 O(1)” 뒤에 숨은 확률·연산열·tail latency를 분리하기 · 이론 40분 + 실습 30분

한 줄 요약
worst case는 크기 n의 입력 중 가장 비싼 한 번, average case는 명시한 입력 분포의 기댓값, amortized cost는 확률 없이 가능한 연산 sequence 전체의 총비용을 나눈 보장이다. 셋은 서로 대체할 수 없고 production에서는 p99·메모리 peak까지 함께 봐야 한다.

1. 용어 사전

Worst case크기가 n인 허용 입력·상태 중 비용이 최대인 경우. 단일 요청의 상한을 논할 때 중요하다.
Average case입력 x가 나올 확률 P(x)를 정했을 때 비용 C(x)의 기댓값 E[C(X)]. 분포를 쓰지 않은 평균은 불완전하다.
Expected cost기댓값 비용. 입력 분포, 알고리즘 내부 난수, 또는 둘 모두에 대해 기대할 수 있으므로 확률의 출처를 밝혀야 한다.
Amortized cost연산 sequence의 총비용 상한을 연산 수로 나눈 비용. 확률 분포 없이 모든 허용 sequence에 대해 증명한다.
Aggregate methodk개 연산의 실제 비용을 직접 모두 더해 총비용을 구하는 상각 분석법.
Accounting method싼 연산에 실제보다 큰 비용을 청구해 credit을 저장하고 미래의 비싼 연산을 지불하는 분석법.
Potential Φ자료구조 상태에 저장된 “미래 작업 에너지”. 실제 비용에 상태 전후 potential 차이를 더해 상각 비용을 계산한다.
Tail latencyp95·p99·p99.9처럼 느린 쪽 꼬리 지연. amortized O(1)이어도 한 번의 resize가 tail을 크게 만들 수 있다.

2. Mental model: 어떤 질문에 답하려는가?

분석 종류를 먼저 고르는 이유는 답이 다르기 때문이다. dynamic array append는 한 번의 worst case가 Θ(n)이지만, n번 append의 총비용은 Θ(n)이어서 append당 amortized Θ(1)이다. 이 문장을 “평균 O(1)”로 줄이면 확률 평균인지 연산열 보장인지 사라진다.

3. 세 분석은 서로 다른 축이다

분석무엇 위에서 계산?확률 필요?보장 대상
Worst크기 n 입력의 최댓값아니오단일 연산 상한
Average입력 분포 P(X)의 기댓값예그 분포에서의 평균

예시: 길이 n 배열의 linear search에서 성공 위치가 균등하다고 가정하면 평균 비교 횟수는 (n+1)/2다. 하지만 production 요청이 앞쪽 key에 치우치거나 실패 검색이 많으면 평균은 달라진다. 반면 dynamic array의 amortized 보장은 “입력이 균등하다” 같은 가정을 하지 않는다.

4. ADT와 representation invariant: DynamicArray

Sequence ADT의 append(x), get(i)를 contiguous buffer로 구현한다. 공간이 가득 차면 capacity를 2배로 늘리고 기존 reference를 복사한다.

  • State: 논리 원소 수 size=n, 물리 슬롯 수 capacity=C, buffer.
  • Invariant 1: 0 ≤ n ≤ C이고 C는 양수다.
  • Invariant 2: ADT의 i번째 값은 buffer[i]에 있으며 0 ≤ i < n이다.
  • Invariant 3: 사용자가 볼 수 없는 buffer[n:C]는 spare capacity이며 논리 길이에 포함되지 않는다.
  • Postcondition: 성공한 append 뒤 size는 정확히 1 증가하고 이전 원소 순서와 값이 보존된다.

CPython의 list도 linked list가 아니라 reference의 contiguous variable-length array이며, 반복 append마다 resize하지 않도록 여유 공간을 할당한다. 단, CPython의 실제 growth factor는 구현 세부이므로 API 계약처럼 고정해 가정하면 안 된다.

5. Aggregate proof: 비싼 resize를 모두 더한다

초기 capacity가 1이고 full일 때 2배로 증가한다고 하자. append 자체 write 비용을 1, resize 때 기존 원소 하나 복사를 1로 센다.

m번 append write: m
resize copy: 1 + 2 + 4 + ··· + 2⌊log₂m⌋ < 2m
총비용: < 3m = Θ(m)
append당 상각 비용: Θ(m) / m = Θ(1)

어떤 한 append는 Θ(n) 복사를 일으킬 수 있으므로 worst-case Θ(n)은 그대로다. 상각 분석은 비싼 연산을 없애는 것이 아니라, 그런 연산이 충분히 자주 연속될 수 없음을 증명한다.

6. Accounting과 potential: 같은 보장을 다른 언어로

Accounting: 각 append에 상수 개의 coin을 청구한다. 실제 write에 하나를 쓰고 나머지를 새로 들어온 원소에 저장한다. 다음 resize까지 Θ(n)개의 싼 append가 쌓이므로 저장한 credit이 Θ(n) copy 비용을 낸다. bank balance는 음수가 되면 안 된다.

Potential: append-only doubling에서 Φ(D)=max(0, 2n−C)로 둔다. 따라서 빈 초기 상태에서 Φ=0이고 항상 음수가 아니다. load factor가 1/2 이상인 구간에서는 Φ=2n−C로 계산한다. 상각 비용은 ĉᵢ = cᵢ + Φ(Dᵢ) − Φ(Dᵢ₋₁)이다.

상황실제 cᵢΔΦ상각 ĉᵢ
resize 없음1≤ +2≤ 3
full에서 2배n+12−n3

합을 취하면 중간 potential들이 telescoping되어 Σĉᵢ = Σcᵢ + Φ(Dₘ) − Φ(D₀)가 된다. Φ가 0에서 시작하고 음수가 아니면 상각 비용 합은 실제 비용 합의 상한이다. potential은 실행되는 저장 공간이 아니라 분석용 함수다.

7. 직접 구현: 비용과 invariant를 관찰한다

class DynamicArray:
    def __init__(self, max_capacity=1 << 24):
        if max_capacity < 1:
            raise ValueError("max_capacity must be positive")
        self.size = 0
        self.capacity = 1
        self.buffer = [None]
        self.max_capacity = max_capacity
        self.copies = 0

    def _check(self):
        assert 0 <= self.size <= self.capacity
        assert len(self.buffer) == self.capacity

    def append(self, value):
        self._check()
        copied = 0
        if self.size == self.capacity:
            if self.capacity > self.max_capacity // 2:
                raise OverflowError("capacity limit exceeded")
            new_capacity = self.capacity * 2
            new_buffer = [None] * new_capacity
            for i in range(self.size):
                new_buffer[i] = self.buffer[i]
                copied += 1
            self.buffer = new_buffer
            self.capacity = new_capacity
            self.copies += copied
        self.buffer[self.size] = value
        self.size += 1
        self._check()
        return 1 + copied  # write 1 + resize copy count

a = DynamicArray()
costs = [a.append(i) for i in range(1, 1025)]
assert a.buffer[:a.size] == list(range(1, 1025))
assert a.copies < a.size
assert sum(costs) < 2 * a.size
print("worst single:", max(costs))
print("amortized observed:", sum(costs) / len(costs))

정당성 포인트: resize는 기존 buffer[0:size]를 같은 index에 복사한 뒤 새 buffer를 공개하므로 순서·값 invariant를 보존한다. allocation이 실패하면 assignment 전이므로 기존 buffer가 남는 구조다. 실제 언어에서는 allocator·move의 exception guarantee도 확인해야 한다.

8. 최소 반례: 잘못된 shrink 정책은 thrashing을 만든다

“절반 이하가 되면 capacity도 바로 절반으로 줄이고, full이면 2배로 늘린다”고 하자. size가 경계 근처일 때 pop → append → pop → append를 반복하면 매번 Θ(n) 복사할 수 있다. 그러면 연산당 amortized Θ(1) 보장이 무너진다.

해결: hysteresis. grow는 load 1에서 2배, shrink는 load 1/4 아래에서 절반으로 해 서로 다른 문턱을 둔다. resize 사이에 Θ(n)번의 싼 연산이 필요해지고, capacity는 여전히 Θ(size)를 유지한다.

9. 시간·공간·locality·production trade-off

  • Time: append worst Θ(n), amortized Θ(1). index access는 Θ(1).
  • Space: steady-state capacity는 Θ(n)이지만 resize 순간 old/new buffer가 공존해 peak memory가 커질 수 있다.
  • Locality: contiguous reference array는 순차 scan과 prefetch에 유리하지만 큰 copy가 memory bandwidth를 사용한다.
  • Latency: amortized 보장은 p99를 보장하지 않는다. real-time·low-latency 경로에서는 preallocation, chunked storage, bounded ring buffer, incremental migration을 고려한다.
  • Concurrency: resize 중 pointer 교체와 reader 접근을 동기화해야 한다. lock contention과 reclamation 비용은 단일 thread 분석 밖에 있다.

10. Error handling과 실무 Best Practice

  • checked capacity: capacity * growth_factor overflow와 platform 최대 index를 allocation 전에 검사한다.
  • OOM atomicity: 새 buffer 확보·복사가 성공한 뒤에만 state를 교체해 실패 시 기존 값과 invariant를 보존한다.
  • resource limit: untrusted batch 크기에 상한을 두고 MemoryError/OOM kill보다 앞서 명시적 오류를 반환한다.
  • tail 지표: 평균 append latency만 보지 말고 resize count, copied bytes, allocation failure, p99와 max를 수집한다.
  • workload 분리: steady state와 cold start, grow-heavy와 oscillating grow/shrink, single-thread와 contention을 따로 측정한다.
  • 계약 문구: “append amortized O(1)”과 “단일 append worst O(n)”을 API·설계 문서에 함께 적는다.
Anti-pattern: 평균 입력 분포를 쓰지 않은 average O(1), 한 번의 latency SLO를 amortized O(1)로 방어, benchmark 평균만 보고 resize spike를 삭제, 구현의 현재 growth factor를 영구 API 계약으로 간주하는 것.

11. 30분 실습: 평균과 꼬리를 동시에 보기

  1. 위 구현에서 append 수를 2¹⁰, 2¹⁵, 2²⁰으로 바꾸고 sum(costs)/m과 max(costs)를 기록한다.
  2. growth factor를 1.25, 1.5, 2로 바꿔 총 copy 수, 최악 copy 수, 마지막 spare capacity를 비교한다.
  3. 잘못된 shrink-at-half와 hysteresis 정책을 각각 구현해 경계에서 pop/append 1,000회를 반복한다.
  4. 실제 시간 benchmark는 입력 준비를 측정 밖에 두고 warm-up 후 여러 번 반복해 median과 p99를 기록한다.

예상: factor가 크면 resize 빈도·총 copy는 줄지만 spare memory가 늘 수 있다. amortized 차수는 같아도 production trade-off는 다르다.

Benchmark 오류 처리: allocation 실패나 capacity limit 초과를 느린 정상 샘플로 섞지 말고 별도 failure counter로 기록한다. timer resolution보다 짧은 연산은 batch로 묶되 resize spike를 숨기지 않도록 per-operation logical cost도 함께 수집한다.

12. 대기업 면접 질문 3개

  1. average와 amortized complexity의 차이는?
    average는 입력·난수 분포에 대한 기댓값이고, amortized는 확률 없이 모든 허용 연산 sequence의 총비용 상한이라고 답한다. “둘 다 평균”으로 끝내지 않는다.
  2. dynamic array append가 O(1)이라고 말해도 되는가?
    amortized Θ(1), 단일 worst Θ(n), space Θ(n), resize 순간 peak·tail latency를 함께 말하고 aggregate 또는 potential 증명을 제시한다.
  3. amortized O(1)이면 low-latency 서비스에 충분한가?
    아니다. 한 요청의 spike를 허용할 수 없으면 preallocate, bounded/chunked 구조, incremental resize를 검토하고 p99와 max를 측정해야 한다.
