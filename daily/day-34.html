한 줄 요약
안전한 KV store는 map 하나가 아니라 WAL에 완전한 batch를 기록하고 durability 계약만큼 sync한 뒤 memtable에 반영하며, immutable SSTable과 원자적으로 설치된 manifest를 통해 최신 sequence와 tombstone을 보존하는 작은 상태 머신이다.

Key-Value storekey로 value를 저장·조회하는 저장소. 사전처럼 보이지만 persistence·동시성·복구 계약이 추가된다.

2. 문제·입출력·제약 mental model

Put(key, value, sync=true|false) Delete(key, sync=true|false) Get(key, snapshot?) -> value | NOT_FOUND Scan(lo, hi, snapshot?) -> ordered entries WriteBatch([Put/Delete...], sync=true|false) -> all-or-none

목표 workload는 작은 key/value, point read와 write 중심, 제한된 range scan이다. 핵심은 평균 latency만이 아니다. process kill, torn tail, disk full, checksum mismatch, 재시작 중 재-crash에도 성공 응답한 sync batch는 모두 보이고, 실패하거나 불완전한 batch는 일부만 보이지 않아야 한다.

3. Architecture: write·flush·read·recovery 흐름

WRITEvalidate → sequence 배정 → batch frame → WAL append → 필요한 경우 sync → memtable apply → ACK
↓ memtable limit 도달: active/immutable 교체
FLUSHimmutable 정렬 → temp SST 작성/checksum → file sync → rename → manifest install/sync → obsolete WAL 회수
↓ Get는 newest-to-oldest, Scan은 k-way merge
READactive → immutable → L0 newest first → lower levels; Bloom negative는 skip, positive는 실제 key 확인
↓ open/restart
RECOVERCURRENT/MANIFEST 검증 → live SST open/checksum → 필요한 WAL record prefix replay → sequence 복원 → serving

순서가 설계다. ACK가 WAL sync보다 앞서면 성공 응답한 write가 사라질 수 있다. 반대로 memtable apply가 WAL append보다 앞서면 process가 살아 있는 동안 보이던 값이 복구되지 않는다. flush에서는 완성되지 않은 SST를 manifest가 참조하지 않도록 temp file을 완성한 뒤 metadata에 설치한다.

4. KV ADT와 representation invariant

ADT: byte-string key의 최신 logical value를 저장하는 ordered map에 atomic batch, durability option, snapshot을 더한다. 내부 파일명이나 level은 추상 계약이 아니다.

  1. committed mutation마다 유일하고 단조 증가하는 sequence가 있으며 batch 내부 순서도 결정적이다.
  2. sync write가 성공했다면 그 batch의 완전한 WAL record는 recovery point 이하에 있다.
  3. snapshot S에서 key의 결과는 seq≤S인 version 중 최대 sequence이며, tombstone이면 NOT_FOUND다.
  4. memtable과 각 SST의 internal key는 (userKey ASC, sequence DESC, type) comparator와 일치한다.
  5. SSTable은 immutable하고 block/file checksum이 맞으며 manifest는 완성된 live file만 참조한다.
  6. L1 이상이 non-overlap 정책이라면 level 내부 key range는 겹치지 않는다. L0 overlap은 newest 순서로 탐색한다.
  7. 열린 snapshot/iterator가 참조하는 file/version은 pin되어 reader가 끝나기 전에 삭제되지 않는다.
  8. WAL은 그 record가 포함된 SST가 manifest에 durable하게 설치되기 전에는 회수하지 않는다.

5. 정당성: linearization과 recovery prefix

write: 동일 writer queue에서 sequence가 배정되고 WAL에 batch가 한 record로 append된다. sync=true의 성공점은 WAL sync 성공 뒤다. 그 뒤 memtable에 같은 record를 적용하므로 정상 실행의 read와 crash replay가 같은 순서를 본다. batch frame이 완전할 때만 replay하므로 부분 batch가 노출되지 않는다.

Get: 후보 source를 newest에서 oldest로 탐색해 snapshot 이하 첫 internal key를 선택한다. 각 source가 같은 comparator를 지키고 더 높은 sequence가 우선되므로 이 후보가 정의상 최대 sequence다. tombstone도 version이므로 older value를 가린다.

recovery: 길이 header와 payload가 완전하고 checksum이 맞는 WAL record만 순서대로 replay한다. 마지막 record의 incomplete tail은 ACK되지 않았을 수 있으므로 버려도 된다. 하지만 이미 완전한 중간 record의 checksum mismatch를 단순 EOF처럼 무시하면 뒤의 acknowledged record까지 조용히 잃으므로 corruption으로 실패해야 한다.

최소 반례 1 — sync 전 ACK: WAL write가 page cache에만 있을 때 ACK하고 전원이 끊기면 API는 성공했지만 record가 없다.
최소 반례 2 — tombstone 조기 제거: L0의 delete를 compact하며 버렸지만 L2에 old value가 남아 있으면 삭제한 값이 부활한다.
최소 반례 3 — manifest 선행: 아직 sync되지 않은 temp SST를 manifest가 참조하면 restart가 존재하지 않거나 찢어진 file을 live로 믿는다.

write는 앞에서 빠르지만 미래 merge 비용을 만든다. 평균 amortized write만 보지 말고 compaction debt가 몰릴 때 p99 stall을 본다. 메모리도 memtable만이 아니라 block cache, Bloom/index, pinned old version, compaction input/output가 동시에 차지하는 peak를 계산한다.

7. 직접 구현: 안전한 WAL frame과 write path

MAX_RECORD = 8 * 1024 * 1024 def encode_batch(seq0, ops): payload = encode_u64(seq0) + encode_u32(len(ops)) for op, key, value in ops: require(0 < len(key) <= MAX_KEY) require(value is None or len(value) <= MAX_VALUE) payload += encode_op(op, key, value) require(len(payload) <= MAX_RECORD) return u32(len(payload)) + u32(crc32(payload)) + payload def write_batch(ops, sync): validate_all_before_side_effect(ops) with writer_mutex: wait_until_room_or_return_busy() seq0 = last_sequence + 1 frame = encode_batch(seq0, ops) wal.append_all(frame) # short write면 error if sync: wal.sync() # 실패 시 ACK 금지 memtable.apply_atomically(seq0, ops) last_sequence += len(ops) return OK def replay(stream): while True: header = read_exact_or_tail(stream, 8) if header is INCOMPLETE_TAIL: return length, expected_crc = decode(header) if length > MAX_RECORD: raise CORRUPTION payload = read_exact_or_tail(stream, length) if payload is INCOMPLETE_TAIL: return if crc32(payload) != expected_crc: raise CORRUPTION batch = decode_and_validate_whole(payload) apply_idempotently_by_sequence(batch)

이 코드는 교육용 skeleton이다. 실제 구현은 partial syscall, EINTR, directory sync, file lock, endianness/version, allocation failure, concurrency, encryption/authentication, platform별 atomic rename을 더 다뤄야 한다. 특히 record length를 믿고 allocation하면 손상된 4바이트가 수 GB allocation을 유발할 수 있어 먼저 상한을 검사한다.

8. Flush와 manifest 설치 transaction

  1. active memtable을 immutable로 바꾸고 새 WAL+memtable에 write를 계속 받는다.
  2. immutable을 새 번호의 .tmp에 sorted block으로 쓰며 block checksum과 footer를 만든다.
  3. 파일을 flush/sync하고 닫는다. 실패하면 manifest는 건드리지 않고 temp를 나중에 정리한다.
  4. 최종 SST 이름으로 atomic rename한다. crash contract에 필요하면 directory도 sync한다.
  5. “new SST 추가, obsolete input 제거, log number 전진” VersionEdit를 manifest log에 append하고 sync한다.
  6. 새 Version을 publish한 뒤 old version reader가 모두 release한 파일과 WAL만 회수한다.

중요: data file 생성과 metadata publish는 하나의 논리 transaction이다. orphan SST는 공간 누수라서 재시작 때 정리할 수 있지만, manifest가 missing SST를 참조하는 것은 serving state 손상이므로 순서를 orphan 쪽으로 설계한다.

10. Benchmark: run 20개를 compact했을 때

CPython 3.9.1에서 keyspace 20,000에 100,000번 mutation(10% delete)을 주고 5,000 mutation마다 memtable을 flush해 20개 sorted run을 만들었다. 50,000 random Get을 실행한 뒤 newest-wins compaction으로 1개 run을 만들고 reference map과 완전히 비교했다.

Benchmark 주의: 이 수치는 Python object와 warm memory의 교육용 상대 비교다. 실제 SSD의 fsync, block cache, compression, Bloom, concurrent compaction, cold restart를 대변하지 않는다. production에서는 throughput 하나가 아니라 write/read p50·p99, bytes read/written, fsync latency, L0 file 수, pending compaction bytes, stall time, disk headroom을 같은 workload phase에서 기록한다.

12. Production Best Practice

  1. durability level(sync/async)과 batch atomicity를 API·SLO·metrics에 명시한다.
  2. WAL은 length+version+checksum으로 frame하고 decode 전 모든 길이·count·overflow 상한을 검사한다.
  3. group commit으로 한 번의 sync 비용을 여러 writer가 공유하되 각 waiter의 성공 조건을 섞지 않는다.
  4. SST는 immutable temp→sync→rename→manifest sync 순으로 설치하고 recovery에서 orphan과 missing을 다르게 취급한다.
  5. Bloom positive는 “있을 수 있음”일 뿐이므로 반드시 index/data block에서 확인한다. negative만 skip에 쓴다.
  6. snapshot oldest sequence와 reader pin을 추적해 tombstone/file GC의 안전 경계를 계산한다.
  7. L0 files, immutable memtable, pending compaction bytes, stall seconds, WA/RA/SA, checksum error를 dashboard와 alert에 둔다.
  8. disk full 전에 soft/hard threshold로 compaction·write를 제어하고 output 임시 공간까지 capacity plan에 포함한다.
  9. backup은 파일 복사가 아니라 일관된 Version/checkpoint 단위로 만들고 restore drill과 checksum scan을 정기 실행한다.
  10. format version·comparator·compression/encryption setting을 metadata에 넣고 rolling upgrade와 rollback을 시험한다.

13. Anti-pattern과 놓치기 쉬운 것

  • WAL write=durable: page cache append와 storage sync를 혼동한다.
  • 모든 write마다 독립 fsync: correctness는 얻어도 throughput이 무너진다. batch/group commit을 검토한다.
  • checksum mismatch를 EOF 처리: 데이터 손실을 정상 tail recovery로 위장한다.
  • flush 시작 직후 old WAL 삭제: SST/manifest 설치 전 crash하면 replay source가 없다.
  • Bloom positive를 값 존재로 확정: false positive가 API 오답이 된다.
  • tombstone 즉시 제거: lower level·old snapshot·replica에 old value가 남을 수 있다.
  • compaction 무제한 우선: foreground read/write I/O와 cache를 빼앗는다. rate limit와 admission control이 필요하다.
  • 평균 latency만 관찰: compaction debt와 sync tail latency가 장애를 먼저 보여준다.

14. 대기업 면접 질문 3개와 답변 포인트

Q1. Put의 성공을 어디에서 반환해야 하나요?
먼저 durability 계약을 명시한다. sync write라면 batch를 WAL에 완전한 frame으로 append하고 sync가 성공한 뒤 ACK한다. memtable은 read visibility를 위한 구조이지 crash durability의 근거가 아니다. group commit은 가능하지만 각 writer가 포함된 sync completion 뒤에만 깨운다.
Q2. crash 중 찢어진 마지막 WAL record와 중간 checksum 오류를 어떻게 구분하나요?
EOF의 incomplete tail은 ACK되지 않은 suffix일 수 있어 마지막 완전 record까지만 replay한다. 반면 중간의 완전 길이 record가 CRC mismatch면 뒤에 durable record가 있을 수 있으므로 corruption으로 실패·repair해야 한다. 길이 상한을 checksum/할당 전에 검사한다.
Q3. 왜 tombstone을 바로 지우면 안 되나요?
더 오래된 SST에 value가 남아 있으면 삭제 표식 제거 후 그 값이 다시 보인다. bottommost/overlap 범위에 older version이 없음, 모든 관련 snapshot이 tombstone보다 최신임, replication/backup 보존 계약이 충족됨을 증명한 뒤 GC한다.
