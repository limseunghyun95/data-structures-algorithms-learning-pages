입력 크기와 cost model,
Big-O · Θ · Ω

“O(n)”을 말하기 전에 무엇을 n과 한 번의 연산으로 셌는지 밝히기 · 이론 35분 + 실습 30분

한 줄 요약
복잡도는 코드에 붙는 절대 등급이 아니라 입력 크기와 비용을 세는 계산 모델을 먼저 정한 뒤, 그 모델에서 비용 함수의 점근적 상한 O, 하한 Ω, 타이트한 경계 Θ를 설명하는 계약이다.

1. 용어 사전

Input size문제 인스턴스의 규모를 나타내는 변수. 원소 수 하나가 아니라 그래프의 V·E, 행렬의 r·c, 정수의 비트 수처럼 여러 변수일 수 있다.
Cost model어떤 기본 연산을 얼마의 비용으로 셀지 정한 추상 기계. 비교 횟수, word 연산, disk I/O, network round trip 등 목적에 따라 달라진다.
Asymptotic입력이 충분히 커질 때 증가율을 본다는 뜻. 상수항과 낮은 차수 항을 숨기지만 실제 지연 시간까지 없애지는 않는다.
O(g(n))충분히 큰 n에서 비용이 g(n)의 어떤 상수배보다 크지 않다는 점근적 상한.
Ω(g(n))충분히 큰 n에서 비용이 g(n)의 어떤 양의 상수배보다 작지 않다는 점근적 하한.
Θ(g(n))O(g(n))이면서 Ω(g(n))인 타이트한 경계. 같은 증가율 범주에 끼인다는 뜻이다.
Word-RAMw비트 word의 산술·비교·주소 접근을 기본적으로 상수 시간으로 보는 계산 모델. word에 들어가지 않는 값까지 공짜로 처리한다는 뜻은 아니다.

4. O, Ω, Θ의 정확한 관계

상한: f(n) ∈ O(g(n)) ⇔ 어떤 c>0, n₀가 있어 모든 n≥n₀에서 0≤f(n)≤c·g(n)
하한: f(n) ∈ Ω(g(n)) ⇔ 어떤 c>0, n₀가 있어 모든 n≥n₀에서 0≤c·g(n)≤f(n)
타이트: f(n) ∈ Θ(g(n)) ⇔ 어떤 c₁,c₂>0, n₀가 있어 모든 n≥n₀에서 c₁g(n)≤f(n)≤c₂g(n)

f(n)=3n+4는 Θ(n)이다. 동시에 O(n), O(n²), O(2ⁿ)이기도 하다. 그러므로 “O(n²)이 맞다”는 말은 거짓은 아니지만 유용한 타이트한 설명이 아니다. 가능한 경우 Θ를 쓰고, 증명한 것이 상한뿐이면 O라고 정직하게 말한다.

면접 단골 함정: Big-O는 worst case의 동의어가 아니다. O/Ω/Θ는 함수의 경계이고, worst/average/best는 어떤 입력 집합에서 비용 함수를 만들었는지에 관한 case 축이다. 예를 들어 insertion sort의 worst-case 비용은 Θ(n²), best-case 비용은 Θ(n)이라고 함께 말할 수 있다.

5. ADT와 representation이 cost model을 바꾼다

Day 01의 Sequence ADT에서 max() 연산을 제공한다고 하자. 정렬되지 않은 배열 표현이고 원소가 word 크기의 정수라면 모든 원소를 읽어야 하므로 Θ(n) 비교·Θ(n) memory read가 필요하다. 하지만 자료구조가 현재 최대값을 별도 field로 유지한다면 조회는 Θ(1)이 될 수 있다.

  • ADT 계약: 비어 있지 않은 comparable 값 sequence의 최대값을 반환한다.
  • 표현 A: 값만 저장 → 조회 Θ(n), 갱신 Θ(1).
  • 표현 B: 값과 cached max 저장 → 조회 Θ(1), 삽입 Θ(1), 최대값 삭제 시 재계산 또는 추가 구조 필요.
  • Representation invariant: cached max를 쓴다면 cached_max = max(values)가 모든 공개 연산 경계에서 참이어야 한다.

복잡도는 ADT 이름만으로 결정되지 않는다. 같은 연산 계약도 representation invariant를 유지하는 위치에 따라 read/write 비용이 이동한다. 이것이 실무에서 “읽기 최적화냐 쓰기 최적화냐”를 묻는 이유다.

6. 정당성 + 정확한 비용: linear_max

def linear_max(values):
    if not values:
        raise ValueError("max requires a non-empty sequence")

    best = values[0]
    comparisons = 0
    for i in range(1, len(values)):
        comparisons += 1
        if values[i] > best:
            best = values[i]
    return best, comparisons

Loop invariant: 반복문의 i번째 검사를 시작할 때 best=max(values[0:i])이다.

  1. 초기화: i=1일 때 prefix에는 첫 원소 하나뿐이므로 invariant가 참이다.
  2. 유지: values[i]와 best 중 큰 값을 남기면 다음 prefix의 최대값이 된다.
  3. 종료: i=n에 도달하면 prefix가 전체 입력이므로 best는 전체 최대값이다.

n≥1일 때 비교 횟수는 정확히 n−1이므로 word 비교 단위에서는 Θ(n), 추가 공간은 Θ(1)이다. 문자열처럼 비교 한 번이 최악 Θ(L)이면 전체 최악 상한은 O(nL)이다. 같은 코드라도 원소 표현과 cost model을 밝히면 분석이 달라진다.

7. 하한을 말하는 법과 최소 반례

정렬되지 않은 n개 값에서 최대값을 찾는 비교 기반 알고리즘은 모든 원소를 후보와 연결하는 충분한 비교가 필요하다. 비교에서 한 번도 패배하지 않은 원소가 둘 이상 남으면 어느 쪽이 최대인지 결정할 수 없다. 각 비교는 최대 한 후보만 탈락시키므로 n−1회 비교가 필요하다. 위 구현의 n−1회 상한과 만나 Θ(n)이 된다.

잘못된 최적화의 최소 반례: “첫 값과 마지막 값만 비교하면 된다”는 구현은 [1, 100, 2]에서 실패한다. 작은 반례는 정확성 문제를 잡고, 하한 증명은 왜 중간 값을 보지 않는 일반적 지름길이 불가능한지 설명한다.

8. 시간·공간·amortized를 한 문장에 섞지 않는다

축질문예시

amortized는 확률적 average와 다르다. 입력 분포를 가정하지 않고 연산 sequence 전체의 총비용으로 보장한다. 이 구분은 Day 03에서 더 깊게 다룬다.

9. 실무 Best Practice와 error handling

  • 복잡도 문장의 완전형: “n개 64-bit 원소를 contiguous memory에서 읽는 Word-RAM 모델에서 worst-case time Θ(n), auxiliary space Θ(1)”처럼 쓴다.
  • 다변수 보존: 그래프를 무조건 n 하나로 뭉개지 말고 O(V+E)처럼 독립 크기를 유지한다. sparse/dense 차이가 사라지지 않는다.
  • 입력 제한: n, bytes, key length, nesting depth를 validation하고 초과 시 명시적 오류·413·resource limit로 실패시킨다.
  • 산술 overflow: 고정 폭 언어에서 n * element_size를 allocation 전에 checked arithmetic으로 검증한다.
  • 비용 예산: CPU뿐 아니라 peak memory, allocation, cache miss, disk I/O, network round trip, serialization bytes를 기록한다.
  • 관측값 분리: 평균만 보지 말고 p50/p95/p99, timeout, OOM, retry 횟수와 입력 분포를 함께 저장한다.
Anti-pattern: “hash map은 O(1)이니 안전”, “상수는 버리니 locality는 무관”, “benchmark가 빨랐으니 복잡도 증명 완료”, “O(n²)이지만 n은 작을 것”이라고 입력 상한 없이 배포하는 것.

10. 30분 실습: 증가율과 상수항을 함께 측정

from statistics import median
from timeit import repeat

def linear_max(values):
    if not values:
        raise ValueError("non-empty input required")
    best = values[0]
    for x in values[1:]:
        if x > best:
            best = x
    return best

def measure(n):
    data = list(range(n))       # setup은 측정 밖
    samples = repeat(lambda: linear_max(data), number=3, repeat=9)
    return median(samples) / 3

previous = None
for exponent in range(10, 21):
    n = 2 ** exponent
    seconds = measure(n)
    ratio = seconds / previous if previous else float("nan")
    print(n, seconds, ratio)
    previous = seconds

관찰: n을 2배로 키울 때 충분히 큰 구간에서 실행 시간 비율이 대체로 2 근처로 가는지 본다. 정확히 2가 아니어도 Θ(n)과 모순은 아니다. interpreter overhead, slicing, cache 경계, CPU 상태가 상수와 변동을 만든다.

실패 시나리오: 빈 입력은 ValueError가 맞는지, n이 너무 커 allocation에 실패하면 측정값으로 섞지 않고 실패로 기록하는지 확인한다. `values[1:]`는 복사로 Θ(n) 추가 공간을 쓰므로, auxiliary space Θ(1)을 지키려면 index iteration으로 바꿔 비교한다.

Benchmark 체크리스트: warm-up, 반복과 median, 입력 생성 분리, 결과 소비, compiler 최적화 방지, 환경·CPU·버전 기록, 여러 크기 사용. 단일 n의 한 번 측정으로 증가율을 맞히지 않는다.

11. 대기업 면접 질문 3개

  1. Big-O와 Θ의 차이는 무엇이며 “3n+4는 O(n²)”가 왜 나쁜 답인가?
    O는 상한 집합, Θ는 상·하한이 만나는 타이트한 경계다. O(n²)은 참이지만 성장률 정보를 느슨하게 버리므로 Θ(n)이 더 정확하다고 답한다.
  2. hash table lookup은 정말 O(1)인가?
    key hash·equality 비용, load factor와 resizing, 좋은 분포라는 평균/기대 가정, collision attack의 최악 O(n), cache와 concurrency 비용을 분리한다.
  3. 두 알고리즘이 모두 O(n)인데 production 성능이 크게 다른 이유는?
    상수항뿐 아니라 representation, element 크기, allocation, locality, branch, vectorization, I/O, runtime, 입력 분포가 다르며 benchmark와 profiler로 교정한다고 답한다.
