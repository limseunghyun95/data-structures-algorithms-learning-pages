한 줄 요약
Quicksort의 성능은 재귀 자체가 아니라 pivot이 만드는 partition의 균형에 달려 있다. 평균 Θ(n log n)·좋은 locality를 얻되, 3-way duplicate 처리·작은 쪽 우선 재귀·깊이 제한 뒤 heapsort fallback으로 Θ(n²) 시간과 O(n) stack을 production에서 봉쇄한다.

2. 문제·입출력·제약 mental model

Input: A[lo:hi), comparator/key Output: 같은 identity multiset의 nondecreasing permutation Default quicksort: in-place, unstable 먼저 물을 것: - 외부 사용자가 입력 패턴을 제어하는가? - equal key가 많은가? distinct cardinality는? - stable order가 계약인가? - worst latency와 stack 상한이 필요한가? - comparison, swap, record move 중 무엇이 비싼가? - comparator가 strict weak order를 지키는가?

“평균 O(n log n)”만 말하면 설계가 끝나지 않는다. production 선택은 pivot policy + partition scheme + duplicate policy + depth/stack policy + fallback의 묶음이다. stable이 필수라면 일반 in-place quicksort보다 stable library sort를 먼저 검토한다.

4. Sorting ADT와 representation invariant

ADT: sort(A,cmp)는 입력 identity multiset과 같은 원소를 cmp 순서의 permutation으로 만든다. 일반 quicksort는 equal-key 상대 순서를 보존하지 않는다는 점을 API 계약에 명시해야 한다.

Lomuto 상태: pivot은 A[hi-1], scan cursor j와 small-boundary i를 쓴다.

[lo, i) [i, j) [j, hi-1) [hi-1] ≤ pivot > pivot unknown pivot
  • 각 반복 시작에 네 구간이 서로 겹치지 않고 정확히 [lo,hi)를 덮는다.
  • A[j] ≤ pivot이면 A[i]와 바꾸고 i를 증가시켜 ≤ 구간을 한 칸 확장한다.
  • scan 종료 후 pivot과 A[i]를 바꾸면 [lo,i] ≤ pivot, [i+1,hi) > pivot이고 pivot은 i에 고정된다.
  • 재귀 범위는 pivot을 제외한 [lo,i), [i+1,hi)여야 진척되고 무한 재귀가 없다.

5. Lomuto partition 정당성

  1. Initialization: i=j=lo이므로 ≤와 > 구간이 empty이고 invariant가 참이다.
  2. Maintenance: A[j]가 ≤pivot이면 경계 i로 보내 두 구간 성질을 보존한다. >pivot이면 그대로 > 구간 끝에 포함한다. 어느 경우든 unknown이 한 칸 줄어든다.
  3. Termination: j=hi−1이면 unknown이 empty다. pivot을 i로 옮기면 왼쪽은 모두 ≤, 오른쪽은 모두 >이고 pivot 위치가 확정된다.
  4. 전체 correctness: 더 작은 두 범위가 귀납적으로 정렬되고, 왼쪽≤pivot<오른쪽이므로 결합된 범위도 정렬된다.
최소 불안정 반례: [(2,a),(2,b),(1,x)]에서 마지막 pivot 1을 첫 위치로 옮기면 [(1,x),(2,b),(2,a)]. 값은 정렬되지만 equal 2의 a/b 순서는 뒤집힌다.

6. 3-way partition: duplicate를 한 번에 제거

[lo, lt) [lt, i) [i, gt) [gt, hi) < p == p unknown > p A[i] < p : swap(A[lt],A[i]); lt++; i++ A[i] = p : i++ A[i] > p : gt--; swap(A[i],A[gt]) # 새 A[i]는 아직 unknown

종료 시 i==gt이고 unknown이 사라진다. [lt,gt) 전체가 equal이므로 재귀하지 않는다. distinct key에서는 추가 비교가 들 수 있지만, all-equal은 한 번의 linear partition으로 끝난다.

7. 시간·공간·expected·amortized 분석

경우recurrence결과
균형 partitionT(n)=2T(n/2)+Θ(n)Θ(n log n)
매번 0 : n−1T(n)=T(n−1)+Θ(n)Θ(n²)
uniform random pivot모든 rank 기대값 평균expected Θ(n log n), worst Θ(n²)
introspective fallbackdepth budget 소진 후 heapsortworst Θ(n log n)
  • 마지막 pivot + sorted/all-equal Lomuto 비교 수는 정확히 n(n−1)/2다.
  • naive recursion stack은 best/expected O(log n), worst O(n). 작은 partition만 재귀하고 큰 쪽은 loop로 처리하면 stack은 worst O(log n)이지만 작업량 Θ(n²)은 그대로다.
  • 배열 자체 partition은 O(1) auxiliary이고 cache-friendly지만, stack과 comparator/key 상태는 별도 비용이다.
  • expected ≠ amortized: random pivot의 Θ(n log n)은 난수에 대한 기대값이다. 연산 sequence의 총비용을 나누는 amortized 보장이 아니다.

8. 직접 구현: 3-way + 작은 쪽 우선

def quick3(a, lo, hi, key=lambda x: x): while hi - lo > 1: p = median3(key(a[lo]), key(a[(lo+hi-1)//2]), key(a[hi-1])) lt, i, gt = lo, lo, hi while i < gt: k = key(a[i]) if k < p: a[lt], a[i] = a[i], a[lt] lt += 1; i += 1 elif k > p: gt -= 1 a[i], a[gt] = a[gt], a[i] else: i += 1 # 작은 쪽만 재귀, 큰 쪽은 tail loop: stack O(log n) if lt - lo < hi - gt: quick3(a, lo, lt, key) lo = gt else: quick3(a, gt, hi, key) hi = lt

이 구현은 학습용이다. median-of-three와 3-way도 worst Θ(n²)을 제거하지 않는다. production 버전은 작은 구간 insertion cutoff, bad-partition/depth budget, heapsort fallback, key caching과 cancellation을 추가한다.

9. Introspective guardrail

budget = 2 * floor(log2(n)) while range is larger than cutoff: if budget == 0: heapsort(range) # worst Θ(m log m) return partition(range) if partition is highly unbalanced: budget -= 1 recurse smaller side; iterate larger side insertion_sort(tiny range)

핵심은 “좋은 pivot을 항상 맞힌다”가 아니라 계속 틀렸을 때 다른 알고리즘으로 종료한다는 것이다. Go의 현재 slices.Sort도 PDQsort 기반으로 bad pivot limit을 두고 heapsort로 fallback하며, 작은 범위는 insertion sort, duplicate는 equal partition으로 처리한다.

10. 테스트 전략

  1. Partition property: 반환 경계마다 왼쪽/같음/오른쪽 predicate를 즉시 검사한다.
  2. Sortedness + identity permutation: 중복·object identity까지 보존됐는지 reference sort와 비교한다.
  3. Progress: 모든 재귀 범위가 부모보다 작고 pivot/equal band가 제외되는지 assert한다.
  4. Exhaustive: n=0..8 모든 permutation을 Lomuto·random-pivot·3-way에 대조한다.
  5. Adversarial matrix: sorted, reverse, organ-pipe, sawtooth, all-equal, few-distinct, median-of-three killer.
  6. Resource oracle: max depth, pending stack, bad partitions, fallback count가 설정 상한을 넘지 않는지 확인한다.
  7. Comparator fault: k번째 비교 예외, NaN/비교불가, non-transitive comparator에서 API 실패 계약을 확인한다.
오늘 검증: Python 3.11.6에서 n=0..8 모든 permutation과 duplicate 입력을 세 구현으로 reference sort에 대조했다. sortedness·identity permutation을 통과했고, Lomuto 불안정 최소 반례도 실행으로 확인했다.

12. Memory와 locality

  • array partition은 연속 범위를 scan해 merge sort의 Θ(n) aux를 피하고 cache locality가 좋다.
  • “in-place O(1)”은 stack을 제외한 표현이다. naive worst stack O(n)은 메모리 안전성 문제다.
  • 작은 쪽 우선 재귀 + 큰 쪽 loop는 stack을 O(log n)으로 제한하지만 quadratic CPU는 heap fallback이 막아야 한다.
  • 큰 record는 swap마다 여러 cache line을 쓰므로 pointer/index를 정렬하고 마지막 permutation 비용을 따로 측정한다.
  • branch prediction은 분포와 partition scheme에 민감하다. comparison count가 같아도 wall time이 달라질 수 있다.

14. 실무 best practice

  • 검증된 표준 library sort를 우선하고 stable, worst bound, comparator 계약을 문서에서 확인한다.
  • duplicate cardinality를 알 수 없으면 equal band가 있는 partition을 검토한다.
  • 작은 partition은 insertion sort로 넘기되 cutoff는 record·comparator·CPU별 benchmark로 정한다.
  • bad partition/depth counter와 heap fallback을 둬 입력 패턴과 무관한 종료 상한을 만든다.
  • key가 비싸면 decorate-sort-undecorate로 한 번 계산하고 original index로 deterministic tie-break할 수 있다.
  • metrics에 max depth, bad partitions, fallback count, comparisons, swaps, duration/p99를 포함한다.

15. Anti-pattern

  • 항상 first/last pivot: sorted/reverse 입력이 바로 Θ(n²)과 깊이 n을 만든다.
  • random pivot이면 끝: all-equal을 2-way 편향으로 보내면 여전히 quadratic이다.
  • median-of-three를 보장으로 오해: organ-pipe/killer pattern은 heuristic을 반복 속인다.
  • equal에서 scan 정지 규칙 누락: OOB, 무한 loop, duplicate quadratic으로 이어진다.
  • 큰 쪽부터 재귀: 불필요하게 pending stack을 키운다.
  • sortedness만 테스트: 원소 소실·복제와 unstable 회귀를 놓친다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. Quicksort가 평균 빠르면서 최악 Θ(n²)인 이유는?
partition은 매번 Θ(n)이지만 pivot rank에 따라 recursion tree 높이가 log n 또는 n이 된다. 균형이면 층당 n × log n, 극단이면 n+(n−1)+…+1이다.
Q2. random pivot으로 충분하지 않은 사례는?
2-way Lomuto의 all-equal 입력은 어떤 위치를 뽑아도 한쪽 크기가 n−1이다. randomization은 위치 패턴만 끊고 equality policy는 고치지 않는다. 3-way equal band가 필요하다.
Q3. production quicksort를 어떻게 방어하나요?
sample/random pivot, 3-way duplicate 처리, insertion cutoff, 작은 쪽 우선 재귀, bad-partition/depth budget과 heapsort fallback을 묶는다. strict weak comparator와 partial-mutation 계약, depth/fallback metrics도 둔다.
