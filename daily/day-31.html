한 줄 요약
Bloom filter는 m-bit 배열과 k개 hash로 집합을 압축해 “확실히 없음” 또는 “있을 수도 있음”을 답하며, false positive는 허용하지만 같은 key 표현·hash·bit가 보존되는 한 false negative는 없어야 하는 read 최적화 장치다.

2. 문제·입출력·제약 mental model

문제: 20개의 SSTable이 point get의 key-range 후보라고 하자. key가 실제로 없으면 정확한 index/data 조회만으로 최대 20번의 storage 접근이 발생한다. 각 SST의 key 집합을 작은 memory filter로 요약하면 대부분의 “없음”을 CPU·RAM만으로 판정할 수 있다.

출력 계약은 3값처럼 읽는다. bit 하나라도 0이면 DEFINITELY_ABSENT. 모두 1이면 MAYBE_PRESENT이므로 정확한 원본 조회가 필수다. Bloom filter 자체는 PRESENT를 증명하지 않는다.

3. Architecture 그림: LSM point-read decision flow

① Get(key)canonicalize → snapshot/sequence → memtable 확인
↓ 각 candidate SST의 key range 확인
② Bloom probe같은 hash/version/seed로 k개 bit 읽기
↙ bit 0 하나: skip SST　　모두 1: MAYBE
③ Exact pathindex → data block → key comparator → checksum
↓ newest visible value/tombstone 또는 다음 SST
④ Result정확한 value / NOT_FOUND / corruption·I/O error

negative는 비싼 branch를 제거한다. positive는 “hit”가 아니라 exact path로 들어갈 허가다. 이 구분을 API 이름·metric·로그에 유지해야 FP를 cache hit처럼 잘못 해석하지 않는다.

4. Bloom Filter ADT와 representation invariant

  • create(capacity, targetFpr, hashVersion): m과 정수 k를 overflow 없이 계산하고 0으로 초기화한다.
  • add(x): canonical bytes의 k개 위치를 1로 만든다. 이미 1이어도 idempotent다.
  • mightContain(x): k개 중 하나라도 0이면 false, 모두 1이면 true다.
  • serialize/load: m·k·seed/hash/canonicalizer version·payload checksum을 함께 보존한다.
  • 표준 Bloom에는 remove가 없다. 삭제가 필요하면 immutable set 재구축 또는 counter·다른 filter를 선택한다.

Representation invariant(RI)

  1. m>0, 1≤k≤safeLimit, bit storage는 최소 m bit이며 padding은 질의 대상이 아니다.
  2. 각 inserted canonical key x에 대해 모든 position_i(x) bit가 1이다.
  3. build와 query의 canonicalizer, hash version, seed, m, k가 정확히 같다.
  4. filter가 live인 동안 bit는 0→1만 가능하다. 임의의 1→0은 금지한다.
  5. SST filter라면 filter generation/file identity와 immutable SST key set이 일치한다.
  6. serialized metadata와 bit payload는 length·version·checksum 검사를 통과해야 usable하다.

5. bit가 채워지는 확률부터 FPR까지

한 hash가 특정 bit를 건드리지 않을 확률은 1−1/m이다. n개 원소에 k번씩, 총 kn번 독립·균등하게 위치를 고른다고 근사하면:

P(bit=0) = (1−1/m)^(kn) ≈ e^(−kn/m)
q = P(bit=1) ≈ 1−e^(−kn/m)
FPR ≈ q^k = (1−e^(−kn/m))^k

k가 너무 작으면 bit를 적게 읽지만 공간을 충분히 활용하지 못한다. 너무 크면 한 key가 너무 많은 bit를 1로 만들어 saturation과 CPU/cache cost를 키운다. 미분하면 근사 FPR을 최소화하는 값은:

k* = (m/n)·ln 2　→　FPR ≈ (0.6185)^(m/n)　→　최적점의 density ≈ 1/2

k는 실제로 정수이므로 반올림 후보를 측정한다. hash의 독립·균등 가정, 작은 filter의 rounding, blocked layout, skew·공격 입력 때문에 공식은 보장이 아니라 capacity model이다.

7. 정당성: 왜 false negative가 없어야 하나

정리: x를 add했고 RI 2~4가 유지되면 mightContain(x)=true다.

  1. add(x)는 query(x)가 계산할 동일한 k개 위치를 모두 1로 만든다.
  2. 다른 원소의 add는 bit를 1로 만들 뿐 0으로 되돌리지 않는다.
  3. 따라서 query 시 x의 k개 bit는 모두 1이며 true를 반환한다.

False positive는 왜 가능한가? x를 넣지 않아도 다른 원소들이 우연히 x의 k개 위치를 모두 1로 만들 수 있다. 그래서 true는 membership 증명이 아니다.

최소 삭제 반례: a와 b가 공유하는 bit 3이 1이라고 하자. a를 삭제하며 bit 3을 0으로 지우면 아직 집합에 있는 b의 query가 0을 보고 false negative가 된다. counter를 쓰더라도 overflow/underflow, duplicate add/remove contract가 필요하다.

운영 반례: build는 Unicode NFC bytes, query는 원본 bytes를 hash하거나; comparator는 trailing space를 무시하지만 filter는 raw bytes를 쓰거나; SST 교체 후 옛 filter를 새 file에 연결하면 존재하는 key를 skip할 수 있다. 이는 확률 문제가 아니라 metadata/canonicalization 버그다.

8. 시간·공간·amortized complexity와 locality

Bloom filter에는 dynamic-array식 상각 업데이트가 본질적으로 필요하지 않다. 하지만 capacity를 넘겨도 구조는 동작한 채 FPR만 서서히 망가지는 quality debt가 생긴다. n이 변하는 mutable set이면 재구축 비용 Θ(nk)을 언제 지불할지 운영 정책이 필요하다.

표준 k random bit probe는 filter가 LLC보다 크면 cache miss가 많다. blocked/cache-line-local Bloom은 먼저 한 block을 고르고 그 안의 bit만 검사해 locality를 개선하지만, shard별 key 수 분산과 작은 block 때문에 FPR 모델이 달라진다. asymptotic O(k)가 같아도 CPU stall은 다르다.

9. 직접 구현: packed bitset + double hashing

class Bloom: def __init__(self, capacity, bits_per_key): self.m = checked_mul(capacity, bits_per_key) self.k = max(1, round(bits_per_key * log(2))) self.bits = bytearray((self.m + 7) // 8) def positions(self, key): h1, h2 = hash_pair(canonical_bytes(key)) h2 |= 1 for i in range(self.k): yield (h1 + i * h2) % self.m def add(self, key): for p in self.positions(key): self.bits[p >> 3] |= 1 << (p & 7) def might_contain(self, key): return all(self.bits[p >> 3] & (1 << (p & 7)) for p in self.positions(key))

코드 리뷰 포인트: 교육용 hash_pair를 production crypto로 오해하지 않는다. capacity*bits_per_key와 byte rounding을 checked arithmetic으로 계산하고, deterministic seed/version을 파일 metadata에 넣으며, 사용자 key와 internal sequence를 어느 수준에서 hash할지 명확히 한다.

10. 테스트 전략: “FPR이 낮다”보다 FN=0이 먼저

  1. RI test: m/k/length, padding, density bounds, add 후 모든 위치가 1인지 검사한다.
  2. No-FN test: 넣은 모든 key를 다시 질의한다. 한 건이라도 false면 즉시 실패한다.
  3. Oracle test: exact set과 함께 random add/query를 실행해 false negative는 0, false positive만 집계한다.
  4. Serialization test: round-trip 후 bit·metadata 동일, truncation/bit flip/version mismatch를 검출한다.
  5. Canonicalization test: comparator가 같다고 보는 모든 key 쌍이 같은 filter key가 되는지 property test한다.
  6. Capacity sweep: 0.5n, n, 2n 삽입에서 density와 FPR 증가를 이론과 비교한다.
  7. Adversarial test: 동일 prefix, patterned key, 반복 false-positive key, hash seed rotation을 시험한다.

통계 주의: q개 absent query에서 관측 FPR p̂의 표준오차는 대략 sqrt(p̂(1−p̂)/q)다. 0.1% 목표를 1,000번 질의해 1건 봤다고 튜닝하지 말고 충분한 sample과 신뢰구간을 쓴다.

12. Benchmark 함정과 올바른 비교

  • filter만 microbenchmark하지 말고 end-to-end get p50/p99, physical reads, cache churn, CPU를 함께 측정한다.
  • hit/miss 비율, candidate SST 수, cache warm/cold, point/prefix/range를 분리한다.
  • 같은 총 memory에서 filter와 block cache가 경쟁한다. filter를 늘려 data cache를 줄인 결과까지 포함한다.
  • bulk-load 직후가 아니라 compaction으로 file size·level 분포가 안정된 steady state를 본다.
  • negative query가 inserted set과 겹치지 않는지 exact oracle로 확인한다.
  • 평균 FPR만 보지 말고 file별 n·density·FPR 분포와 반복되는 hot false-positive key를 본다.

특히 “filter corruption을 NOT_FOUND로 처리”하면 빠르게 틀린 결과를 낸다. fail-open은 성능을 잃지만 정확성은 보존한다. exact SST 자체가 손상됐으면 NOT_FOUND로 숨기지 말고 명시적 corruption/I/O error와 복구 경로를 사용한다.

14. 실무 Best Practice와 관측성

  1. 목표는 “FPR 최소”가 아니라 filter memory + CPU + avoided I/O + block-cache 효과의 총비용 최소다.
  2. SST 예상 n과 memory budget으로 bits/key를 정하고 실제 density/FPR로 검증한다.
  3. comparator/canonicalizer/prefix extractor와 filter key 변환을 하나의 versioned 계약으로 묶는다.
  4. immutable SST와 함께 build·checksum·atomic publish하고 compaction output에는 새 filter를 만든다.
  5. missing/corrupt/incompatible filter는 fail-open하고 background rebuild 또는 다음 compaction에서 교체한다.
  6. large filter는 partition/cache 정책을 쓰고 metadata와 data cache를 포함한 전체 memory를 제한한다.
  7. whole-key Bloom은 point get, prefix Bloom은 계약에 맞는 seek에서만 쓴다. 임의 range의 존재를 증명하지 않는다.
  8. seed/hash는 성능·호환성·공격 모델을 고려해 versioning하고 migration 중 old/new reader 호환을 시험한다.

필수 지표: filter checked, useful negatives, positive, true positive, observed FPR, bit density, bytes/key, cache hit/miss/eviction, exact reads avoided/issued, filter decode/checksum error, bypass reason, query별 candidate SST 수.

RocksDB식 point lookup 관측에서는 (positive−truePositive)/(positive−truePositive+trueNegative)로 absent-query FPR을 계산한다. positive/checked만 나누면 실제 key hit가 섞여 오해할 수 있다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. Bloom filter의 FPR과 최적 k를 유도해 보세요.
m bits, n keys, k hashes에서 한 bit가 0일 확률을 (1−1/m)^(kn)≈e^(−kn/m)로 잡는다. 따라서 FPR은 (1−e^(−kn/m))^k, 이를 최소화하면 k=(m/n)ln2이고 최적 density는 약 1/2다. 독립·균등 hash 근사와 정수 rounding을 함께 말한다.
Q2. Bloom filter는 왜 false negative가 없고 삭제는 왜 어려운가요?
insert가 query할 모든 bit를 1로 만들고 bit를 지우지 않으면 membership key의 bit는 항상 1이다. 하지만 여러 key가 bit를 공유하므로 한 key 삭제 시 bit를 0으로 만들면 다른 key에 FN이 생긴다. immutable rebuild 또는 counter의 정확한 add/remove 계약이 필요하다.
Q3. LSM에서 10 bits/key를 켜면 끝인가요?
아니다. workload의 point miss·SST 후보 수·I/O 비용과 전체 memory를 확인하고 whole/prefix semantics, comparator 호환, filter cache, observed FPR/useful negatives를 측정한다. corruption/version mismatch는 fail-open하며 range scan에는 효과가 제한적이다.

오늘 filter가 불필요한 read를 줄였다면, 내일은 여러 SST를 merge할 때 실제로 몇 byte를 읽고 쓰는지, leveled/tiered 정책이 read·write·space amplification과 tail latency를 어떻게 바꾸는지 계산하고 장애 실험으로 연결한다.
