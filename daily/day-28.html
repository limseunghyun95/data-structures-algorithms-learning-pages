아키텍처의 핵심 경계는 논리 계약과 물리 표현이다. 호출자는 predecessor와 range를 요구할 뿐 RB 색이나 array index를 알아서는 안 된다. 그래야 workload가 바뀔 때 표현만 교체할 수 있다.

4. Ordered Map ADT와 계약

  • get(k), put(k,v), remove(k): missing·duplicate 결과를 typed value로 반환한다.
  • lower(k), floor(k), ceiling(k), higher(k): 경계 포함 여부를 이름과 테스트로 고정한다.
  • range(loInclusive, hiExclusive): 정렬된 snapshot인지 live view인지, iteration 중 mutation을 허용하는지 정의한다.
  • first/last: empty를 null, optional, exception 중 무엇으로 표현하는지 정한다.
  • key equivalence는 comparator가 0을 반환하는 관계다. 언어의 equals/hash와 다르면 같은 논리 key가 둘로 보이거나 덮어써질 수 있다.

추상 불변식: 각 논리 key는 최대 한 mapping을 가지며, iteration은 comparator 순서이고, 모든 navigation 결과는 정의한 strict/non-strict 경계를 만족한다.

L은 key 길이, P는 prefix 길이, k는 반환 항목 수다. AVL/RB의 O(log n)은 worst-case이고, hash의 O(1)은 보통 분포 가정 아래 expected/amortized다. API SLO가 p99라면 이 차이는 장식이 아니다.

7. Correctness: range가 정확한 이유

BST node x가 허용하는 전역 interval을 (low,high)라 하자. range(x,lo,hi)는 다음처럼 pruning한다.

range(x, lo, hi):
  if x == null: return
  if lo < x.key: range(x.left, lo, hi)
  if lo <= x.key and x.key < hi: emit(x)
  if x.key < hi: range(x.right, lo, hi)
  • Soundness: emit 조건이 직접 lo≤key<hi이므로 범위 밖 항목은 나오지 않는다.
  • Completeness: x.key≤lo면 왼쪽 모든 key는 더 작아 답이 될 수 없고, x.key≥hi면 오른쪽 모두 답이 아니다. 잘라낸 subtree에 정답이 없으므로 모든 정답은 방문된다.
  • Order: left→node→right 순회와 BST RI 때문에 출력은 comparator 오름차순이다.
  • 비용: 경계로 내려가는 O(h)와 실제 출력 k를 합쳐 균형 트리에서 O(log n+k).

8. 최소 반례로 잘못된 선택 깨기

Heap을 정렬 인덱스로 착각
min-heap [1,5,2,9,7,8,6]은 RI를 만족하지만 array 순서는 정렬이 아니다. 2의 successor가 index 이웃이라는 보장도, [5,8) 항목이 연속이라는 보장도 없다.
Comparator 추이성 위반
A<B, B<C인데 C<A가 되면 한 insert path와 search path가 서로 다른 subtree를 선택한다. rotation은 inorder를 보존해도 잘못 정의된 “order”를 고칠 수 없다.
문자열 순서와 숫자 순서 혼동
trie의 code-point lexicographic order에서는 “10”이 “2”보다 먼저 올 수 있다. 숫자 범위가 필요하면 parse된 숫자 comparator 또는 order-preserving encoding이 필요하다.

9. 직접 구현: 계약을 oracle로 검증하기

구현체보다 단순한 reference model을 둔다. 테스트에서는 production 구현과 작은 sorted vector oracle에 같은 operation trace를 적용한다.

for op in generated_trace:
  expected = sorted_vector.apply(op)
  actual   = candidate.apply(op)
  assert actual == expected
  assert candidate.size == oracle.size
  assert candidate.keys() is strictly ordered
  assert navigation_boundaries(candidate)
  assert representation_invariant(candidate)

필수 trace: empty, one node, ascending/descending insert, duplicate replace/reject, root·leaf·two-child delete, absent remove, min/max key, equal comparator, mutation 중 iterator, allocation failure. 매 seed와 최소화된 counterexample을 저장한다.

Augmentation 주의: rank/select를 위해 subtree size를 붙이면 모든 rotation·delete에서 size=1+left.size+right.size도 RI가 된다. core tree만 검증하고 metadata를 빼먹으면 논리적으로 틀린 rank가 조용히 나온다.

11. Benchmark를 설계하는 법

  1. production trace에서 n, key length, hit/miss, read/write/range 비율, skew와 burst를 추출한다.
  2. build·steady-state·churn·recovery를 분리한다. setup과 allocator warm-up을 query time에 섞지 않는다.
  3. 모든 후보가 동일한 key/value ownership, comparator, duplicate semantics를 갖게 한다.
  4. wall time 외에 comparisons, allocations, bytes/entry, cache miss, rotations/splits, lock wait, p50/p95/p99를 본다.
  5. 결과를 사용해 dead-code elimination을 막고, seed·compiler·flags·CPU pinning·sample count를 기록한다.
  6. 평균만 비교하지 말고 rehash, compaction, page split, GC가 포함된 tail과 memory peak를 보고한다.

Benchmark anti-pattern: sorted input 하나, 1000개뿐인 microbenchmark, 서로 다른 allocator, hash는 warm cache인데 tree는 cold cache, 출력 k가 다른 range, sanitizer build의 성능 수치, 한 번 실행의 최솟값.

13. Memory와 locality를 계산하기

node tree가 key 16B, value 8B, left/right/parent 24B, color·padding 8B라면 대략 56B/entry이고 allocator metadata와 fragmentation은 별도다. sorted array의 같은 payload가 24B/entry라면 1천만 건에서 이론상 차이만 약 320MB다.

  • pointer tree search는 log n개의 불연속 node를 따라가며 cache/TLB miss가 날 수 있다.
  • sorted array binary search도 멀리 점프하지만 node가 조밀하고 range scan은 연속이다.
  • B-tree는 한 node/page에 여러 key를 넣어 fan-out을 키우고 pointer chasing·page read 수를 줄인다.
  • intrusive RB tree는 node와 payload의 간접 참조 한 층을 줄일 수 있지만 lifetime·API coupling을 감수한다.

메모리 예산은 payload만 세지 않는다. capacity slack, allocator header, parent/metadata, duplicate version, tombstone, snapshot, rebuild 중 old+new 동시 보유까지 peak RSS로 계산한다.

14. Concurrency·persistence trade-off

  • Thread-safe ≠ compound atomic: get과 put이 각각 안전해도 check-then-act는 원자적이지 않다. putIfAbsent, transaction, lock 범위를 계약한다.
  • Iterator: fail-fast는 동시성 correctness 보장이 아니다. weakly consistent, snapshot, locked iterator 중 하나를 명시한다.
  • Fine-grained tree lock: rotation이 여러 node를 바꾸므로 lock order·version·reclamation이 어렵다. 검증된 concurrent skip list/map을 우선한다.
  • Persistence: in-memory RI만으로 crash consistency가 생기지 않는다. WAL → page update → durable commit 순서와 torn write·replay를 설계한다.
  • Online rebuild: dual-write 또는 versioned snapshot에서 cutover 선형화 지점, catch-up, rollback, memory peak를 정의한다.

16. 실무 Best Practice와 Anti-pattern

  1. ADT와 SLO를 먼저 쓰고 표준 라이브러리의 검증된 구현을 기본값으로 둔다.
  2. comparator/equality/hash/canonicalization을 한 모듈에서 versioning하고 property test한다.
  3. RI validator와 작은 oracle differential test를 debug·fuzz·migration 검증에 쓴다.
  4. 실제 operation mix로 시간·bytes/entry·p99·peak memory를 함께 benchmark한다.
  5. 복합 인덱스(heap+id map, tree+augmentation)는 원자적 갱신과 교차 RI를 선언한다.
  6. capacity, timeout, cancel, snapshot, iterator, shutdown을 정상 API 경로로 설계한다.
  7. 지표가 임계값을 넘을 때 rebuild/reindex/구조 전환하는 runbook과 rollback을 준비한다.

Anti-pattern: “hash가 O(1)이니 항상 빠름”, “균형 트리면 cache도 좋음”, “heap array는 거의 정렬됨”, “trie는 key 수와 무관하니 무조건 O(1)”, custom concurrent tree부터 구현, benchmark 한 수치로 영구 결정.

17. 대기업 면접 질문 3개와 답변 포인트

Q1. ordered map 구현으로 RB tree와 sorted array 중 무엇을 고르겠습니까?
먼저 read/write/range 비율, n, worst-case, memory와 concurrency를 묻는다. static/read-mostly면 array의 O(log n) lookup·O(log n+k) range·locality를, dynamic이면 RB의 worst-case O(log n) update를 선택한다. 실제 p99·bytes/entry와 migration 조건까지 제시한다.
Q2. min-heap으로 range query도 처리할 수 있지 않나요?
heap RI는 parent≤children뿐이라 sibling/subtree 간 전체 순서가 없다. root minimum은 O(1)이지만 arbitrary search/range는 O(n)이다. range가 핵심이면 ordered tree/B-tree, exact만이면 hash를 고려하고 heap은 priority queue 계약에 제한한다.
Q3. O(log n) 트리가 O(log n) binary search보다 느린 이유와 개선법은?
pointer chasing, allocator fragmentation, branch prediction, cache/TLB miss, 큰 node를 말한다. compact node/B-tree·arena·intrusive layout, batched lookup, cached extreme을 후보로 두되 write cost와 complexity를 실제 workload로 검증한다.
