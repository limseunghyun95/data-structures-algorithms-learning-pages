한 줄 요약
hash table resize는 한 번에 Θ(n)이지만 용량을 기하급수적으로 키우고 grow·shrink 사이에 hysteresis를 두면 연산열의 상각 비용은 O(1)이다. 단, 상각 O(1)은 단일 요청의 지연·OOM·peak memory·iterator 안전성을 보장하지 않는다.

4. Map ADT와 resizing representation invariant

ADT: 외부에서는 여전히 유한 부분함수 M: K ⇀ V다. capacity·rehash·old/new table은 표현일 뿐, resize 전후 모든 key의 get 결과와 size가 같아야 한다.

  1. RI-1 capacity: 구현이 요구하는 최소값·power-of-two/prime 조건을 만족하고 0≤size≤max_live(capacity)다.
  2. RI-2 uniqueness: 같은 equality key는 authoritative storage 전체에 정확히 하나다.
  3. RI-3 reachability: 모든 live key는 현재 capacity의 hash/probe 규칙으로 찾을 수 있다. old slot을 같은 index로 memcpy하는 것은 일반적으로 충분하지 않다.
  4. RI-4 count: live/tombstone counter와 control state의 실제 개수가 일치한다.
  5. RI-5 commit: monolithic resize 동안 old가 authoritative이고, new가 완성된 뒤 한 번의 publish로 바뀐다.
  6. RI-6 incremental ownership: migration cursor 이전의 old bucket은 new가, 이후 bucket은 old가 authoritative다. put/get/delete는 key의 old-home ownership을 따라 같은 table로 간다.
  7. RI-7 reclaim: 어떤 reader·iterator도 old를 참조하지 않을 때만 old storage를 해제한다.

주의: RI-6의 bucket 단위 migration은 chaining·segmented 설계에서 설명하기 쉽다. flat open addressing은 한 slot 이동이 다른 key의 probe 증명을 깨뜨릴 수 있어 table 전체, 독립 group/table, 또는 엄밀한 dual-table protocol 단위로 옮겨야 한다.

5. 왜 add-1 growth는 Θ(n²)이고 doubling은 Θ(n)인가

capacity가 찰 때마다 1칸만 늘리면 migration 비용은 1+2+…+(n-1)=n(n-1)/2=Θ(n²)다. n번 insert의 평균도 Θ(n)이 된다.

doubling이면 rebuild 시점의 크기가 1,2,4,…,2ᵏ다. n≤2ᵏ⁺¹일 때 이동 총합은 1+2+4+…+2ᵏ=2ᵏ⁺¹−1<2n. 각 insert 자체 O(1)을 더해도 n개 insert 전체 expected Θ(n), 한 insert의 amortized expected O(1)이다.

면접에서 꼭 분리: hash collision 때문에 기본 put이 expected O(1)이라는 가정과, resize 비용이 amortized O(1)이라는 보장은 서로 다른 분석 축이다. adversarial collision이면 resize를 잘해도 lookup/put worst-case O(n)이 남는다.

6. Aggregate·Accounting·Potential 세 증명

Aggregate

위 geometric sum으로 n개 insert의 base work n과 migration work <2n을 합쳐 <3n으로 묶는다. 모든 연산열에 대한 총비용 상한이므로 확률적 average와 다르다.

Accounting

grow 직후 다음 grow까지 최소 Θ(m)개의 새 insert가 들어온다. 각 insert에 실제 비용 1 외에 일정 credit를 붙여 entry migration 통장에 적립하면 다음 Θ(m) rebuild를 지불하고도 credit가 음수가 되지 않는다. 성장률 γ가 1에 가까울수록 grow 간격이 짧아져 필요한 상수 credit는 커진다.

Potential

classic full-doubling table에서 Φ(T)=2n−m를 쓴다(α≥1/2 구간). 일반 insert는 actual 1, ΔΦ=2라 상각 비용 3이다. full table을 2m으로 grow하며 insert할 때 actual은 기존 m개 이동+1이지만 capacity 증가로 potential이 크게 떨어져 이 비용을 상쇄한다. shrink까지 포함하면 α≥1/2와 α<1/2에 piecewise potential을 사용해 grow·shrink 모두 O(1) amortized를 보인다.

γ trade-off: 큰 γ는 rebuild 빈도와 amortized 상수를 줄이지만 slack memory와 peak allocation을 늘린다. 작은 γ는 memory를 촘촘히 쓰지만 migration·allocator 호출이 잦다. γ는 알고리즘 상수이자 운영 파라미터다.

7. Shrink hysteresis와 최소 thrashing 반례

grow와 shrink를 같은 α=0.5에서 실행한다고 하자. n=m/2인 table에 insert 하나를 하면 grow, 곧바로 delete 하나를 하면 shrink한다. 이 두 연산을 반복하면 매번 Θ(n) migration이 발생해 상각 O(1)이 깨진다.

해결: 예를 들어 α>0.75에서 grow, α<0.20에서 shrink-to-half한다. grow 직후 다시 shrink하려면 충분한 delete가, shrink 직후 다시 grow하려면 충분한 insert가 필요하다. 여기에 최소 capacity, cooldown, sustained-low watermark를 더하면 burst 직후의 메모리 진동을 막는다.

8. 직접 구현: failure-atomic monolithic resize

ResizeResult resize(Map *t, size_t requested) {
  size_t new_cap, bytes;
  if (!normalize_capacity(requested, &new_cap) ||
      !checked_mul(new_cap, sizeof(Slot), &bytes))
    return CAPACITY_OVERFLOW;

  Slot *next = alloc_zeroed(bytes);
  if (next == NULL) return OUT_OF_MEMORY;   // old는 그대로

  for (size_t i = 0; i < t->capacity; ++i) {
    if (t->slots[i].state != FULL) continue;
    if (!insert_no_grow(next, new_cap,
                        t->slots[i].key, t->slots[i].value)) {
      destroy_constructed(next, new_cap);
      free(next);
      return MIGRATION_FAILED;              // rollback 불필요
    }
  }

  Slot *old = t->slots;                     // commit point
  t->slots = next;
  t->capacity = new_cap;
  t->deleted = 0;
  free_after_readers_quiesce(old);
  return RESIZED;
}

순서가 계약이다: old payload를 먼저 move-from 또는 destroy하면 중간 실패 시 복구할 수 없다. copy가 불가능하고 move가 실패할 수 있는 타입이라면 node indirection, noexcept move 제약, transaction log 등 표현 자체를 바꿔야 한다.

9. Incremental migration state machine

NORMAL한 table, threshold 초과 시 new 할당
↓ old/new/cursor=0 publish
MIGRATINGoperation마다 ≤B bucket 이동; key의 old-home이 cursor보다 작은지로 authoritative table 결정
↓ cursor==old.bucket_count, active reader 0
COMMIT/RECLAIMnew을 root로 확정하고 old 해제
  • 장점: 한 요청이 지불하는 migration work를 B로 제한해 pause를 낮춘다.
  • 대가: 두 table, routing branch, cursor, 동시성, iteration, crash/retry 상태가 복잡해진다.
  • 진행 보장: traffic이 없으면 migration이 영원히 끝나지 않을 수 있어 background worker 또는 maintenance tick이 필요하다.
  • overload: 새 insert 속도가 migration 속도보다 빠르면 new도 차오른다. migration debt와 completion ETA를 관측하고 admission control을 둔다.

현재 Go runtime map 구현은 큰 map의 incremental growth를 위해 hash space를 여러 table로 나누고 개별 table grow/split 크기를 제한한다. 이는 “flat table slot 몇 개만 무작정 옮기기”보다 invariant 경계를 작게 만드는 production 설계 사례다.

12. 테스트 전략

  1. capacity 2/4/8 경계의 직전·직후 insert에서 모든 key와 size가 유지되는지 검사한다.
  2. 같은 key update는 size 증가나 불필요한 grow를 만들지 않는지 본다.
  3. allocation을 모든 가능한 지점에서 강제 실패시키고 old snapshot·counter·iterator 계약이 보존되는지 확인한다.
  4. capacity*sizeof(Slot), ceil(expected/αmax), doubling의 overflow를 checked arithmetic로 검사한다.
  5. grow/shrink threshold 주변 operation sequence를 model-check해 resize 횟수가 연산 수에 선형 이하인지 본다.
  6. incremental이면 migration step마다 ownership·uniqueness·lookup equivalence를 reference map과 differential test한다.
  7. 동시성 구현은 publish/reclaim 사이 reader interleaving, cancellation, shutdown, background worker 정지를 검증한다.

이번 검증: C11 구현은 매 run 뒤 count·load·reachability RI를 검사했다. Apple clang 21.0.0 -Wall -Wextra -Werror와 ASan/UBSan에서 dynamic 16회 grow 및 presized 경로를 각각 5회 통과했다.

14. 실무 best practice와 anti-pattern

  • Best: 예상 mapping 수를 안다면 API의 reserve/with_capacity/initial-capacity를 쓴다. Rust는 overflow·allocator 실패를 반환하는 try_reserve도 제공한다.
  • Best: grow, tombstone cleanup, shrink를 별도 trigger와 metric으로 운영한다.
  • Best: resize count·duration·moved entries·peak bytes·migration debt·probe tail을 trace에 남긴다.
  • Best: latency-sensitive path는 shard별 작은 rebuild, bounded assist, 미리 reserve한 spare table을 검토한다.
  • Anti: 매 delete 후 shrink_to_fit. churn에서는 CPU·allocator·cache를 태운다.
  • Anti: 상각 O(1)을 p99 O(1)로 설명. 한 operation의 Θ(n)은 그대로다.
  • Anti: capacity를 entry 수와 동일시. threshold·bucket/group granularity 때문에 실제 allocation은 더 클 수 있다.
  • Anti: resize 중 old/new 양쪽에 같은 key를 무규칙하게 쓰고 lookup 순서로 덮는다. uniqueness와 최신값 계약이 깨진다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. hash map insert가 O(1)이라고 말해도 되나요?
hash 분포 가정 아래 expected lookup/insert와 geometric resize의 amortized O(1)을 분리한다. 단일 insert worst Θ(n), collision worst Θ(n), resize tail·OOM·memory는 별도라고 답한다. geometric sum 또는 potential 증명을 짧게 보인다.
Q2. delete가 많을 때 왜 바로 shrink하지 않나요?
동일 threshold는 insert/delete 두 번으로 Θ(n) thrashing을 만든다. grow/shrink hysteresis, cooldown, 최소 capacity, live/used α 분리, same-size cleanup과 shrink의 차이를 설명한다.
Q3. p99가 중요한 서비스에서 resize를 어떻게 설계하나요?
expected size reserve, sharding/segmentation, bounded incremental migration, request assist budget, peak memory·OOM fallback, iterator/reclamation 계약, resize event trace를 제시한다. 상각 보장은 tail SLO가 아니라고 먼저 선을 긋는다.
