한 줄 요약
인덱스 선택은 “B-tree냐 LSM이냐” 한 줄 답이 아니라 필요한 연산, key order, 읽기·쓰기 분포, 결과 cardinality, locality, durability, read/write/space amplification, 운영 SLO를 먼저 고정하고 구조의 불변식과 실패 비용으로 선택을 반증하는 과정이다.

1. 초보자를 위한 용어 사전

Index원본 데이터를 더 적게 읽도록 key→위치/값을 조직한 보조 구조. 조회 이득 대신 write·공간·복구 비용을 낸다.
Access methodB-tree, hash, inverted/GIN, BRIN처럼 index의 연산과 물리 표현을 정의하는 방식.
Primary indexrow의 주된 배치/식별과 강하게 연결된 index. DB마다 clustered 의미가 다르므로 제품 계약을 확인한다.
Secondary index주 저장 순서와 다른 key의 보조 index. entry에서 row/primary key로 한 번 더 찾아갈 수 있다.
Clustered비슷한 index key의 row가 물리적으로 가까운 정도. range locality를 높이지만 보통 한 순서만 선택한다.
Selectivity조건을 통과하는 비율. 낮을수록 좁지만 ORDER BY·covering·locality까지 합쳐야 실제 cost가 된다.
Composite index여러 열을 하나의 ordered tuple key로 만든 index. 열 순서가 탐색 interval을 결정한다.
Covering index검색과 출력에 필요한 열을 담아 원본 row fetch를 줄이는 index. leaf 폭과 write 비용은 증가한다.
Cardinality estimateoptimizer가 예측한 결과 행 수. 통계·상관관계 오차가 access path를 뒤집는다.
B+tree높은 fan-out의 page-balanced ordered tree. point·range·order·prefix에 균형 잡힌 선택이다.
LSM treewrite를 WAL+memtable에 모아 immutable sorted run으로 flush·compact하는 구조.
Hash indexequality lookup에 맞춘 bucket 구조. key order가 없어 range·ORDER BY에는 직접 답하지 못한다.
Bloom filter“확실히 없음/있을 수도 있음”을 답하는 보조 확률 구조. index를 대체하지 않고 불필요한 run I/O를 줄인다.
RA/WA/SA사용자 작업 1단위에 대한 read/write/space amplification. 서로 동시에 최소화하기 어렵다.
Write stallflush/compaction debt가 커져 write를 지연·중단하는 상태. 평균 write가 빨라도 tail SLO를 깨뜨릴 수 있다.

3. Architecture/decision flow

① Contractequality/range/order/prefix/unique/snapshot/durability 정의
↓ hard requirement로 불가능한 후보 제거
② Cost빈도×p50/p99×RA/WA/SA×memory×운영 비용 계산
↓ composite/covering/Bloom/compaction 구체화
③ Proveordering·visibility·latest-version·uniqueness RI와 반례 확인
↓ representative data + adversarial skew + failure test
④ Measureactual rows, buffers, cache, bytes, compaction debt, stall, recovery time
↓ canary·rollback·continuous review
⑤ Operatestats refresh, bloat/WA, disk headroom, rebuild, ownership 관리

선택은 층별이다. SQL query의 secondary B-tree와 storage engine의 LSM은 서로 배타적이지 않다. LSM 기반 engine 위에 composite secondary index가 있을 수 있고, 각 SST에 Bloom이 붙을 수 있다. “하나의 최강 index”가 아니라 각 층이 어떤 amplification을 줄이고 어디에 새 비용을 만드는지 설명한다.

4. Ordered Index ADT와 공통 representation invariant

ADT: insert/delete, find(key), lowerBound(key), scan(lo,hi), 선택적으로 findAt(snapshot), uniqueInsert. 구현은 B+tree page일 수도, 여러 SST의 merge view일 수도 있다.

  1. 모든 writer와 reader가 같은 total comparator, collation, NULL, encoding 계약을 쓴다.
  2. logical live row마다 필요한 index entry가 있으며 삭제/이전 version의 visibility가 engine 계약과 일치한다.
  3. ordered scan은 comparator 순서와 정확한 inclusive/exclusive boundary를 보존한다.
  4. duplicate key가 허용되면 row identity/sequence가 stable tie-breaker가 된다.
  5. UNIQUE는 허용된 NULL semantics와 snapshot/transaction 범위에서 live duplicate가 없다.
  6. covering payload는 search key와 구분되고 원본 row version과 일관된다.
  7. crash 뒤 durable metadata가 참조하는 node/file은 완전하며 checksum·page invariant를 만족한다.

B+tree 추가 RI: page occupancy 범위, separator가 child range를 정확히 나눔, 모든 leaf depth 동일, leaf chain 정렬.
LSM 추가 RI: sequence 최신 우선, tombstone이 old value를 가림, 각 run 정렬·immutable, level overlap 규칙, manifest가 live file set을 원자적으로 정의.

5. 정당성: 연산 계약으로 후보를 제거한다

명제: comparator 순서의 range [L,U)를 출력해야 한다면 순서를 보존하지 않는 순수 hash index 하나로는 결과를 key order로 직접 생성할 수 없다. Hash bucket은 key order 정보를 보존하지 않으므로 모든 후보를 수집해 정렬하거나 별도 ordered structure가 필요하다. 따라서 range/order가 hard requirement면 hash-only 후보를 제거한다.

Composite B-tree: (a,b,c)의 사전식 순서에서 선행 equality a=A,b=B가 고정되면 c range는 하나의 연속 interval이다. 중간 b가 빠지면 c 값은 b group마다 흩어져 하나의 좁은 interval이 아니다.

LSM Get: snapshot 이하 최대 sequence의 version을 선택하면 된다. memtable과 overlapping run을 newest-to-oldest로 검사하고 Bloom negative만 건너뛰며 tombstone도 version으로 처리하면 old value 부활을 막는다.

최소 반례 모음
① range query에 hash-only: 2와 100이 어느 bucket 순서인지 알 수 없어 ordered result를 직접 못 만든다.
② “가장 selective 열 먼저”: (created_at,tenant)는 tenant별 최근 50건에서 넓은 시간대를 훑을 수 있다.
③ Bloom positive=존재: false positive 하나가 NOT_FOUND여야 할 key를 존재로 오답 처리한다.
④ tombstone 조기 GC: lower run의 old value가 다시 보인다.
⑤ covering 과다: leaf entry가 커져 fan-out·cache hit가 낮아지고 write가 더 비싸진다.

6. 구조별 cost model

구조강점주 비용/실패대표 선택

LSMsequential batched write, high ingestRA/WA/SA, compaction, stallwrite-heavy KV/time series/storage engine

Inverted/GINtoken/array/JSON containmentposting list·update·merge 비용full text, tags, multi-valued field

같은 Big-O도 다르다. B+tree의 log는 page fan-out 기반이고 상단 page가 cache되면 물리 I/O는 적다. LSM point read는 run 후보 수·Bloom·block cache에 좌우된다. Hash O(1)은 adversarial collision, resize pause, locality가 빠진 expected cost다. 공간은 entry bytes뿐 아니라 allocator, page slack, Bloom/index block, old version, compaction 임시 output을 포함한다.

7. B+tree vs LSM: 질문별 방어

축B+tree 경향LSM 경향
foreground writetarget page update/splitWAL+memtable, 순차 flush
point read한 root-to-leaf pathmemtable+run, Bloom/cache로 prune
range scanleaf chain sequential여러 run k-way merge·version skip
background workvacuum/rebalance/checkpoint 제품 의존flush/compaction가 지속 throughput 결정
space peakpage slack·MVCC/bloatold run+new output 동시 존재
tail risksplit/latch/random I/Ocompaction debt/write stall

“write-heavy라 LSM”도 충분하지 않다. ingest가 200MB/s인데 실제 compaction throughput이 WA를 포함해 150MB/s라면 backlog는 무한히 증가한다. 반대로 read-heavy라도 working set이 cache되고 Bloom negative가 많으면 LSM이 충분할 수 있다. sustained 처리율과 p99를 측정한다.

8. Composite·covering 설계 flow

  1. normalized query family와 빈도·총 DB time·tail SLO를 모은다.
  2. 항상 고정되는 equality columns로 선행 prefix 후보를 만든다.
  3. 첫 range와 ORDER BY/LIMIT을 같은 연속 interval/scan으로 만족시킨다.
  4. duplicate·NULL·collation·DESC를 포함한 comparator와 uniqueness 범위를 명시한다.
  5. 출력 열은 INCLUDE/covering 후보지만 width·update 빈도·visibility check를 계산한다.
  6. 다른 query family의 leading-column gap, 별도 index, bitmap/skip scan, seq scan 비용을 합산한다.
  7. estimated/actual rows, buffers, sort, heap fetch, write WAL, index bytes를 before/after 비교한다.

선택성만으로 정렬하지 않는다. tenant별 최근 50건은 (tenant_id, created_at DESC)가 tenant equality→time order→LIMIT early stop을 한 leaf walk로 묶는다. 전역 time 분석이 중요하면 (created_at, tenant_id) 또는 별도 index가 필요하다. 두 query를 하나의 지나치게 넓은 index로 덮으면 cache와 write 비용이 커진다.

9. 직접 구현: constraint-first decision record

def shortlist(workload): candidates = {"btree", "lsm", "hash"} if workload.range_ratio > 0 or workload.order_required: candidates.discard("hash") if workload.prefix_search: require_total_order_and_prefix_compatible_encoding() if workload.unique: require_atomic_conflict_check_under_concurrency() return candidates def decision_record(W, measurements): C = shortlist(W) return min(C, key=lambda c: W.point * measurements[c].point_p99 + W.scan * measurements[c].scan_p99 + W.write * measurements[c].write_p99 + penalty_if(measurements[c].wa > W.max_wa) + penalty_if(measurements[c].space_peak > W.disk_budget) + penalty_if(measurements[c].recovery > W.rto)) # 숫자는 vendor 기본값이 아니라 우리 dataset·hardware·concurrency의 실측값이어야 한다. # hard constraint 위반은 작은 가중치가 아니라 후보 제거 또는 무한 penalty다.

구현 포인트는 “점수표가 정답”이 아니라 decision record의 재현성이다. workload version, data distribution, engine version, configuration, hardware, cold/warm phase, concurrency, 결과 검증을 같이 저장한다. 가중치가 10% 바뀌어 선택이 뒤집히면 결론이 민감하므로 dual benchmark/canary가 필요하다.

13. Production Best Practice

  1. index마다 owner query family, 기대 SLO, 생성 이유, 측정 baseline, review/drop 기준을 기록한다.
  2. optimizer 통계와 실제 분포를 관리하고 correlated columns에는 extended/multivariate stats를 검토한다.
  3. covering은 hot stable query에 제한하고 leaf width, cache, update/WAL, MVCC heap fetch를 함께 본다.
  4. LSM은 RA/WA/SA와 L0 files, pending compaction bytes, stall seconds, disk peak를 함께 alert한다.
  5. Bloom bits/key는 negative lookup 비율·SST 수·memory budget·FPR 목표로 결정하고 false negative 0을 검증한다.
  6. hot key/tenant skew를 별도 dimension으로 계측해 평균 cardinality가 숨기는 partition·latch 병목을 찾는다.
  7. write throughput은 foreground 성공률뿐 아니라 compaction/vacuum이 따라잡는 steady state에서 평가한다.
  8. schema/format 변경은 backup·restore drill, checksum scan, rolling compatibility, rollback을 포함한다.

14. Anti-pattern

  • WHERE 열마다 single-column index: AND/ORDER BY를 하나의 interval로 못 묶고 maintenance만 늘 수 있다.
  • selectivity 높은 열 무조건 선두: equality prefix, range, LIMIT, ordering을 무시한다.
  • index가 있으면 빠름: 결과가 많고 heap locality가 나쁘면 seq scan이 더 싸다.
  • write-heavy=LSM: compaction 처리율·disk headroom·read SLO 없이 결정한다.
  • Bloom=cache 또는 존재 증명: payload를 저장하지 않으며 positive는 확정 답이 아니다.
  • 평균 latency만 비교: split·compaction·checkpoint가 만드는 p99와 timeout을 놓친다.
  • benchmark에 결과 검증 없음: 빠르게 틀린 query/손실된 write를 성공으로 측정한다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. B+tree와 LSM 중 무엇을 선택하나요?
point/range/order/write 비율, sustained ingest, p99, RA/WA/SA, memory/disk, recovery를 먼저 수치화한다. B+tree는 한 ordered page path와 range locality가 강하고 LSM은 foreground sequential write가 강하지만 compaction·run read 비용이 있다. Bloom/cache/compaction style을 포함한 실제 steady-state benchmark로 결정한다.
Q2. composite index 열 순서를 어떻게 정하나요?
query family의 equality prefix→첫 range/ORDER BY→LIMIT early stop→필요 payload 순으로 후보를 만든다. 전역 distinct 수만 보지 않는다. 다른 query family의 leading gap과 write/leaf width를 합산하고 EXPLAIN actual rows·buffers로 반증한다.
Q3. 인덱스를 추가했는데 더 느려질 수 있는 이유는?
모든 write가 추가 structure와 WAL을 유지하고 cache working set이 커지며 page split/compaction가 늘어난다. covering 과다로 fan-out이 낮아질 수 있고 stale stats가 나쁜 plan을 고를 수도 있다. read 이득과 write·space·tail·운영 비용을 before/after로 본다.
