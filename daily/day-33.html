한 줄 요약
Composite B-tree는 key tuple을 사전식(lexicographic) 순서로 정렬하므로, 선행 equality와 그 다음 range가 하나의 좁은 연속 구간을 만들 때 강력하고, 실제 선택은 selectivity뿐 아니라 정렬·covering·heap locality·통계 오차·write 비용까지 합친 cost로 방어해야 한다.

Correlation두 열이 독립이 아닌 관계. 예: country와 city. 독립 가정은 결과 수를 크게 틀릴 수 있다.
Cost-based optimizer통계로 각 plan의 I/O·CPU·정렬 비용을 추정해 가장 싼 plan을 선택하는 구성요소.

2. 문제·입출력·제약 mental model

SELECT id, amount FROM orders WHERE tenant_id = 321 AND created_at BETWEEN :from AND :to ORDER BY created_at DESC LIMIT 50;

300만 행 중 tenant 321의 최근 주문 50개를 찾는다고 하자. (tenant_id, created_at DESC)는 tenant 321의 구간으로 내려간 뒤 시간순으로 50개만 읽는다. 반대로 (created_at, tenant_id)는 넓은 시간 구간을 훑으며 tenant를 filter할 수 있다. 같은 두 열이어도 순서가 작업량을 바꾼다.

먼저 묻는 제약설계 결정
어떤 query shape가 몇 %인가?workload-weighted key order와 index 집합
각 equality/range의 실제 rows와 skew는?leading key, histogram, MCV, extended stats
ORDER BY/GROUP BY/LIMIT이 있는가?sort 제거, 방향, early stop 가능성
출력 열과 row width는?covering/INCLUDE의 이득과 leaf bloat
read/write 비율과 HOT/update 패턴은?index maintenance·WAL·cache·vacuum 비용

선택성 함정: “가장 distinct가 큰 열을 무조건 왼쪽”은 규칙이 아니다. equality로 tenant를 고정한 뒤 시간 range와 ORDER BY/LIMIT을 만족하는 것이 더 중요할 수 있다. 열 하나의 전역 selectivity가 아니라 전체 query가 만드는 연속 index interval과 필요한 row 수를 계산한다.

3. Architecture 그림: SQL에서 물리 plan까지

① Normalizepredicate·type·collation·ORDER BY·LIMIT 분석
↓ SARGable clause와 candidate access path 생성
② Estimatehistogram·MCV·NDV·correlation로 rows 추정
↓ seq/index/bitmap/index-only + join/sort cost 비교
③ ExecuteB-tree seek → leaf range scan → recheck → heap/visibility
↓ actual rows·buffers·time와 estimate 비교
④ FeedbackANALYZE/extended stats/index 변경 후 회귀 검증

Optimizer는 “index가 존재하면 사용”하지 않는다. 예상 결과가 많고 random heap fetch가 비싸면 sequential scan이 더 싸다. 잘못된 plan은 index 부족뿐 아니라 stale statistics, 열 상관관계, parameter 분포, collation·cast 불일치에서 나온다.

4. Ordered Composite Index ADT와 representation invariant

ADT: seekLowerBound(keyPrefix), scanRange(low, high), next/prev, insert/delete(key,TID), 선택적으로 returnPayload. SQL index는 map처럼 보이지만 duplicate key와 MVCC row identity를 함께 다룬다.

  1. 모든 entry는 선언된 key 순서·ASC/DESC·NULL order·collation의 동일 comparator로 정렬된다.
  2. 동일 user key가 허용되면 TID/primary key 등 안정적인 tie-breaker로 entry를 구별한다.
  3. B+tree의 separator는 자식 key range를 정확히 나누고 모든 leaf는 같은 depth이며 leaf chain은 전체 순서를 보존한다.
  4. 각 visible table row에는 필요한 index entry가 있고, 삭제/업데이트된 entry의 visibility 처리는 engine의 MVCC 계약과 일치한다.
  5. UNIQUE라면 SQL NULL semantics를 포함한 uniqueness 범위에서 중복 live key가 없다.
  6. INCLUDE payload는 search comparator·uniqueness에 참여하지 않으며 원본 row version과 연결된다.
  7. expression/partial index는 정의한 expression이 immutable하고 predicate가 참인 row만 포함한다.

5. 정당성: 왜 leftmost equality가 연속 구간을 만드는가

index (a,b,c)는 tuple을 사전식으로 비교한다. a=A AND b=B AND L≤c≤U를 생각하자.

  1. a<A인 tuple은 모두 목표 구간 앞, a>A는 모두 뒤에 있다.
  2. a=A 안에서 b<B는 앞, b>B는 뒤에 있다.
  3. a=A,b=B가 고정된 block 안에서는 c가 정렬돼 있으므로 [L,U]가 하나의 연속 interval이다.
  4. 따라서 lower bound (A,B,L)로 한 번 내려가 upper bound를 넘을 때까지 순차 scan하면 정확히 답한다.
최소 반례 — 중간 key gap: (a,b,c)에서 a=1 AND c=9만 주어지면, c=9는 b=0 block, b=1 block, b=2 block…에 흩어진다. 하나의 좁은 interval이 아니므로 a=1 전체를 scan해 c를 filter하거나, distinct b별로 재탐색하는 skip scan이 필요하다.

Range barrier: a=1 AND b>10 AND c=9에서 b range 안의 각 b group마다 c가 다시 정렬된다. c=9가 전체 b range에서 하나로 모이지 않으므로 c는 보통 scan 범위를 크게 줄이지 못한다. 단, DB별 skip scan·loose scan·bitmap 전략은 예외가 있으므로 EXPLAIN으로 확인한다.

복잡도는 page fanout B에 의존한다. wide string과 많은 INCLUDE column은 entry를 키워 fanout을 낮추고 tree height·cache miss·split을 늘린다. index scan이 K개의 TID를 찾더라도 heap row가 무작위 page에 흩어지면 locality가 나빠 bitmap/seq scan보다 느릴 수 있다.

7. Composite key 순서 결정 flow

1. query family를 모은다
WHERE·JOIN·ORDER BY·GROUP BY·LIMIT·projection과 빈도/p99 기여도
2. equality prefix를 만든다
항상 함께 고정되는 tenant/owner/status 중 workload 공통 선행 열
3. 첫 range·정렬을 배치한다
created_at range와 ORDER BY/LIMIT을 같은 leaf walk로 해결할 수 있는지
4. payload를 분리한다
검색 key가 아닌 출력 열은 INCLUDE/covering 후보, width·update 빈도 확인
5. 다른 query를 손익 계산한다
leading column 없는 질의, 별도 index/bitmap/skip scan/seq scan의 비용
6. EXPLAIN으로 반증한다
estimated/actual rows, buffers, heap fetches, sort, write overhead 비교

실무 예: multi-tenant 최근 주문은 (tenant_id, created_at DESC) INCLUDE (amount,status)가 후보지만, 전체 서비스의 “최근 실패 주문” 질의가 중요하면 별도 partial/index (created_at DESC) WHERE status='FAILED'가 더 적합할 수 있다. 하나의 초대형 index로 모든 질의를 덮으려 하지 않는다.

8. 직접 구현: lexicographic lower/upper bound

# entries: sorted list of ((tenant_id, created_at, order_id), amount) def lower_bound(entries, target): lo, hi = 0, len(entries) while lo < hi: mid = lo + (hi - lo) // 2 if entries[mid][0] < target: lo = mid + 1 else: hi = mid return lo def tenant_time_range(entries, tenant, start, end): left = lower_bound(entries, (tenant, start, MIN_ID)) right = lower_bound(entries, (tenant, end, MAX_ID)) for i in range(left, right): key, payload = entries[i] assert key[0] == tenant and start <= key[1] <= end yield key, payload

코드 리뷰 포인트: overflow 없는 midpoint, inclusive/exclusive boundary, NULL/collation, DESC transform, duplicate tie-breaker, comparator total order를 확인한다. DB index는 concurrent split·MVCC·page latch·recovery까지 더 필요하지만 contiguous interval의 핵심은 같다.

9. 테스트 전략: query 결과와 plan 계약을 분리

  1. Comparator property: antisymmetry·transitivity·totality와 DB collation/NULL order를 검사한다.
  2. Oracle: index range 결과를 full scan+sort 결과와 random dataset에서 비교한다.
  3. Boundary: 빈 index, 최소/최대 key, duplicate, 동일 timestamp, NULL, Unicode normalization을 넣는다.
  4. Query matrix: a, a,b, b, a range+c, mixed ORDER BY를 각각 EXPLAIN한다.
  5. Distribution: uniform뿐 아니라 1% hot tenant, correlated country/city, 시간 편향, soft-delete skew를 넣는다.
  6. Write path: insert/update/delete, unique conflict, page split, rollback, crash/restart 후 index-table 일치를 검증한다.
  7. Plan regression: estimated rows와 actual rows 비율, chosen scan, buffers, sort spill, heap fetch를 release마다 비교한다.

10. Benchmark: 열은 같아도 순서가 100배를 만든다

CPython 3.9.1의 in-memory SQLite에서 300,000 orders를 만들고 두 covering B-tree idx_tc(tenant_id,created_at), idx_ct(created_at,tenant_id)를 강제로 비교했다. 9회 중앙값이며 storage·cache가 다른 production 수치로 일반화하지 않는다.

질의/강제 indexplanner 범위중앙값
tenant=321 + time range / idx_tctenant equality + time range0.0199 ms
같은 질의 / idx_cttime range만 seek, tenant filter2.4047 ms
1,000-row time range / idx_tcANY(tenant) skip scan0.5175 ms
같은 range / idx_ct연속 time range0.0242 ms

첫 query에서 올바른 equality prefix가 약 121배 빨랐고, 시간-only query에서는 열 순서가 반대로 유리했다. SQLite는 idx_tc에서 skip scan을 선택했지만 여전히 직접 time range보다 약 21배 느렸다. 결론은 “정답 index 하나”가 아니라 workload 빈도와 SLO에 따라 두 query family의 비용을 합산하는 것이다.

Benchmark 주의: INDEXED BY는 비교를 위한 강제 장치다. 실제 운영에서는 planner가 선택하도록 두고 EXPLAIN ANALYZE, cold/warm cache, on-disk dataset, concurrent writers, realistic LIMIT/result width를 측정한다. microsecond 차이는 timer·CPU scaling noise보다 작을 수 있다.

11. 선택성 추정 실패: 독립 가정의 반례

100만 주소에서 country='KR'가 10%, city='Seoul'이 5%라고 하자. 독립으로 곱하면 둘 다 만족할 확률은 0.5%=5,000행이다. 그러나 Seoul이 전부 KR에 속한다면 실제는 5%=50,000행으로 10배다. 이 오차는 nested-loop와 hash join, index와 seq scan 선택을 뒤집는다.

single-column histogram만으로 상관관계를 알 수 없다. PostgreSQL의 extended statistics처럼 dependency·다변량 NDV·MCV를 수집하거나 schema/domain constraint를 활용한다. 통계 생성만 하고 ANALYZE를 빼먹지 않으며, estimate/actual row 비율로 효과를 검증한다.

13. Production Best Practice

  1. slow query 한 건이 아니라 normalized query family, 호출 빈도, 총 DB time, tail SLO로 우선순위를 정한다.
  2. equality prefix → 첫 range → ORDER BY/LIMIT → INCLUDE 순으로 후보를 만들되, 실제 plan으로 반증한다.
  3. EXPLAIN (ANALYZE, BUFFERS)의 estimated/actual rows, loops, heap fetch, sort spill을 함께 본다.
  4. correlated columns에는 extended statistics를 고려하고 ANALYZE 주기·sample quality를 관리한다.
  5. partial index는 작은 hot subset에 강하지만 query predicate가 index predicate를 함의해야 한다.
  6. covering은 read를 줄이지만 모든 출력 열을 넣지 않는다. leaf size, write rate, cache와 MVCC visibility를 측정한다.
  7. 중복 prefix index 제거는 DB별 planner·unique/FK·ordering·operator class 차이를 검증한 뒤 한다.
  8. index마다 owner query, 기대 효과, 생성 이유, 검토/삭제 기준을 기록해 schema debt를 막는다.

14. Anti-pattern과 놓치기 쉬운 것

  • 선택성이 높은 열을 무조건 먼저: equality/range/ORDER BY와 query family를 무시한다.
  • WHERE에 나온 열을 모두 key로: range 뒤 key는 filtering만 하고 index width·write cost만 키울 수 있다.
  • EXPLAIN만 보고 성공: 추정 plan과 실제 row·buffer·time은 다르다.
  • 함수로 column 감싸기: DATE(created_at)=...가 range seek를 깨뜨릴 수 있다. 명시 range나 expression index를 검토한다.
  • covering이면 항상 index-only: PostgreSQL 같은 MVCC engine에서는 visibility map 상태에 따라 heap fetch가 남는다.
  • unused index 즉시 drop: 월말 batch·장애 대응·FK/unique·rare critical query를 놓칠 수 있다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. 인덱스 (a,b,c)는 어떤 조건에 효과적인가요?
B-tree가 tuple을 lexicographic하게 정렬하므로 선행 equality a=?, b=?와 다음 c range가 하나의 interval을 만든다. a 없이 b/c만 주면 연속 구간이 아니며 full/skip scan이 필요할 수 있다. range 뒤 열은 대개 탐색 범위를 더 못 줄인다. DB별 skip scan은 EXPLAIN으로 확인한다.
Q2. (tenant_id, created_at)와 (created_at, tenant_id) 중 무엇을 고르나요?
multi-tenant 최근 N건이면 tenant equality 뒤 time range/order가 유리하다. 전체 시간대 분석이면 반대가 유리하다. query 빈도·result rows·ORDER BY/LIMIT·covering·write 비용을 workload-weighted로 비교하고 실제 row/buffer로 검증한다.
Q3. index가 있는데 seq scan을 고르는 이유는?
결과가 많거나 heap fetch locality가 나쁘면 index random I/O가 더 비싸다. stale/correlated stats로 rows를 틀리게 추정했거나 cast/collation 때문에 search key가 아닐 수도 있다. estimated vs actual rows, buffers, SARGability, statistics를 순서대로 본다.
