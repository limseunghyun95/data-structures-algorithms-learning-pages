한 줄 요약
Bounded queue는 과부하를 없애지 않고 유한한 대기 예산으로 바꾼다. Backpressure는 consumer가 감당 가능한 demand·credit을 upstream에 전달하는 제어 계약이며, 그 신호가 불가능할 때는 deadline-aware rejection·load shedding·spill 중 의도한 실패를 선택해야 한다.

4. ADT와 상태 계약

Queue abstract value: FIFO sequence Q=⟨j₀,…,jₙ₋₁⟩, 0≤n≤C. Admission ADT: offer(j)는 공간이 있으면 Q·⟨j⟩와 ACCEPTED, 없으면 Q를 보존하고 FULL을 반환한다. poll()은 nonempty일 때 (j₀,⟨j₁,…⟩)다.

6. 직접 구현: bounded offer/poll + credit

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct { uint64_t id, enqueued_tick; } Job;
typedef struct { Job *data; size_t capacity, head, size; } BoundedQueue;
typedef enum { Q_OK, Q_INVALID, Q_FULL, Q_EMPTY } QStatus;

static bool valid(const BoundedQueue *q) {
    if (!q) return false;
    if (q->capacity == 0)
        return !q->data && q->head == 0 && q->size == 0;
    return q->data && q->head < q->capacity &&
           q->size <= q->capacity && (q->size || q->head == 0);
}
static size_t offset(size_t start, size_t delta, size_t cap) {
    size_t room = cap - start;
    return delta >= room ? delta - room : start + delta;
}
static QStatus offer(BoundedQueue *q, Job job) {
    if (!valid(q)) return Q_INVALID;
    if (q->size == q->capacity) return Q_FULL;
    q->data[offset(q->head, q->size, q->capacity)] = job;
    ++q->size;
    return Q_OK;
}
static QStatus poll(BoundedQueue *q, Job *out) {
    if (!valid(q) || !out) return Q_INVALID;
    if (q->size == 0) return Q_EMPTY;
    Job job = q->data[q->head];
    if (q->size == 1) q->head = q->size = 0;
    else {
        q->head = q->head + 1 == q->capacity ? 0 : q->head + 1;
        --q->size;
    }
    *out = job;
    return Q_OK;
}

/* Receiver가 C credit으로 시작. emit마다 1 소비, poll마다 1 반환. */
static bool try_emit(BoundedQueue *q, size_t *credit, Job job) {
    if (!q || !credit || *credit == 0) return false;
    --*credit;
    QStatus s = offer(q, job);
    if (s != Q_OK) { ++*credit; return false; } /* failure atomic */
    return true;
}
static QStatus consume_and_grant(BoundedQueue *q, size_t *credit, Job *out) {
    if (!credit) return Q_INVALID;
    QStatus s = poll(q, out);
    if (s == Q_OK) ++*credit;
    return s;
}

Production concurrent queue에는 lock/condition variable 또는 검증된 atomic algorithm이 추가되어야 한다. 위 코드는 backpressure 상태 전이와 invariant를 분리 검증하는 single-thread reference model이다. try_emit은 offer 실패 시 credit을 돌려 failure atomicity를 지킨다.

7. 정당성 증명

Credit 안전성 귀납: 초기 credit=C, size=0이므로 합은 C. emit은 credit을 1 줄이고 queue size를 1 늘려 합을 보존한다. credit=0이면 상태 변화가 없다. consume은 size를 1 줄이고 credit을 1 늘린다. 따라서 모든 operation prefix에서 credit+size=C, 특히 size≤C다.

보존식 귀납: 초기 counter가 모두 0. offer 성공은 arrivals와 size를 각각 1 증가, full은 arrivals와 rejected를 각각 1 증가, poll 성공은 size를 1 감소하고 completed를 1 증가한다. 각 transition이 A=R+D+|Q|를 보존하므로 job은 사라지거나 복제되지 않는다.

중요한 한계: 이 증명은 capacity 안전성과 accounting correctness다. consumer가 영원히 progress한다는 liveness, 공정성, crash 후 exactly-once를 증명하지 않는다. 안전성과 생존성을 면접에서 구분한다.

10. Little's Law로 capacity를 latency로 번역

안정된 시스템에서 L=λW. MIT 6.02 자료의 면적 증명처럼 시간축 아래 queue-size 면적은 모든 job의 대기시간 합과 같다. 따라서 평균 queue occupancy를 effective throughput으로 나누면 평균 queue delay를 얻는다.

Back-of-the-envelope: worker pool이 초당 μ=1,000개를 처리하고 queueing budget이 50ms라면 FIFO backlog budget은 대략 μ×0.05=50개다. service time과 concurrency를 포함한 전체 in-flight budget, burst 분포, p99는 별도 검증해야 한다.
  • Little's Law의 λ는 실제 system을 통과한 effective rate다. rejected offered rate를 넣으면 식이 어긋난다.
  • 평균에 대한 식이므로 p99를 보장하지 않는다. heavy-tail service, correlated burst, priority를 load test한다.
  • λ≥μ가 지속되면 unbounded queue는 안정 조건을 잃고 W가 계속 자란다. bounded queue는 대신 rejection을 만든다.

12. Error handling과 shutdown protocol

  1. Invalid: null storage/output, zero·overflow capacity, 잘못된 demand n≤0을 구분한다.
  2. Full: 명시적 retryable status와 retry-after/backoff 정보를 반환하되 무조건 retryable로 표시하지 않는다.
  3. Timeout: queue 진입 전과 worker 시작 전 남은 deadline을 확인한다. 만료된 작업은 비싼 dependency call 전에 제거한다.
  4. Cancellation: waiting producer·consumer와 queued owning object 모두 정리 경로가 있어야 한다.
  5. Close: OPEN→DRAINING→CLOSED state를 두고 새 offer 거절, 기존 item drain, 모든 waiter 깨움, 최종 통계를 남긴다.
  6. Partial failure: credit를 줄인 뒤 enqueue가 실패하면 credit를 복구한다. batch offer의 all-or-nothing 여부를 API에 적는다.
놓치기 쉬운 점: Java BlockingQueue 자체에는 표준 close/shutdown이 없다. poison pill 하나는 consumer가 여러 개일 때 부족할 수 있고, queue가 full이면 poison enqueue도 막힌다. 별도 lifecycle state와 broadcast cancellation을 설계한다.

14. benchmark·load test 주의점

  • Coordinated omission: client가 느린 응답을 기다리며 다음 요청을 늦추면 실제 overload arrival을 생성하지 못하고 latency가 좋아 보인다.
  • Warm-up과 collapse: 평균 처리량만 보지 말고 step/ramp/spike/soak 후 recovery time과 useful throughput을 본다.
  • Histogram: 평균만이 아니라 queue wait와 service time을 분리해 p50/p95/p99/p99.9·max를 기록한다.
  • Work mix: 작은/큰 job, cache hit/miss, tenant, dependency slow/fail, cancellation 비율을 실제 분포로 재현한다.
  • Failure mode: 목표는 최대 QPS 숫자가 아니라 overload에서 memory bound, deadline 준수, 빠른 rejection, 자동 회복이다.
  • 실험 한계: 오늘 deterministic tick 결과는 인과를 보여 주는 model이다. production capacity 값은 실제 open-loop load test로 정한다.

15. 최소 반례와 장애 연쇄

“Queue를 10배 키우면 overload가 해결된다”의 최소 반례: λ=2 job/tick, μ=1 job/tick이 영원히 지속되면 크기 C의 queue는 C tick 정도 늦게 full이 될 뿐 장기 throughput은 1이다. 기다리는 job의 age만 커진다.

장애 연쇄: dependency slowdown → service time 증가·μ 감소 → in-flight와 queue 증가 → deadline 초과 → client retry → offered λ 증가 → CPU/GC/thread 증가 → useful μ 추가 감소. 이 양의 피드백을 admission, deadline propagation, retry budget, isolation으로 끊는다.

Backpressure 불가능 source: sensor tick, UDP, mouse event처럼 생산을 멈출 수 없다면 bounded buffer 뒤 선택지는 drop-new, drop-old, sample/coalesce, spill, fail뿐이다. “backpressure를 켠다”는 말만으로 물리 source가 느려지지 않는다.

16. 직접 테스트 체크리스트

  1. capacity 0/1, empty poll, full offer, wrap-around, output canary를 ASan/UBSan으로 검사.
  2. emit/consume 모든 짧은 interleaving에서 credit+size=C assertion.
  3. arrival/service transition마다 보존식과 completed ID uniqueness 검사.
  4. full, timeout, cancellation, close가 동시에 발생하는 model-based state test.
  5. dependency service를 느리게·실패하게 주입해 queue age와 rejection이 예상 방향인지 확인.
  6. retry를 켠 상태와 끈 상태의 offered/effective load·recovery time 비교.

오늘 실제 검증: capacity 3에서 길이 0..15의 emit/consume 65,535개 모든 operation sequence를 전수 검사했다. 매 prefix에서 RI와 credit+size=capacity가 성립했고 ASan/UBSan을 통과했다. overload simulation은 매 tick 보존식을 검사했다.

17. 대기업 면접 질문 3개와 답변 포인트

Q1. Queue capacity를 어떻게 정하겠습니까?
메모리가 아니라 queueing SLO부터 역산한다. service rate·worker concurrency·service distribution, 허용 wait, burst 크기/주기, element bytes를 측정한다. Little's Law로 1차 근사 후 open-loop load test에서 p99·reject·recovery를 검증한다.
Q2. Backpressure와 load shedding의 차이는 무엇입니까?
Backpressure는 consumer demand를 upstream 생산률에 피드백해 초과 생성을 예방한다. Shedding은 이미 초과했거나 source를 제어할 수 없을 때 일부 작업을 의도적으로 거절한다. 둘은 함께 쓸 수 있고 deadline·retry 계약이 필요하다.
Q3. 큰 queue가 왜 tail latency와 장애를 악화할 수 있습니까?
μ를 늘리지 않고 backlog age·memory만 늘린다. client deadline 뒤 stale work, retry amplification, tenant HOL blocking이 생긴다. queue age와 conservation metrics, bounded admission, early reject, cancellation, per-tenant isolation으로 방어한다.

  5. Day 12 ring RI가 오늘 system conservation proof의 어느 부분을 담당하는가?
  6. Day 9 geometric growth를 producer-consumer queue에 그대로 쓰면 어떤 tail failure가 생기는가?
  7. Day 11 call stack overflow와 오늘 queue overload의 공통 설계 원칙은?
답 확인: 1) W=L/λ=0.05s=50ms. 2) credit+size=C와 receiver bound. 3) 아니며 backlog는 평균 20/s 증가. 4) 없다. thread·deadline·upstream control에 따라 timed wait/reject를 선택. 5) queue 내부가 C를 넘거나 분실되지 않는 local safety. 6) resize pause·OOM·unbounded latency와 overload 은폐. 7) 유한 resource budget을 명시하고 overflow를 정상 API 경로로 다룬다.
