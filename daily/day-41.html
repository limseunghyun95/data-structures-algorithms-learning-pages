한 줄 요약
정렬의 승자는 알고리즘 이름 하나가 아니라 분포·key 범위·기존 run·중복도·record 폭·측정 계약의 함수다. 정확성을 먼저 검증하고 setup을 분리하며, warm-up·무작위 interleaving·반복·원시 표본을 남겨야 결과를 production 결정에 쓸 수 있다.

1. 초보자를 위한 용어 사전

Benchmark고정한 조건에서 성능을 반복 측정하는 실험. stopwatch 한 번과 다르다.
Workload입력과 연산의 조합. n, 분포, 중복도, 기존 순서, record 폭을 포함한다.
Distribution값이 나타나는 모양. uniform, hot-key, few-distinct, sorted가 내부 실행 경로를 바꾼다.
Warm-upcache·JIT·lazy initialization이 안정되도록 측정 전에 실행하고 결과는 버리는 구간.
Measurement windowtimer 안에 포함한 범위. copy·allocation·validation 포함 여부를 명시한다.
p50/p95/p99표본의 50/95/99%가 이하인 percentile. 9개 표본으로 p99를 주장할 수 없다.
CVcoefficient of variation=표준편차/평균. 단위 없는 변동성 지표다.
InterleavingA 전부 뒤 B 전부가 아니라 실행 순서를 섞어 온도·부하의 순서 편향을 줄이는 방법.
Oracle결과 정답을 판정하는 기준. sortedness뿐 아니라 permutation과 stability도 검사한다.
Dead-code elimination사용하지 않는 계산을 compiler가 제거하는 최적화. 결과 소비를 보장해야 한다.
Effect size차이가 얼마나 큰지를 나타내는 값. 통계적 유의성과 실무 의미는 다르다.

2. 문제·입출력·제약 mental model

Input: algorithms A, distributions D, sizes N, repetitions R, seed S Output: raw samples + statistics + correctness + metadata 실험 전에 고정할 것: - timer 안: copy? allocation? key extraction? validation? - 같은 dataset snapshot을 비교하는가? - stable/in-place/failure semantics가 같은가? - CPU·OS·runtime·compiler·flags·seed를 기록했는가? - 목표는 p50 throughput, p99 latency, peak memory 중 무엇인가?

“n=32,768 정렬”은 workload 정의가 아니다. sorted 32,768개와 full-range random 32,768개는 Timsort의 run 탐지, counting의 k, quicksort의 partition, radix의 pass 경로를 다르게 자극한다.

4. Benchmark ADT와 representation invariant

ADT: measure(algorithm,dataset,config)는 원시 duration 배열, correctness, 실패/거부 사유, 환경 metadata를 반환한다. 결과는 알고리즘의 “고유 속도”가 아니라 이 config의 관측치다.

  • Input RI: 같은 cell의 알고리즘은 동일 seed의 같은 value multiset을 받는다.
  • Isolation RI: 각 실행은 독립 copy에서 시작하고 이전 mutation을 공유하지 않는다.
  • Window RI: timer 경계가 모두 같다. 오늘은 input copy·validation은 밖, 내부 allocation·commit은 안이다.
  • Correctness RI: 기록 표본은 reference와 같아야 한다. 오답은 빠른 값으로 집계하지 않는다.
  • Trace RI: seed·n·분포·runtime·OS·warm-up·반복 수와 원시 표본을 남긴다.

6. 직접 구현한 harness

expected = {d: sorted(base[d]) for d in distributions} samples = {(d, a): [] for d in D for a in A} # warm-up은 버리되 correctness는 검사 for d in D: for a in A: work = list(base[d]) try: algorithm[a](work) assert work == expected[d] except RangeTooWide as e: rejected[d, a] = str(e) for repetition in range(R): jobs = [(d,a) for d in D for a in A if (d,a) not in rejected] rng.shuffle(jobs) # 순서 편향 완화 for d, a in jobs: work = list(base[d]) # setup: timer 밖 t0 = perf_counter_ns() algorithm[a](work) # allocation/commit: timer 안 elapsed = perf_counter_ns() - t0 assert work == expected[d] # oracle: timer 밖 samples[d,a].append(elapsed)

컴파일 언어/JVM에서는 결과 제거를 막기 위해 Google Benchmark의 DoNotOptimize나 JMH Blackhole 같은 harness 기능을 쓴다. volatile을 무작정 쓰면 다른 최적화를 왜곡한다.

7. Correctness proof와 최소 반례

  1. Initialization: 고정 seed의 immutable base와 reference sort를 timer 밖에서 만든다.
  2. Maintenance: 각 job은 base copy만 변경하므로 다음 job의 입력 RI가 보존된다. shuffled schedule은 각 label이 시간대 전체에 섞이게 한다.
  3. Validation: elapsed를 기록한 뒤 reference·identity·stability 계약을 검사한다. 실패 표본은 성능 결론에 포함하지 않는다.
  4. Termination: 유한한 D×A×R job을 모두 수행하면 각 허용 cell에 정확히 R개 표본이 있다.
최소 잘못된 benchmark: A는 sorted(copy)를 timer 안에 넣고 B는 이미 만든 배열을 in-place sort하면 A만 allocation/copy 비용을 낸다. 차이는 정렬이 아니라 window 차이다. 또 A를 항상 먼저 재면 thermal drift가 algorithm label과 결합된다.

8. 시간·공간·amortized 분석

D개 분포, A개 알고리즘, R회 반복에서 총 작업은 Σ(D,A) R·(Θ(n) copy + TA,D(n)), 저장 표본은 Θ(DAR)이다. reference는 분포별 O(n log n), snapshot memory는 Θ(Dn)이다.

  • 평균/기대/amortized 분석과 표본 통계는 다른 층이다. 기대 Θ(n log n)이 한 host의 9회 평균을 뜻하지 않는다.
  • 작은 kernel은 timer와 harness overhead가 지배한다. 여러 iteration을 batch하고 empty baseline을 잰다.
  • 표본 수를 늘려도 잘못된 window, 다른 입력, dead-code elimination 같은 systematic bias는 사라지지 않는다.

10. 해석: 숫자보다 경로를 설명하라

  • Builtin은 C 구현과 Timsort run 적응을 함께 얻어 sorted/reverse/nearly-sorted에서 random32보다 약 36~66배 낮은 중앙값이었다.
  • Counting은 16-key에서 builtin과 비슷했지만 full signed32는 거부됐다. O(n+k)의 k가 실제 의사결정 변수다.
  • 90% hot heap은 16-key heap보다 빨랐다. 동일 key가 많아 sift-down 비교가 일찍 끝나는 경로가 생겼다.
  • 직접 Python loop와 C builtin의 절대 시간을 알고리즘 차이만으로 해석하면 안 된다. production 언어·library에서 다시 잰다.
Noise 발견: 9회 표본의 CV가 0.487~1.784였고 일부 최대값은 중앙값의 여러 배였다. 이 실험의 p95 후보는 사실상 최대값이라 tail SLO 근거가 아니다. background load를 격리하고 표본을 늘려야 하며, 오늘 결과는 경로 학습용 smoke benchmark다.

11. Memory/locality와 counter

  • 시간이 달라지면 comparisons, swaps/writes, allocated bytes, branch/cache miss 중 무엇이 변했는지 가설을 세운다.
  • Heap은 O(1) aux지만 부모↔자식 jump와 swap이 많다. Merge/radix는 sequential access가 좋지만 Θ(n) scratch와 반복 memory traffic이 있다.
  • Counting count table이 cache를 벗어나면 k zero-fill과 counter access가 지배한다.
  • Google Benchmark는 user counter, memory manager, PMU counter를 결과와 함께 기록할 수 있다. profiling overhead가 크면 timing run과 분리한다.

12. 통계와 benchmark 주의점

  • 원시 표본, median, IQR/CV, min/max를 함께 보존한다. outlier를 지우려면 사전 규칙과 원인을 기록한다.
  • baseline/candidate를 시간 순서로 분리하지 말고 무작위 interleaving 또는 paired execution을 쓴다.
  • 유의성 검정 전 독립성·표본 수·다중 비교를 검토하고 ratio/절대 ms 같은 effect size와 SLO를 함께 본다.
  • Google Benchmark 비교 도구도 Mann–Whitney U test는 반복이 9회 미만이면 의미 없다고 경고한다. 9회가 충분하다는 뜻은 아니다.

14. 실무 best practice와 anti-pattern

Best practice

  • 검증된 library sort를 기본값으로 두고 profile이 확인한 병목에만 specialized path를 추가한다.
  • benchmark config를 version-control하고 JSON/CSV 원시 결과와 environment fingerprint를 artifact로 남긴다.
  • functional test와 benchmark를 분리하되 benchmark에도 lightweight oracle을 유지한다.
  • PR gate는 noise floor보다 큰 회귀만 막고 전용 host 추세와 production telemetry로 재확인한다.
  • fast path 거부/실패 시 안전한 library fallback과 선택·fallback metric을 둔다.

Anti-pattern

  • 한 번 실행하고 승자를 선언한다.
  • random 입력 하나로 adaptive·duplicate·range·adversarial 경로를 숨긴다.
  • setup 차이와 sort 차이를 섞는다.
  • 평균만 보고 bimodal·tail·outlier를 감춘다.
  • microbenchmark를 production p99·concurrency·NUMA 결과로 일반화한다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. 정렬 benchmark가 공정하다는 것을 어떻게 증명하나요?
동일 seed/snapshot, 독립 copy, 동일 timer boundary, randomized order, warm-up, correctness oracle과 환경 metadata라는 RI를 제시한다. 원시 표본과 실패도 남긴다.
Q2. 평균 10% 개선이면 배포하나요?
paired ratio·noise floor·effect size·분포를 보고 target workload의 p95/p99·memory·correctness를 확인한다. 전용 host와 canary telemetry로 재검증한다.
Q3. Counting sort가 빠른데 기본값으로 쓰지 않는 이유는?
Θ(n+k)에서 k가 untrusted하면 overflow/OOM·cache blow-up이 난다. checked range·byte cap 아래 fast path로만 쓰고 library/radix fallback을 둔다.
