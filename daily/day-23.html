한 줄 요약
Binary Search Tree는 모든 node가 담당하는 전역 key interval을 지킬 때만 탐색이 맞고, 연산 비용은 O(h)이므로 balance를 보장하지 않으면 정렬 입력 하나로 O(n) linked list가 된다.

1. 초보자를 위한 용어 사전

BSTBinary Search Tree. 각 node의 왼쪽 전체 subtree는 더 작은 key, 오른쪽 전체 subtree는 더 큰 key를 갖는 binary tree.
Key / value정렬·검색에 쓰는 식별 기준 / key와 연결된 업무 데이터. key는 같아도 value를 교체할 수 있다.
Comparator두 key를 less/equal/greater로 판정하는 함수. tree의 모든 연산이 같은 의미를 써야 한다.
Total order임의의 두 key를 일관되게 비교할 수 있고, 반대칭·추이성·동치 일관성을 만족하는 순서.
Ordering invariant모든 node k에 대해 left의 모든 key<k<right의 모든 key라는 항상 참이어야 하는 조건.
Search pathroot에서 비교 결과에 따라 한 child씩 선택해 내려가는 경로.
Height h여기서는 root에서 가장 먼 leaf까지 edge 수. 연산이 보는 node 수는 최대 h+1이다.
Balanced / skewed높이가 O(log n)으로 제한된 상태 / 한 방향 chain에 가까워 h≈n−1인 상태.
Minimum / maximum가장 왼쪽 / 가장 오른쪽 node. 각각 더 작은/큰 child가 없을 때 도착한다.
Predecessor / successor정렬 순서상 바로 이전 / 다음 key. successor는 delete와 range iteration의 핵심이다.
Lower bound주어진 key 이상인 첫 entry. exact match보다 ordered map다운 연산이다.
Transplant삭제할 subtree root를 다른 subtree root로 부모와 다시 연결하는 조작.
Duplicate policy같은 key를 reject, value replace, count 누적, 한쪽에 저장 중 무엇으로 처리할지 정한 계약.
Augmentationsubtree size·sum·max 같은 metadata를 node에 추가해 rank/select 등 새 연산을 지원하는 기법.
가장 중요한 문장: “left child < parent”가 아니라 “left subtree의 모든 key < parent”다. 로컬 비교만 하는 validator는 잘못된 tree를 통과시킨다.

5. Ordered Map ADT와 representation invariant

ADT: get(k), put(k,v), remove(k), min/max, lowerBound(k), successor(k), range(lo,hi). 외부는 node 주소나 tree shape를 관찰하지 않는다.

  1. RI-1 structural tree: root는 parent 없음, non-root는 parent 하나, cycle/shared child/orphan 없음.
  2. RI-2 global order: node x의 left 모든 key < key(x) < right 모든 key.
  3. RI-3 comparator: 모든 연산은 같은 total order를 사용하고 실행 중 의미가 바뀌지 않는다.
  4. RI-4 duplicate: 이 구현은 unique key이며 equal put은 value replace, size 불변이다.
  5. RI-5 parent symmetry: x.left=y ⇒ y.parent=x, right도 동일하다.
  6. RI-6 ownership: reachable node만 소유하고 삭제 후 dangling pointer/double free가 없다.
  7. RI-7 size: header size는 root에서 도달 가능한 node 수와 같다.
  8. RI-8 augmentation: subtree size를 저장하면 1+size(left)+size(right)다.

중복은 사소하지 않다. “equal은 오른쪽” 정책을 쓰면 validator 구간을 [lo, hi)처럼 바꾸고 successor·count·delete semantics도 맞춰야 한다. 실무 map은 보통 key 하나에 value 하나를 두고 equal put을 replace한다.

9>3이라 부모 3과의 local 비교는 통과한다. 그러나 9는 root 8의 left subtree에 있으므로 9<8이어야 한다. 올바른 validator는 root에서 (−∞,+∞), left로 (−∞,8), 다시 right로 (3,8)을 전달해 9를 거부한다.

대안: inorder가 strictly increasing인지 검사해도 unique-key BST ordering을 확인할 수 있다. 단, cycle·shared node·parent link·size는 별도 검사가 필요하다.

7. Search 정당성: 버린 subtree에 답이 없음을 증명하라

Loop invariant: 반복 시작 시 target key가 tree에 존재한다면 현재 node가 root인 subtree 안에 있다.

  1. 초기화: 현재 node는 전체 tree root이므로 참이다.
  2. 유지: target<current면 global RI에 의해 current와 right subtree의 모든 key는 target이 아니다. left만 남겨도 invariant가 유지된다. target>current는 대칭이다.
  3. 종료: equality면 정확한 entry를 찾았다. null에 닿으면 후보 subtree가 empty이므로 존재하지 않는다.

비교 한 번마다 key 범위를 줄이지만 node 수가 절반이 된다는 보장은 없다. 반으로 줄어드는 것은 balance가 추가로 보장될 때뿐이다.

8. Insert와 duplicate contract

search와 같은 path를 따라 null child에 도착한 뒤 새 leaf를 연결한다. 그 null이 담당하던 (lo,hi) 구간 안에 key가 있다는 path invariant 때문에 새 leaf도 전역 RI를 보존한다.

equal key 정책장점반드시 정할 것
Replace valueMap semantics 단순old value 반환/해제 책임
Reject예약·unique index에 적합typed DUPLICATE 오류
Count/list in valuetree key는 unique 유지value collection lifetime
Equal to one side구현 가능구간 경계·rotation 후 정책 복잡

Failure atomicity: node allocation과 key/value copy를 먼저 성공시킨 뒤 마지막에 parent child pointer 하나를 바꾼다. OOM 전에 tree를 연결하면 rollback과 RI 복구가 어려워진다.

9. Delete: 두 child가 있을 때 successor를 쓰는 이유

상태조작안전 근거
0 childparent link를 null로subtree 제거만 일어남
1 childchild를 transplantchild subtree가 같은 구간 안
2 childrenright subtree minimum인 successor로 대체successor는 left child가 없고 사이 key가 없음

successor y는 삭제 node z보다 크고 z.right의 나머지 key 이하이므로 z의 자리를 맡을 수 있다. y가 z의 바로 오른쪽 child가 아니면 y.right를 y의 원래 자리에 transplant한 뒤 y를 z 자리에 옮긴다. parent pointer와 augmentation을 바닥부터 갱신해야 한다.

Node identity 함정: successor의 key/value만 z에 복사하면 외부가 node handle을 보유할 때 “같은 node의 key가 바뀜” 문제가 생긴다. node 주소를 API에서 숨기거나 iterator invalidation 계약을 명시하라.

10. 직접 구현: iterative put과 bounds validator

PutResult put(Tree *t, Key k, Value v) {
  Node *parent = NULL, *x = t->root;
  int cmp = 0;
  while (x != NULL) {
    cmp = compare(k, x->key);
    if (cmp == 0) { replace_value(x, v); return REPLACED; }
    parent = x;
    x = cmp < 0 ? x->left : x->right;
  }

  Node *z = try_make_node(k, v);       // 아직 tree 불변
  if (z == NULL) return OUT_OF_MEMORY;
  z->parent = parent;
  if (parent == NULL) t->root = z;
  else if (cmp < 0) parent->left = z; // 마지막 commit point
  else parent->right = z;
  t->size++;
  return INSERTED;
}

bool ordered(Node *x, Bound lo, Bound hi) {
  if (x == NULL) return true;
  if ((lo.set && compare(lo.key, x->key) >= 0) ||
      (hi.set && compare(x->key, hi.key) >= 0)) return false;
  return ordered(x->left, lo, bound(x->key)) &&
         ordered(x->right, bound(x->key), hi);
}

production validator는 위 ordering뿐 아니라 visited set으로 cycle/shared node, parent symmetry, reachable count와 size를 함께 검사한다. 깊이가 untrusted면 validator도 explicit stack을 써야 한다.

11. Complexity: O(log n)이 아니라 O(h)

plain BST에는 연산을 반복한다고 높이가 저절로 좋아지는 amortized 보장이 없다. 정렬 key n개를 넣으면 1+2+…+n=Θ(n²) 비교가 될 수 있다. 균형 tree는 회전/색/높이 invariant로 h=O(log n)을 강제한다.

Rust 표준 문서도 single-element heap node BST는 비교마다 indirection/cache miss가 날 수 있다고 설명하고, B-tree는 한 node에 여러 element를 연속 배치해 allocation과 cache miss를 줄이는 절충이라고 밝힌다. “비교 횟수 최소”와 “wall-clock 최소”는 다르다.

15. 테스트 전략

  • 최소 shape: empty, one node, root 삭제, only-left/right, two-child successor가 직계/깊은 경우.
  • 최소 반례: 8의 left subtree 안 9처럼 local 비교는 통과하지만 bounds는 위반하는 tree.
  • Golden order: inorder가 reference sorted unique keys와 정확히 같다.
  • Differential: random put/get/remove를 표준 ordered map 또는 sorted vector model과 비교한다.
  • Property: comparator 반대칭·추이성, size=reachable, parent symmetry, 모든 key bounds.
  • Shape: sorted, reverse, all-equal, random, organ-pipe 입력의 height/comparisons를 측정한다.
  • Failure injection: node/key/value N번째 allocation 실패 전후 exact state를 비교한다.
  • Sanitizer: delete 3 cases, repeated clear, iterator invalidation을 ASan/UBSan/LeakSanitizer로 확인한다.

16. 실무 Best Practice

  1. Plain BST는 교육용 baseline: production ordered map은 높이 보장 구현을 사용한다.
  2. Comparator를 schema로 취급: 정렬 방향, null/NaN, case/locale, version을 persistence와 API에 고정한다.
  3. Key를 제자리 수정하지 않기: ordering이 달라지면 remove→modify→reinsert한다.
  4. Range가 없으면 hash도 비교: exact lookup만 필요할 때 ordered structure 비용을 정당화한다.
  5. Read-mostly면 sorted array: batch build 후 조회가 압도적이면 locality와 작은 memory footprint가 강하다.
  6. Height를 metric으로: size만 보지 말고 max/average depth, comparisons p95/p99, rotations를 관측한다.
  7. Bulk load 활용: sorted 입력을 median 순서로 build하거나 library bulk-load를 써서 O(n²) 삽입을 피한다.
  8. Node handle을 숨기기: rotation/delete 뒤 주소·identity 계약을 최소화하고 iterator invalidation을 문서화한다.

18. 대기업 면접 질문 3개와 답변 포인트

Q1. BST validator에서 부모와 child만 비교하면 왜 틀리며 어떻게 고치나요?
8-left-3-right-9 최소 반례를 그린다. 9>3은 local 통과지만 root left이므로 9<8 위반이다. (lo,hi)를 내려보내거나 strict inorder를 검사하고, cycle/shared/parent/size는 별도 RI로 검증한다.
Q2. BST delete의 두-child case를 설명하고 정당화하세요.
right subtree minimum successor는 left child가 없고 삭제 key와 나머지 right keys 사이에 있다. successor 원래 자리에는 right child를 transplant하고 삭제 위치를 successor가 맡는다. parent·root·metadata·identity 계약까지 말한다.
Q3. BST, hash map, sorted array, B-tree 중 무엇을 고르겠습니까?
exact vs range/successor, update 비율, worst-case SLA, memory/cache/page를 먼저 묻는다. exact 중심은 hash, read-mostly는 sorted array, in-memory ordered update는 balanced tree, cache/page locality는 B-tree 계열로 방어한다.
