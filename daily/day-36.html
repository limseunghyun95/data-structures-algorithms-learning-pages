정렬 알고리즘은 시간복잡도만 비교하지 말고 동일 key의 순서 보존(stable), 보조 메모리(in-place), 기존 질서 활용(adaptive), 최악 시간, 이동 비용, comparator 계약, locality와 failure atomicity를 workload 요구로 분해해 선택해야 한다.

4. Sorting ADT와 representation invariant

ADT: sort(A,key,order)는 입력 multiset과 같은 원소를 comparator 순서의 sequence로 돌려준다. stable 옵션이 계약이면 equal-key identity 순서까지 결과의 일부다.

  1. 처리 완료 prefix는 comparator 순서로 정렬되어 있다.
  2. 정렬 중 어느 시점에도 입력 원소의 identity와 개수는 잃거나 복제되지 않는다.
  3. key와 satellite data는 하나의 record로 함께 이동한다.
  4. stable 알고리즘은 equal key를 이동할 때 원래 index가 작은 record를 앞에 둔다.
  5. comparator는 strict weak/total order 계약을 만족하고 정렬 도중 결과가 변하지 않는다.
  6. 범위 정렬이면 [lo,hi) 밖의 원소는 바뀌지 않는다.
  7. 실패를 허용하는 API라면 allocation/comparator 예외 뒤 입력 상태 보장을 문서화한다.

in-place 주의: 입력 list를 직접 수정하는 Python list.sort()가 곧 O(1) extra space라는 뜻은 아니다. Java object-array adaptive merge는 입력에 따라 임시 참조 공간을 쓴다. recursive quicksort도 call stack O(log n), 최악 O(n)을 보조 공간에 포함하는지 정의해야 한다.

5. 안정성 정당성: 왜 equal일 때 왼쪽을 먼저 뽑나

stable merge를 생각하자. 왼쪽 run L과 오른쪽 run R은 각각 stable하게 정렬돼 있고, 원래 배열에서 L의 모든 원소가 R보다 앞에 있었다.

  1. key(L[i]) < key(R[j])면 L[i]를 출력해야 정렬성이 유지된다.
  2. key(R[j]) < key(L[i])면 R[j]를 출력한다.
  3. key가 같으면 L[i]는 원래 R[j]보다 앞이었으므로 L[i]를 먼저 출력해야 안정성이 유지된다.
  4. 선택한 run 내부 상대 순서는 이미 stable하고 포인터만 전진하므로 귀납적으로 전체 merge도 stable하다.
최소 반례 — selection swap: [(2,a),(2,b),(1,x)]에서 최솟값 (1,x)을 첫 위치와 swap하면 [(1,x),(2,b),(2,a)]가 되어 equal key 2의 a/b 순서가 뒤집힌다. 정렬 결과 key는 맞지만 stable 계약은 실패한다.

다중 키: 먼저 secondary key로 stable sort하고 그다음 primary key로 stable sort하면, primary가 같은 group 안에서 secondary 순서가 보존된다. 불안정한 두 번째 sort는 이전 정렬 정보를 파괴한다. radix sort의 각 digit pass도 같은 이유로 stable해야 한다.

6. 적응성: n 말고 disorder를 비용에 넣는다

Insertion sort의 이동 횟수는 inversion 수 I와 직접 연결된다. 각 shift는 현재 원소와 앞의 더 큰 원소 한 쌍의 inversion을 제거하므로 총 shift는 정확히 I다. 따라서 시간은 Θ(n+I): 이미 정렬이면 Θ(n), 역순이면 I=n(n−1)/2라 Θ(n²)이다.

Run-adaptive merge 계열은 이미 정렬된 연속 구간을 찾아 merge한다. r개 run만 있다면 직관적으로 n개 singleton부터 시작하는 것보다 merge 단계가 줄고, 좋은 구현은 run 길이 분포를 활용한다. 단 “adaptive”는 자동으로 O(1) memory나 stable을 뜻하지 않는다. 세 속성은 독립 축이다.

속성답하는 질문독립 반례

in-placeextra memory O(1)?selection sort는 in-place지만 unstable

8. 직접 구현: stable in-place insertion sort

def insertion_sort(a, key): for i in range(1, len(a)): x = a[i] # satellite data 전체 보존 kx = key(x) # 비싸면 한 번만 계산 j = i # strict <만 사용: equal이면 shift하지 않아 stable while j > 0 and kx < key(a[j - 1]): a[j] = a[j - 1] j -= 1 a[j] = x # loop invariant: # 반복 i 시작 시 a[0:i]는 원래 a[0:i]의 stable sorted permutation. # inner loop는 x보다 큰 원소만 한 칸 오른쪽으로 옮기므로 # permutation과 equal-key 상대 순서를 보존한다.

정당성: base i=1에서 길이 1 prefix는 정렬됐다. inner loop는 x보다 큰 suffix만 오른쪽으로 shift하고 x를 빈 위치에 넣으므로 새 prefix가 정렬된다. 원소는 복사/삽입될 뿐 소실되지 않아 permutation이다. equal에는 shift하지 않으므로 먼저 있던 equal record가 앞에 남아 stable이다. i가 n에 도달해 종료하면 전체 postcondition이 성립한다.

실무 코드 리뷰: key 함수를 while마다 다시 호출하지 않도록 모든 key를 decorate/cache할지, key 계산 실패 시 입력이 부분 변경돼도 되는지, comparator가 state/time에 따라 변하지 않는지, move가 예외를 던질 수 있는 언어인지 확인한다.

10. Benchmark: 같은 n, 다른 disorder

CPython 3.9.1에서 5,000개의 (key, originalIndex)를 stable insertion sort와 Python Timsort로 5회 실행해 중앙값을 구했다. 비교를 직접 계수했고 모든 결과를 sortedness·permutation·stability oracle로 검증했다.

분포InsertionTimsort
random693.496ms · 6,270,443 비교8.535ms · 54,921 비교
1% adjacent swap0.529ms · 5,045 비교1.682ms · 6,715 비교
descending1,374.544ms · 12,497,489 비교3.240ms · 18,168 비교
8 distinct keys590.748ms · 5,396,191 비교5.654ms · 33,560 비교

Insertion은 거의 정렬된 입력에서 Timsort보다 빨랐지만 random/reverse에서 quadratic cost가 폭발했다. Timsort는 descending run과 duplicate 분포를 활용했다. 결론은 insertion을 “느린 O(n²)”로만 외우지 말고 small-run base case와 near-sorted fast path로 이해하는 것이다.

Benchmark 주의: Python 레벨 insertion과 C 구현 Timsort의 절대 시간은 공정한 알고리즘 비교가 아니다. 비교 횟수와 입력 형태의 변화가 핵심이다. production 선택에는 같은 언어/라이브러리에서 record width, key 비용, GC, temp memory peak, cold/warm cache, concurrency를 측정한다.

11. Comparator와 데이터 함정

  • 정수 빼기로 비교: return a-b는 overflow로 부호가 뒤집힐 수 있다. 안전한 3-way compare를 쓴다.
  • NaN: IEEE NaN은 일반 < 관계로 total order를 만들지 않는다. NaN 위치 정책을 명시한다.
  • locale/Unicode: code point, locale collation, normalization이 다른 순서를 만든다. index/sort comparator를 일치시킨다.
  • mutable key: 정렬 중 key가 바뀌면 comparator transitivity가 깨지고 결과가 정의되지 않는다.
  • 비결정 tie: distributed pagination에서 equal key tie-breaker가 없으면 page 간 중복·누락이 생긴다.
  • expensive key: regex/parsing/network lookup을 comparator마다 반복하지 말고 순수 key를 미리 계산한다.

13. Production Best Practice

  1. 전체 sort 전에 top-k, selection, bucket, pre-sorted index, streaming merge로 문제를 줄일 수 있는지 본다.
  2. library 이름이 아니라 버전별 stable·worst-time·extra-space·exception guarantee를 공식 문서에서 확인한다.
  3. DB pagination과 distributed merge에는 business key 뒤 unique deterministic tie-breaker를 둔다.
  4. 비싼 key는 한 번 계산하되 O(n) key cache의 메모리·failure atomicity를 예산에 넣는다.
  5. small partition에는 insertion sort cutoff를 쓰되 threshold는 record/key/hardware별 benchmark로 정한다.
  6. 큰 record는 reference/index sort와 final gather의 cache trade-off를 비교한다.
  7. RAM을 넘으면 chunk sort→durable run→k-way merge→atomic publish external pipeline을 쓴다.
  8. 비교·move·allocated bytes·spill bytes·p99·cancellation을 입력 분포 label과 함께 관측한다.

14. Anti-pattern과 놓치기 쉬운 것

  • in-place=입력 수정: API mutation과 O(1) auxiliary space를 혼동한다.
  • stable이면 느림: 속성이지 고정 성능 등급이 아니다. adaptive stable sort가 실무에서 강하다.
  • O(n log n)이면 동일: comparisons, moves, temp bytes, locality, worst case가 다르다.
  • 정렬 후 LIMIT: k가 작으면 heap/select가 훨씬 적은 일을 할 수 있다.
  • tie는 아무 순서: 재현성·pagination·snapshot diff·UI UX에서 문제를 만든다.
  • random input만 benchmark: sorted/reverse/duplicates/runs/adversarial에서 선택이 뒤집힌다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. stable sort가 언제 필요한가요?
equal key의 기존 순서가 semantics일 때, secondary→primary 다중 pass 정렬, radix digit pass, deterministic UI/pagination에서 필요하다. 최소 반례로 selection swap을 보여주고, 필요 없으면 unstable in-place 후보의 memory/locality 이득도 비교한다.
Q2. in-place와 input을 수정하는 것은 같은가요?
아니다. destructive는 입력을 덮어쓰는 API 효과, in-place는 strict O(1) auxiliary space 특성이다. 입력을 수정하면서 O(n) temp를 쓸 수 있고, recursion stack·key cache도 공간 분석에 포함한다.
Q3. 거의 정렬된 입력에 어떤 알고리즘을 고르나요?
disorder metric을 먼저 확인한다. insertion은 Θ(n+I)라 inversion이 적고 n이 작으면 강하다. 큰 n과 여러 run에는 Timsort류 adaptive stable merge가 worst O(n log n)을 유지한다. 실제 key/move/memory를 분포별로 측정한다.
