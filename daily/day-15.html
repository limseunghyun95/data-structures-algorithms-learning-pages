4. Map ADT, abstraction function, RI

ADT 상태: 유한한 부분함수 M: K ⇀ V. get(k)는 정의되어 있으면 M(k), 아니면 NOT_FOUND. put(k,v) 뒤 M(k)=v이고 다른 key의 mapping은 그대로다. delete(k)는 k만 제거한다.

Chaining representation: 길이 m의 bucket array B[0..m-1]와 entry 수 n. Abstraction function은 모든 bucket의 (key,value)를 합쳐 map으로 해석한다.

  1. RI-1: m>0, len(B)=m, n=Σ len(B[i]).
  2. RI-2: 모든 entry e는 B[index(e.key)]에만 존재한다.
  3. RI-3: equality 기준으로 같은 key는 전체 table에 최대 하나다.
  4. RI-4: key가 table에 머무는 동안 equality와 hash에 참여하는 field는 변하지 않는다.
  5. RI-5: x==y ⇒ hash(x)==hash(y). 역은 필요 없다. 같은 hash라고 같은 key는 아니다.

왜 equality가 마지막 판정인가? hash code는 후보를 좁히는 값일 뿐이다. 64-bit hash에도 가능한 key가 더 많으면 충돌은 존재한다. hash만 비교해 값을 반환하면 서로 다른 tenant의 상태가 섞이는 correctness·보안 버그가 된다.

5. Collision은 왜 피할 수 없는가: 최소 증명

가능한 key가 u개이고 bucket이 m개이며 u>m라 하자. 모든 key가 서로 다른 bucket으로 간다면 m개 bucket에 u개 key를 하나씩 넣어야 한다. 하지만 bucket은 m개뿐이므로 비둘기집 원리에 의해 최소 두 key는 같은 bucket으로 간다. 따라서 collision-free를 일반 동적 map의 전제로 둘 수 없다.

최소 반례: h(k)=k mod 8이면 key 1과 9가 같은 bucket 1이다. bucket에 value 하나만 덮어쓰면 1의 mapping이 사라진다. 올바른 구현은 collision resolution 뒤 equality로 1과 9를 구별한다.

6. Load factor가 expected cost를 만드는 과정

n개 entry와 m개 bucket에서 α=n/m다. chaining에서 key가 bucket에 균등하게 분산된다고 가정하면 bucket 하나의 기대 chain 길이는 α다. hash·array 접근 Θ(1)에 chain 비교 Θ(α)가 더해져 search는 expected Θ(1+α)다.

중요: α는 평균 밀도이지 분포 품질이 아니다. α=0.5여도 모든 key가 한 bucket에 몰리면 lookup은 Θ(n)이다. 반대로 chaining에서는 α가 1보다 클 수 있다. 구현 방식별 임계값을 문서로 확인해야 한다.

8. Universal hashing: 가정을 구현으로 옮기기

“입력 key가 랜덤하다”는 서비스에서 방어하기 어려운 가정이다. 대신 함수 family H에서 실행마다 h를 무작위 선택해, 임의의 서로 다른 kᵢ,kⱼ에 대해 Pr[h(kᵢ)=h(kⱼ)]≤1/m을 보장하는 universal hashing을 쓸 수 있다.

MIT 6.006의 정수 key 예시는 hₐᵦ(k)=(((a·k+b) mod p) mod m)이며 p는 key universe보다 큰 소수, a≠0이고 a,b를 무작위로 고른다. 특정 seed에 collision이 사라진다는 뜻이 아니라, seed 선택에 대한 기대 chain 길이를 제한한다.

  1. key kᵢ와 같은 bucket에 들어온 kⱼ를 indicator Xᵢⱼ∈{0,1}로 둔다.
  2. universality로 서로 다른 key마다 E[Xᵢⱼ]≤1/m.
  3. 기댓값의 선형성으로 E[chain(i)]≤1+(n-1)/m<1+α.
  4. 따라서 α=O(1)이면 lookup은 seed 선택에 대해 expected O(1). 독립 입력 분포를 가정하지 않는다.

9. 직접 구현: fixed-capacity chaining map

오늘은 resize를 숨기지 않기 위해 정수 key 범위가 정해진 bounded map을 만든다. Day 18에서 rehash를 붙인다. 새 key가 max load를 넘으면 기존 상태를 보존한 채 FULL을 반환한다.

P = 2_305_843_009_213_693_951  # 2^61-1 prime

class FixedHashMap:
    def __init__(self, m, a, b, max_load=4.0):
        if m <= 0 or not (1 <= a < P) or not (0 <= b < P):
            raise ValueError("invalid hash parameters")
        self.buckets = [[] for _ in range(m)]
        self.size = 0
        self.a, self.b, self.max_load = a, b, max_load

    def _index(self, key):
        if type(key) is not int or not (0 <= key < P):
            raise ValueError("key must be int in [0, P)")
        return ((self.a * key + self.b) % P) % len(self.buckets)

    def put(self, key, value):
        bucket = self.buckets[self._index(key)]
        for entry in bucket:          # hash는 후보, equality가 판정
            if entry[0] == key:
                old = entry[1]
                entry[1] = value
                return ("REPLACED", old)
        if (self.size + 1) / len(self.buckets) > self.max_load:
            return ("FULL", None)     # failure atomic: 아직 mutation 없음
        bucket.append([key, value])    # MemoryError면 size도 아직 그대로
        self.size += 1
        return ("INSERTED", None)

    def get(self, key):
        for stored_key, value in self.buckets[self._index(key)]:
            if stored_key == key:
                return ("FOUND", value)
        return ("NOT_FOUND", None)

구현 리뷰: replacement는 load limit과 무관하게 가능해야 한다. 새 entry append가 성공한 뒤에만 size를 증가시켜야 한다. 실제 Python list append의 MemoryError 처리와 value 교체 중 user code 예외 같은 언어 세부까지 strong guarantee가 필요한지는 API에서 정한다.

10. 정당성 증명과 테스트 전략

get correctness: 찾는 key k가 map에 있다면 RI-2에 의해 entry는 정확히 B[index(k)]에 있다. loop가 bucket의 모든 entry를 검사하므로 RI-3의 유일한 equality match를 반환한다. 없다면 같은 bucket 전체를 검사한 뒤 NOT_FOUND이므로 거짓 양성이 없다.

put preservation: 기존 key면 그 entry의 value만 바꿔 bucket 위치·key 집합·size가 유지된다. 새 key면 올바른 bucket에 하나 추가하고 size를 1 늘려 RI-1~3을 보존한다. FULL·validation·allocation failure가 mutation 전에 발생하면 추상 map은 그대로다.

  1. 예제: key 1과 9가 같은 bucket인 작은 m에서 둘 다 put/get/delete되는지 확인한다.
  2. 대체: 같은 key를 두 번 put하면 size는 그대로이고 마지막 value가 나온다.
  3. Property: 임의 operation sequence마다 Python dict reference와 mapping·size가 같다.
  4. RI 검사: 모든 entry의 실제 bucket, total count, key uniqueness를 각 prefix 뒤 검사한다.
  5. 실패 주입: invalid key, FULL, append MemoryError, equality exception 뒤 snapshot이 계약대로 보존되는지 본다.
  6. 분포: random·sequential·common-prefix·stride·attacker-chosen key 각각에 max/p95 chain histogram을 측정한다.

12. Memory·locality·lifetime deep dive

  • Bucket array: m을 크게 잡으면 α와 chain은 줄지만 빈 bucket·iteration·cache footprint가 커진다. bytes/entry는 payload 외 metadata까지 측정한다.
  • Chaining: node-per-entry면 pointer·allocator metadata·fragmentation과 pointer chasing이 추가된다. bucket별 작은 contiguous vector는 locality가 좋지만 erase 이동 비용이 있다.
  • Open addressing: table 안에서 probe해 locality와 메모리 밀도가 좋을 수 있으나 α가 1에 가까워질수록 probe가 길어지고 deletion 상태가 복잡해진다.
  • Key storage: 긴 string을 매 lookup마다 hash하면 O(|key|). immutable key에 hash를 cache할 수 있지만 객체 lifetime·seed 변경·memory overhead를 고려한다.
  • Reference stability: resize·erase가 entry 주소와 iterator를 무효화할 수 있다. 언어 container의 정확한 계약을 확인하고 외부에 내부 주소를 오래 노출하지 않는다.
  • Concurrency: hash 계산이 thread-safe여도 map의 복합 put-if-absent가 atomic인 것은 아니다. shard/lock/version/snapshot과 linearization point가 별도 필요하다.

16. 대기업 면접 질문 3개와 답변 포인트

Q1. HashMap lookup은 항상 O(1)인가요?
아니다. 좋은 분포와 bounded α 아래 expected O(1)이고, 모든 key가 한 bucket/probe cluster에 몰리면 worst Θ(n)이다. hash 계산 O(|key|), equality, cache miss, resize tail도 분리하고 universal/keyed hashing과 분포 지표를 제시한다.
Q2. load factor 0.75는 무엇을 뜻하고 왜 무조건 최선이 아닌가요?
n/m이며 구현의 resize 밀도 기준이다. 낮추면 보통 probe/chain은 줄지만 memory·iteration footprint가 늘고, 높이면 반대다. chaining은 α>1 가능, open addressing은 α<1 필수다. Java HashMap 0.75는 일반적 절충이지 모든 workload의 정답이 아니다.
Q3. equals와 hashCode 계약이 깨지면 어떤 버그가 생기나요?
동등한 두 key가 서로 다른 bucket 후보로 가서 lookup miss·중복 mapping·delete 실패가 생긴다. 동일 canonical immutable field로 둘을 구현하고 x==y ⇒ hash(x)==hash(y) property, mutation-after-insert 반례, cross-version serialization 경계를 설명한다.

  5. Day 3의 amortized와 오늘 expected는 어떤 확률·연산열 축이 다른가?
  6. Day 8 locality 관점에서 node chaining이 open addressing보다 불리할 수 있는 이유는?
  7. Day 14 operation mix에 range query가 많아지면 hash map 선택을 왜 재검토해야 하는가?
답 확인: 1) hash는 식별자가 아닌 후보 축약값. 2) 모든 key를 같은 bucket으로 보내는 함수·입력. 3) chaining bucket은 여러 entry를 담지만 open addressing은 빈 slot이 있어야 삽입 가능. 4) collision은 허용된다. 5) expected는 hash/입력 randomness, amortized는 긴 연산열 비용 합. 6) pointer chasing·allocation·cache miss. 7) hash map은 정렬 순서와 범위 탐색을 제공하지 않는다.
