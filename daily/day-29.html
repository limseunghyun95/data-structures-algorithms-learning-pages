Range flow: 시작 key까지 root→leaf로 한 번 내려간 뒤 leaf의 next link를 따라 연속 page를 scan한다. 매 결과마다 root부터 다시 찾는 구현은 B+tree의 핵심 locality를 버린다.

교과서 이름보다 구현 계약을 확인한다. 실제 DB 엔진은 “btree”라고 부르면서 leaf 중심·sibling link·dedup·MVCC tuple 등 B+tree 성격과 엔진 고유 정책을 결합한다.

5. Ordered Index ADT

  • get(key,snapshot): visible한 value/row-id 또는 NOT_FOUND.
  • put(key,value): duplicate replace/reject/multi-entry와 durability 지점을 정의한다.
  • remove(key): physical 즉시 삭제인지 tombstone/version cleanup인지 구분한다.
  • scan([lo,hi),direction,limit): 정렬 순서, snapshot, continuation token, cancel을 계약한다.
  • bulkLoad(sortedInput): online put 반복과 다른 fill factor·WAL·atomic publish 정책을 가진다.

중요: 자료구조 ADT의 “key 한 개”와 DB index의 duplicate key, MVCC version, row-id tie-break는 다르다. 물리 key를 (indexedColumns,rowId)처럼 total order로 만드는 이유다.

6. Representation invariant

  1. Page shape: internal page의 child 수는 separator 수+1이고, leaf entry와 slot은 1:1이다.
  2. Local order: 각 page의 logical key/slot 순서는 comparator 기준 엄격히 증가한다.
  3. Global range: separator s[i] 기준 child i의 key는 왼쪽 범위, child i+1은 오른쪽 범위에 속한다. 경계 포함 규칙은 일관돼야 한다.
  4. Balance: root를 제외한 모든 leaf는 같은 depth이며, non-root page는 정한 최소·최대 occupancy를 만족한다.
  5. B+ payload: 논리 record는 정확히 한 leaf에 있고 internal separator는 routing 복사본일 뿐이다.
  6. Leaf chain: next/prev가 key 순서를 보존하고 tree traversal의 leaf 순서와 정확히 일치한다.
  7. Reachability: root에서 모든 live page가 정확히 한 번 도달하며 freed/reused page를 가리키지 않는다.
  8. Physical page: header·slot·free-space·cell 영역이 겹치지 않고 checksum/LSN/page-id가 기대값과 일치한다.

논리 RI와 물리 RI를 분리해서 검사한다. key 순서가 맞아도 slot offset이 page 밖을 가리키면 corruption이고, page layout이 맞아도 stale separator면 잘못된 child로 간다.

가변 길이 cell 자체를 매 insert마다 밀지 않고 작은 slot offset만 정렬한다. delete로 freeblock·fragment가 생기면 page compaction을 할 수 있다. 큰 payload가 overflow page로 나가면 fan-out은 지키지만 추가 I/O와 corruption surface가 늘어난다.

Fan-out 근사: usable page가 P bytes, header H, 평균 separator+child entry가 E bytes면 internal fan-out은 대략 1+floor((P−H)/E)다. 실제값은 slot, prefix compression, variable key, alignment, reserve space와 fill factor를 포함해 측정한다.

고정 order에서 연속 insert 전체의 structural split 수는 page가 충분히 차야 다음 split이 가능하므로 상각하면 insert당 O(1)개 수준이지만, root→leaf 탐색과 WAL/page write는 여전히 사라지지 않는다. “split 상각 O(1)”을 “insert I/O O(1)”로 바꾸면 틀리다.

9. 숫자로 보는 fan-out

4KiB page에서 header·slot·여유를 제외하고 internal entry가 평균 16B라면 fan-out은 대략 200대가 될 수 있다. leaf가 평균 100 entry를 담고 fan-out F=200이라 가정하면 10억 entry에 필요한 leaf 약 1천만 page를 root 포함 약 5 level로 도달한다. pointer BST는 균형이어도 약 log₂(10억)≈30 node level이다.

이는 설명용 근사다. root·상위 internal은 buffer pool에 거의 항상 남을 수 있어 실제 storage read는 더 적고, 반대로 긴 composite key·낮은 fill·overflow·cache miss는 더 늘린다.

10. Leaf split 알고리즘과 정당성

insertIntoFullLeaf(L, key, value):
  T = stableSortedMerge(L.entries, (key,value))
  R = allocatePage()
  L.entries = T[0:mid]
  R.entries = T[mid:]
  R.next = L.next; L.next = R
  separator = R.entries[0].key
  insertIntoParent(L, separator, R)
  • Order: T가 정렬됐고 두 연속 slice로 나누므로 각 leaf의 local order와 max(L)<=min(R)가 성립한다.
  • Coverage: slice가 T를 중복 없이 분할해 기존 entry와 새 entry가 정확히 한 leaf에 남는다.
  • Occupancy: mid를 최소 occupancy 범위 안에서 고르면 L/R 모두 하한과 상한을 만족한다.
  • Routing: parent에 min(R) separator와 R pointer를 넣으면 이전 L 범위가 L/R 두 범위로 정확히 분할된다.
  • Balance: 같은 level에서 sibling 하나가 생긴다. parent split도 같은 논리를 재귀 적용하며 root split 때 새 root를 만들면 모든 leaf depth가 함께 1 증가한다.

DB 구현에서는 이 논리적 증명에 WAL record·latch visibility·page LSN·free-page allocation 순서가 추가돼야 한다. 메모리 RI를 지키는 코드가 곧 crash-safe 코드는 아니다.

12. 직접 구현·테스트·benchmark

Python으로 unique integer B+tree를 직접 구현했다. leaf/internal split, root 성장, get, leaf-link range를 만들고 다음 RI를 재귀 검증했다: local/global order, children=separators+1, separator=min(right subtree), leaf 동일 depth, 모든 entry 보존, leaf next chain 일치.

120,000개 key를 deterministic shuffle로 insert하고 200,000 hit lookup, 100-key range oracle, duplicate rejection을 실행했다.

13. Production benchmark 설계

  1. key/value 길이 분포, duplicate, monotonic/random/hotspot insert를 production trace에서 재현한다.
  2. cold cache와 warm cache를 분리하고 root/internal/leaf별 hit ratio와 physical read를 기록한다.
  3. point hit/miss, short/long range, update/delete churn, bulk load를 각각 측정한다.
  4. throughput만 보지 말고 p50/p95/p99, pages/op, split/sec, dirty eviction, WAL bytes/op, bytes/entry, cache hit을 본다.
  5. steady-state 전까지 충분히 채우고 checkpoint·compaction·vacuum·rebuild가 겹친 tail을 포함한다.
  6. crash injection을 WAL flush 전/후, new page write, parent install, page reuse 지점에 넣고 recovery 후 full validator를 돌린다.

주의: OS page cache와 DB buffer pool의 이중 cache, fsync 생략, 압축 여부, prefetch, queue depth가 다르면 결과를 비교할 수 없다. 평균 key만으로 fan-out을 계산하면 긴 tail key의 overflow와 split을 놓친다.

14. Split·delete·fragmentation의 실무 비용

  • Right-edge hotspot: 증가 key insert는 오른쪽 leaf와 parent에 집중된다. 순차 locality는 좋지만 latch contention·split burst가 생길 수 있다.
  • Random insert: page 전반에 dirty write와 split을 퍼뜨려 cache·storage write locality가 나빠질 수 있다.
  • Low fill factor: 미래 insert 여유와 split 감소를 사지만 index size·cache miss·scan I/O가 늘어난다.
  • Delete: 즉시 merge는 oscillation과 write를 만들 수 있다. DB는 MVCC dead tuple cleanup, redistribution, background maintenance를 결합한다.
  • Long key/include column: covering read는 줄여도 fan-out 저하, overflow, cache pressure, 모든 update의 index write를 키운다.

15. Concurrency: latch crabbing

  1. parent를 latch한 상태에서 child를 pin+latch한다.
  2. child가 현재 연산에 “safe”하면 parent latch를 놓는다. insert safe는 split될 만큼 full하지 않다는 뜻이다.
  3. unsafe path는 필요한 ancestor를 더 오래 잡거나 optimistic read 후 restart한다.
  4. 모든 thread가 root→leaf 같은 방향의 latch order를 지켜 deadlock을 줄인다.
  5. range scan의 sibling 이동과 concurrent split은 high-key/right-link, version check 또는 restart protocol로 누락·중복을 막는다.

latch는 page bytes의 순간적 일관성을 지키고 transaction lock/MVCC는 사용자가 보는 논리적 isolation을 지킨다. 둘을 하나라고 설명하면 면접에서 바로 꼬리 질문이 온다.

17. 실무 Best Practice

  1. page size·key distribution·SLO에서 fan-out과 예상 height를 계산한 뒤 실제 bytes/entry로 검증한다.
  2. 검증된 storage engine을 우선하고 custom tree보다 comparator·schema·index 선택을 먼저 최적화한다.
  3. point/range와 covering/base fetch를 분리 측정해 index가 줄이는 I/O와 새 write 비용을 함께 본다.
  4. 논리 RI, page bounds/checksum, cross-page link, root reachability validator를 offline/online 수준별로 둔다.
  5. bulk load는 sorted input과 목표 fill factor로 만들고 atomic publish·rollback·peak disk를 계획한다.
  6. split, page occupancy histogram, leaf fragmentation, cache hit, WAL bytes, p99 latch wait를 관측한다.
  7. backup restore와 crash recovery를 정기적으로 실제 실행한다. index rebuild 가능성과 base data 진실 원본을 구분한다.

18. 대기업 면접 질문 3개와 답변 포인트

Q1. DB index가 Red-Black tree보다 B+tree를 쓰는 이유는?
cost model을 page I/O로 선언한다. page-sized multiway node가 fan-out을 키워 height/I/O를 줄이고, internal payload를 줄인 B+tree는 fan-out과 linked-leaf range locality가 좋다. buffer pool·covering/heap fetch·split write 비용까지 말한다.
Q2. B+tree leaf split의 정당성과 crash 위험을 설명하세요.
sorted merge→연속 partition으로 order·coverage·occupancy를 보이고 min(right)를 parent에 복사해 routing을 복구한다. root split만 높이를 늘려 balance를 유지한다. production에서는 WAL-before-data, page LSN, latch visibility, recovery idempotence가 추가된다.
Q3. page 크기와 fill factor를 크게 하면 항상 좋은가요?
큰 page/fill은 fan-out·scan density를 높이지만 read/write granularity, cache pollution, split cost, contention과 tail을 키울 수 있다. key 분포·storage·point/range/write mix에서 p99, pages/op, split, WAL, bytes/entry로 결정한다.
