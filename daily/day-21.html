1. 초보자를 위한 용어 사전

Memory hierarchy작고 빠른 CPU cache에서 RAM, SSD/HDD로 이어지는 저장 계층. 아래로 갈수록 보통 크고 느리다.
Cache lineCPU cache가 메모리와 데이터를 주고받는 고정 크기 블록. 한 byte를 읽어도 이웃 byte가 함께 온다.
Temporal locality방금 쓴 데이터를 곧 다시 쓸 가능성. cache에 남아 있으면 hit가 난다.
Spatial locality접근한 주소의 이웃도 곧 쓸 가능성. 연속 배열·page batching이 활용한다.
Page / framepage는 DB의 논리적 고정 크기 블록, frame은 그 page를 담는 RAM 공간이다.
Buffer poolDB가 disk page를 RAM frame에 보관하는 관리형 cache. page table·교체 정책·dirty flush가 필요하다.
Pin count현재 page를 사용 중인 실행자의 수. 0이 아니면 frame을 쫓아내면 안 된다.
Dirty pageRAM에서 수정됐지만 아직 영구 저장소에 반영되지 않은 page.
Table indexquery마다 만들지 않고 유지하는 보조 자료구조. key에서 row 위치 후보로 이동한다.
Tuple / TIDtuple은 DB row, TID는 그 row의 물리적 위치를 가리키는 식별자다.
Lossy scan / recheckindex가 정확한 답 대신 후보를 내고 원본 row에서 조건을 다시 검사하는 방식.
Hash join한 입력의 join key로 임시 hash table을 build하고 다른 입력을 probe하는 equality join 알고리즘.
Spill / batchhash table이 메모리 예산을 넘을 때 partition을 임시 파일에 쓰고 나눠 처리하는 것.
Skew특정 key나 partition에 데이터가 몰린 분포. 균등 hash 가정과 memory 계획을 깨뜨린다.
Logical I/ODB가 page를 요청한 횟수. 실제 disk read인지 buffer hit인지는 별도로 본다.

중요한 구분: CPU cache는 일반적인 Map<K,V> 구현이 아니다. 물리 주소의 일부 bit로 set을 고르고 tag를 비교하는 hardware cache다. 반면 buffer pool의 page table과 query hash table은 실제 software hash map일 수 있다. 비슷한 “빠른 재사용” 효과와 내부 계약을 혼동하지 말자.

PostgreSQL hash index는 4-byte hash value만 저장하므로 scan이 lossy하며 원본 조건을 다시 확인해야 한다. equality 한 column만 지원하고 uniqueness를 보장하지 않는다. 긴 key equality workload에서 작을 수 있지만 범위·정렬 요구에는 맞지 않는다.

6. Hash join 정당성 증명

In-memory build/probe: R의 모든 tuple r을 h(r.k) bucket에 보존한다. 각 s∈S에 대해 h(s.k) bucket만 보고 그 안의 모든 r에 실제 r.k=s.k를 검사한다.

  1. Completeness: 실제 match r.k=s.k라면 hash contract로 h(r.k)=h(s.k), 따라서 s probe가 r의 bucket을 방문한다.
  2. Soundness: 같은 hash인 것만으로 출력하지 않고 equality가 true인 pair만 내므로 collision false positive가 없다.
  3. Multiplicity: build bucket에 같은 key의 r을 모두 보존하고 각 s와 비교하므로 duplicate의 Cartesian multiplicity가 유지된다.

Grace partition: R과 S를 같은 p=h₁(k) mod P로 나눈다. equal key는 같은 partition 번호이므로 서로 다른 partition 사이에는 match가 없다. 모든 tuple이 정확히 한 partition에 들어간다는 보존식 Σ|Rᵢ|=|R|, Σ|Sᵢ|=|S|와 각 pair의 정확한 in-memory join을 합치면 전체 join과 같다.

최소 반례: hash code만 같으면 join 결과로 내면 collision인 "Aa"와 "BB" 같은 서로 다른 key가 false match가 된다. 또 duplicate build rows를 map의 단일 value로 덮어쓰면 기대 결과 2개가 1개로 줄어든다.

7. 메모리가 부족하면 I/O 알고리즘이 된다

작은 build relation이 B−2 buffer page 안에 들어가면 naive in-memory hash join은 입력을 한 번씩 읽어 약 M+N page I/O가 든다. 들어가지 않으면 Grace hash join은 partition 단계에서 양쪽을 읽고 써 2(M+N), probe 단계에서 다시 읽어 M+N, 총 3(M+N) I/O가 든다(한 번의 균등 partition으로 충분하고 output write 제외).

조건선택위험

hot partition이 계속 큼다른 seed 재partition·heavy-hitter 분리·fallback같은 hash 반복 시 무진행 recursion
입력이 이미 정렬·결과도 정렬 필요sort-merge join 비교hash가 항상 빠르다는 고정 관념

PostgreSQL에서는 한 query에 sort/hash node가 여러 개이고 session도 여러 개일 수 있다. 따라서 work_mem 하나를 “connection당 최대 메모리”로 해석하면 안 된다. hash 기반 node의 한도는 work_mem × hash_mem_multiplier로 계산된다.

8. 직접 구현: buffer pin과 partitioned join

PageGuard fetch(PageId id) {
  lock(page_table_latch);
  if (page_table.contains(id)) {
    Frame *f = page_table[id];
    f->pin_count++;                 // evict 불가 상태를 먼저 만든다
    replacer.set_evictable(f, false);
    unlock(page_table_latch);
    return guard(f);                // guard destructor가 unpin
  }

  Frame *victim = reserve_unpinned_frame();
  if (!victim) return NO_FRAME;
  if (victim->dirty && !flush(victim)) {
    rollback_reservation(victim);   // dirty data를 버리지 않는다
    return IO_ERROR;
  }
  read_page(id, victim);            // 실패 시 page table commit 전 rollback
  page_table[id] = victim;
  victim->pin_count = 1;
  unlock(page_table_latch);
  return guard(victim);
}

11. Benchmark와 EXPLAIN에서 볼 것

  • Hash node: 실제 rows, Buckets, Batches, peak Memory Usage. Batches가 1보다 커졌다면 partition/spill 가능성을 조사한다.
  • BUFFERS: shared hit/read/dirtied/written과 temp read/written. logical access와 실제 I/O를 분리한다.
  • Estimate error: estimated rows와 actual rows의 배율. row count·width 오차는 잘못된 build side와 memory budget으로 이어진다.
  • Distribution: 평균 bucket뿐 아니라 max chain/partition, hot-key frequency, duplicate multiplicity를 본다.
  • Lifecycle: cold/warm cache, concurrent sessions, checkpoint/VACUUM, resize/split 구간을 분리한다.
  • End-to-end: micro hash probe만 재지 말고 heap fetch, visibility check, materialization, output network까지 포함한다.
분석 문장 예시: “Hash Join 자체 probe는 평균 2.25회였지만 8 batches와 temp read가 발생했고, hot key가 한 partition을 키웠다. work_mem만 전역으로 올리기 전에 cardinality·skew를 고치고 동시 query 총 메모리를 계산하겠다.”

13. 실무 Best Practice

  1. Plan from predicates: equality·range·ordering·uniqueness를 먼저 적고 index 종류를 고른다. equality라고 무조건 hash index가 아니다.
  2. Use the DBMS: 영구 hash index의 WAL, concurrent split, vacuum을 직접 재구현하지 않는다. 버전별 공식 지원 범위를 확인한다.
  3. Budget multiplication: per-node memory × 한 plan의 동시 node × session 수 × parallel workers를 capacity plan에 넣는다.
  4. Observe skew: 평균 cardinality뿐 아니라 most-common-values, max partition, duplicate output을 수집하고 통계를 최신화한다.
  5. Keep cause metrics: latency와 함께 probes, buffer hit/read, batches, temp bytes, row estimate ratio를 기록한다.
  6. Own resource lifetime: pin, latch, memory context, temp file을 guard/arena로 query cancel에도 회수한다.
  7. Test cold and warm: 개발 노트북 warm-cache 결과 하나를 production storage 성능으로 일반화하지 않는다.

15. 대기업 면접 질문 3개와 답변 포인트

Q1. HashMap 조회가 O(1)인데 DB 조회가 왜 느릴 수 있나요?
expected/worst 전제를 먼저 구분한다. hash는 bucket 후보만 찾고 cache miss, buffer miss, overflow page, random heap fetch, equality·visibility recheck, lock/latch가 뒤따른다. 시간과 probes·BUFFERS·I/O를 함께 측정한다고 답한다.
Q2. Hash index와 hash join의 차이를 설계 관점에서 설명하세요.
persistent 보조 구조와 query-local 실행 구조의 수명부터 나눈다. index는 DML·WAL·split·VACUUM·TID recheck, join은 build/probe·duplicate multiplicity·memory/spill·temp cleanup이 핵심이다. 둘 다 equality만 활용하지만 계약이 다르다.
Q3. Hash join이 memory를 넘고 hot key도 있을 때 어떻게 대응하나요?
같은 h₁로 양쪽을 partition하는 correctness와 한 pass 3(M+N) I/O를 설명한다. Batches/temp I/O/max partition을 관측하고, 다른 seed 재partition·heavy-hitter 분리·recursion limit·sort-merge fallback을 둔다. 전역 memory 증가는 동시성 총량 계산 후 결정한다.

  • persistent index와 ephemeral operator의 ownership·failure·concurrency 차이를 설명하는가?
  • 평균값 대신 max probe/partition, p99, temp bytes로 실패 입력을 볼 수 있는가?
  • “hash를 쓰자”가 아니라 predicate·분포·memory·locality·운영 계약으로 선택을 방어하는가?
