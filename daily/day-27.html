Heap 하나가 아니라
시간·취소·과부하 계약을 구현하라

Stable min-heap → id index → monotonic deadline → bounded overload → retry/persistence · 170분

한 줄 요약
Production scheduler는 (deadline, sequence) min-heap뿐 아니라 id→index 취소, monotonic clock, bounded admission, 실행 상태·재시도·idempotency, 장애 복구를 하나의 불변식과 실패 정책으로 묶어야 한다.

4. Scheduler ADT와 state machine

ABSENTschedule →QUEUEDdue+claim →RUNNING
← terminal cleanupcancel ↓ / retry ↑↓ success/fail
DONE/DLQCANCELLEDDONE/RETRY

선형화 지점: schedule은 heap+map commit, cancel은 map 제거와 heap repair, dispatch는 QUEUED→RUNNING claim이다. cancel이 claim보다 먼저면 실행하지 않고, 뒤면 interrupt를 보장한다고 거짓말하지 말고 cooperative cancellation 결과를 반환한다.

5. 결합 representation invariant

  1. Bounds: 0≤size≤capacity, live tasks는 정확히 heap[0..size).
  2. Heap order: 모든 child c에 대해 (deadline,seq)[parent(c)]≤(deadline,seq)[c].
  3. Stable identity: sequence는 accepted task마다 증가하고 wrap되지 않으며 tie에서 total order를 만든다.
  4. Bidirectional index: 모든 heap i에 pos[heap[i].id]=i; 모든 live map entry도 같은 heap id를 가리킨다.
  5. Uniqueness: live id는 정확히 한 번 존재한다. duplicate schedule 정책은 replace가 아니라 명시적 reject다.
  6. Time domain: deadline과 now는 같은 monotonic clock·unit·epoch에서 비교한다.
  7. State ownership: QUEUED만 heap에 있고 RUNNING/DONE/CANCELLED는 없다. durable store를 쓰면 state/version과 일치한다.

swap helper가 heap만 바꾸고 pos를 갱신하지 않으면 다음 cancel이 다른 task를 삭제한다. 이 버그는 heap-order validator만으로 잡히지 않으므로 양방향 RI 검사가 필요하다.

6. Cancel/remove 정당성

id index로 위치 i를 찾고 마지막 task를 i로 옮긴 뒤 size를 줄인다. 옮긴 task가 새 parent보다 작으면 sift-up, 아니면 sift-down한다.

  • 삭제 전 위반 가능 edge는 i 주변뿐이다. 다른 subtree는 바뀌지 않았다.
  • parent보다 작으면 위쪽 위반만 가능하고 sift-up loop invariant가 복구한다.
  • 그렇지 않으면 parent edge는 안전하고 child 방향만 가능해 sift-down이 복구한다.
  • 매 swap에서 두 pos를 함께 바꾸면 map RI도 유지된다. 삭제 id의 pos는 NONE이 된다.

최소 반례: “delete는 항상 sift-down”이라 하면 옮겨온 last가 새 parent보다 작은 경우 parent edge가 깨진다. 방향 판정이 필수다.

8. Clock와 periodic semantics

  • duration/deadline: monotonic clock을 쓴다. wall clock jump가 이미 예약된 delay를 앞당기거나 영원히 미루면 안 된다.
  • calendar event: 사용자의 09:00 KST를 wall time으로 해석한 뒤 현재 monotonic deadline으로 변환한다. timezone/DST 변경 시 재평가 정책을 둔다.
  • fixed-rate: 다음 due=origin+k·period. 지연 뒤 catch-up 폭주를 skip/coalesce/limited catch-up 중 하나로 제한한다.
  • fixed-delay: 다음 due=completion+delay. drift가 생기지만 overlap과 catch-up 폭주를 피하기 쉽다.
  • 정밀도: timer resolution·OS wakeup·GC·worker backlog 때문에 due는 실행 가능 하한이지 실시간 보장이 아니다.

10. 과부하 실험: queue가 처리율을 만들지 않는다

100,000 tick 동안 매 tick 12개가 들어오고 10개만 처리되는 지속 과부하를 실행했다. due는 도착 tick이며 종료 후 accepted task를 drain했다.

10배 buffer가 장기 처리율을 거의 바꾸지 않고 p99 대기를 약 10.8배 키웠다. capacity는 peak를 흡수하는 시간 예산이지 지속적인 arrival>service를 해결하는 장치가 아니다. deadline-aware reject·tenant quota·producer backpressure가 필요하다.

11. Retry는 새 예약이며, 폭주를 만들 수 있다

next=min(cap, base·2^attempt)에 full jitter를 적용하고 max attempts·overall deadline·retry budget을 둔다. non-idempotent 작업은 무조건 재시도하지 않는다.

  • timeout이 “실패”가 아니라 “결과를 모름”일 수 있으므로 idempotency key와 결과 조회가 필요하다.
  • 모든 계층이 3회씩 retry하면 호출 fan-out이 곱해진다. 한 계층에서만 책임지고 budget을 공유한다.
  • retry task도 admission/capacity/tenant quota를 통과시켜 새 요청을 굶기지 않는다.
  • DLQ는 쓰레기통이 아니다. 원인·attempt·last error·payload reference·replay authorization을 보존한다.

13. Concurrency와 wake-up protocol

  1. heap+map+state를 하나의 lock 아래 갱신하거나 동등한 linearizable protocol을 쓴다.
  2. timer thread는 root deadline까지 condition wait한다.
  3. 새 task가 이전 root보다 이르면 signal한다. signal 누락 시 새 deadline을 지나서 깨어난다.
  4. spurious wakeup과 cancel/reschedule 때문에 깨어날 때마다 lock 아래 root와 now를 다시 검사한다.
  5. worker queue도 bounded하게 두고 handoff 실패 시 task state를 잃지 않는 rollback/requeue 정책을 둔다.

15. 실무 Best Practice

  1. due, start SLA, delivery, cancel, periodic, shutdown semantics를 API에 먼저 쓴다.
  2. (deadline,sequence) total order와 monotonic clock domain을 고정한다.
  3. heap+id index validator를 debug/fuzz에서 매 연산 수행하고 swap helper를 단일화한다.
  4. queue와 worker를 모두 bounded하게 하고 tenant quota·deadline-aware admission을 둔다.
  5. timer thread와 execution pool을 분리하고 새 earliest task에서 wake-up한다.
  6. retry는 idempotency·backoff+jitter·attempt/deadline/budget을 모두 만족할 때만 한다.
  7. durability가 필요하면 검증된 scheduler/queue를 우선하고 WAL·replay·duplicate를 장애 주입한다.
  8. depth만 보지 말고 oldest age, lateness p99, reject, cancel latency, stale ratio, lock hold, worker saturation을 본다.

17. 대기업 면접 질문 3개와 답변 포인트

Q1. 취소 가능한 scheduler priority queue를 설계하고 정당성을 설명하세요.
stable min-heap과 id→index를 결합하고 양방향 RI를 선언한다. last를 삭제 위치로 옮긴 뒤 parent 비교로 up/down을 고르고 swap마다 map을 고친다. cancel vs claim 선형화와 running 협력 취소까지 말한다.
Q2. Queue capacity를 10배 키우면 과부하가 해결되나요?
지속적으로 λ>μ이면 backlog/reject는 피할 수 없고 큰 buffer는 대기 시간과 메모리를 늘릴 뿐이다. 실측처럼 처리율·reject·oldest age·p99를 보고 admission, backpressure, quota, scaling을 적용한다.
Q3. Scheduler에서 exactly-once 실행을 어떻게 보장하나요?
heap만으로는 불가능하다. crash가 외부 side effect와 ack 사이에 끼므로 at-least-once + idempotency key/outbox/dedup을 설계하거나 제한된 transactional boundary가 필요하다. 보장 범위와 failure model을 먼저 명시한다.
