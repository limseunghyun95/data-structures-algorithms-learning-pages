한 줄 요약
Merge sort는 크기 n 문제를 독립적인 두 절반으로 나눈 뒤 두 sorted run을 Θ(n)에 안정적으로 병합하여, 입력 분포와 무관하게 Θ(n log n)을 보장한다. 대신 일반적인 배열 구현은 Θ(n) 보조 메모리와 많은 이동을 지불한다.

1. 초보자를 위한 용어 사전

Divide-and-conquer큰 문제를 더 작은 독립 문제로 나누고(divide), 각각 풀고(conquer), 결과를 합치는(combine) 설계법.
Subproblem원래 문제와 같은 형태이지만 입력 범위가 작은 문제. 여기서는 A[lo:hi) 정렬이다.
Base case더 나누지 않고 답을 아는 가장 작은 문제. 길이 0 또는 1인 배열은 이미 정렬됐다.
Run정렬된 연속 구간. merge는 인접한 두 run을 하나로 만든다.
Merge두 sorted sequence의 앞 원소 중 작은 쪽을 반복 선택해 하나의 sorted sequence를 만드는 연산.
Recurrence입력 크기별 실행 시간을 더 작은 크기의 시간으로 표현한 식. Merge sort는 T(n)=2T(n/2)+Θ(n).
Recursion tree재귀 호출을 층별로 펼친 그림. 각 층의 병합량 합이 n이고 층 수가 log₂n이다.
Stable같은 key인 record의 입력 상대 순서를 보존하는 성질. merge에서 동률이면 왼쪽을 먼저 고르면 된다.
Auxiliary buffer병합 중 아직 읽지 않은 원소를 덮어쓰지 않도록 쓰는 임시 배열.
Top-down / bottom-up재귀로 큰 범위를 나누는 방식 / 길이 1 run부터 반복문으로 합치는 방식.
External sort전체 입력이 메모리에 안 들어갈 때, 메모리 크기의 run을 파일로 만든 뒤 여러 run을 병합하는 정렬.
Fan-in한 번의 외부 merge에서 동시에 읽는 run 수 k. 크면 pass는 줄지만 buffer와 file descriptor가 늘어난다.

2. 문제·입출력·제약 mental model

Input: A[0..n), key 또는 comparator Output: 입력과 같은 identity multiset의 sorted permutation Option: stable, range sort, memory budget B, external input 먼저 물을 것: - 최악 시간 보장이 필요한가? - stable이 비즈니스 계약인가? - Θ(n) 임시 메모리가 허용되는가? - record가 큰가, pointer/key만 옮길 수 있는가? - 입력이 RAM보다 커서 sequential I/O가 중요한가? - comparator/key extraction이 실패하거나 비싼가?

n만 보지 말고 비교 비용 C, 이동 비용 W, 메모리 M, I/O pass를 분리한다. 배열 merge sort는 predictable한 Θ(n log n)과 sequential access를 얻지만, 임시 공간과 복사 traffic을 쓴다. linked list는 node 재연결로 병합할 수 있지만 pointer chasing 때문에 locality가 나쁠 수 있다.

4. Sorting ADT와 representation invariant

ADT 계약: sort(A,key)의 결과 R은 (1) key 순서로 nondecreasing이고, (2) 입력 identity와 같은 multiset이며, (3) stable 옵션이면 equal-key identity의 상대 순서를 보존한다.

Top-down 상태: 배열 A, 공유 보조 배열 aux, 반열린 범위 [lo,hi). 재귀 함수 반환 시 A[lo:hi)가 정렬되어야 한다.

  • 0 ≤ lo ≤ mid ≤ hi ≤ n. 반열린 범위로 empty와 길이 계산을 일관되게 한다.
  • merge 시작 시 A[lo:mid)와 A[mid:hi)는 각각 sorted run이다.
  • merge 도중 A[lo:k)는 두 run에서 소비한 원소의 sorted stable merge다.
  • aux는 호출 전체에 한 번 n칸 할당해 재귀마다 새 배열을 만들지 않는다.
  • 항상 입력 identity의 permutation이다. copy 경계와 cursor가 원소를 잃거나 복제하지 않는다.

5. Divide → conquer → combine

단계작업비용
Dividemid=lo+(hi-lo)//2로 두 반열린 범위 결정Θ(1)
Conquer왼쪽과 오른쪽을 재귀적으로 정렬2T(n/2)
Combine두 cursor로 작은 원소를 순서대로 출력Θ(n)
n elements level cost [0,n) n / \ [0,n/2) [n/2,n) n / \ / \ ... ... n n leaves of size 1 - height = ⌈log₂ n⌉, each merge level = Θ(n) T(n) = 2T(n/2) + Θ(n) = Θ(n log n)

n이 2의 거듭제곱이 아니어도 자식 크기 차이는 최대 1이며 높이는 Θ(log n)이다. Master theorem에서는 a=2, b=2, f(n)=Θ(n)=Θ(nlog₂2)이므로 Θ(n log n)이다.

6. Merge 정당성 증명

전제: L과 R은 각각 정렬되어 있다. cursor i, j가 아직 소비하지 않은 첫 원소를 가리키고 출력 cursor k가 다음 위치를 가리킨다.

  1. Initialization: k=lo일 때 출력 prefix는 empty이므로 정렬되어 있고, 소비한 원소의 stable merge라는 명제가 참이다.
  2. Maintenance: L[i]와 R[j]는 각 run의 미소비 최솟값이다. 더 작은 것을 출력하면 전체 미소비 집합의 최솟값이므로 sortedness가 유지된다. 동률이면 L[i]를 먼저 출력해 원래 왼쪽에 있던 equal record가 앞선다.
  3. Termination: 두 run의 원소를 정확히 한 번씩 소비하면 출력 길이는 합과 같고, sorted permutation이 완성된다.
안정성을 깨는 최소 반례: 왼쪽 [(2,a)], 오른쪽 [(2,b)]에서 동률일 때 오른쪽을 고르면 [(2,b),(2,a)]가 된다. 값은 정렬됐지만 stable 계약은 실패한다. 따라서 비교는 left.key <= right.key여야 한다.

8. 직접 구현: shared buffer + stable tie

def merge_sort(a, key=lambda x: x): n = len(a) aux = [None] * n # 호출 전체에서 한 번만 할당 def sort(lo, hi): # A[lo:hi)를 정렬 if hi - lo <= 1: return mid = lo + (hi - lo) // 2 # 고정폭 정수 언어에서 overflow 회피 sort(lo, mid) sort(mid, hi) # 두 run이 이미 이어져 있으면 copy/merge 생략 if key(a[mid - 1]) <= key(a[mid]): return i, j = lo, mid for k in range(lo, hi): if i == mid: aux[k] = a[j]; j += 1 elif j == hi: aux[k] = a[i]; i += 1 elif key(a[i]) <= key(a[j]): # 동률: LEFT FIRST aux[k] = a[i]; i += 1 else: aux[k] = a[j]; j += 1 a[lo:hi] = aux[lo:hi] sort(0, n)

production 수정: 위 코드는 설명용이라 key를 반복 계산한다. key가 비싸거나 실패 가능하면 호출 전에 한 번씩 계산해 `(key, originalIndex, reference)`로 decorate하고, 성공한 뒤 undecorate한다. 이 방식은 비교 중 side effect도 줄인다.

10. 테스트 전략: 값만 맞으면 부족하다

  1. Sortedness: 모든 i에 key(A[i]) ≤ key(A[i+1]).
  2. Permutation: identity multiset이 입력과 정확히 같다. 중복 key 때문에 값 집합만 보면 누락을 놓친다.
  3. Stability: key별 originalIndex sequence가 입력과 동일하다.
  4. Boundary: n=0,1,2, odd length, non-power-of-two, all equal, duplicates, reverse.
  5. Exhaustive: n≤8의 모든 permutation을 reference sort와 대조한다.
  6. Fault injection: aux allocation·key extraction·comparator·temp-file write가 k번째에 실패할 때 상태와 cleanup 계약을 검증한다.
오늘 검증: Python 3.11.6에서 n=0..8 모든 permutation과 duplicate stability를 top-down/bottom-up 두 구현에 대조했다. sortedness·identity permutation·key별 original order oracle을 모두 통과했다.

12. Memory와 locality: O(n) 한 줄로 끝내지 말기

  • 공유 aux: 재귀마다 slice를 만들면 한 시점 peak는 구현에 따라 O(n)이더라도 allocation churn과 총 copy가 커진다. n칸 buffer를 한 번 재사용한다.
  • Ping-pong: source/destination 역할을 level마다 바꾸면 불필요한 copy-back을 줄일 수 있지만 API와 proof가 복잡해진다.
  • Indirect sort: 큰 record 자체보다 `(key,pointer)`를 정렬하고 마지막에 한 번 재배치한다. cache traffic은 줄지만 indirection과 final permutation 비용이 생긴다.
  • Sequential merge: 두 run을 앞으로 읽고 출력도 앞으로 쓰므로 cache prefetch와 disk sequential I/O에 유리하다.
  • Linked list: aux array 없이 relink 가능하지만, 이론적 O(1) extra가 실제 cache miss를 숨기지 못한다.

13. Production architecture: external k-way merge

① Run generationmemory budget만큼 읽기 → in-memory sort → temp run에 순차 기록
↓ manifest에 length·checksum·key range 기록
② k-way merge각 run head를 min-heap에 넣고 smallest를 output
↓ fsync/rename 정책과 partial output 처리
③ Commit완료 marker 후 atomic rename · old/temp run 정리

k가 커지면 merge pass는 줄지만 k개 input buffer, heap O(log k), file descriptor가 필요하다. memory budget을 record만으로 꽉 채우지 말고 input/output buffer·heap·allocator overhead를 예약한다. PostgreSQL도 큰 입력을 temporary file과 balanced k-way merge로 처리하고 sort method와 memory/disk 사용량을 계측한다.

15. 실무 best practice

  • 일반 애플리케이션은 검증된 표준 library sort를 우선하고, stable·memory·worst-case 계약을 문서로 확인한다.
  • key 함수는 가능하면 원소당 한 번 계산한다. DB collation·locale·Unicode normalization도 key version과 함께 고정한다.
  • aux buffer는 요청별 무제한 할당 대신 quota/pool을 쓰고, 한도 초과 시 external spill 또는 명시적 실패로 전환한다.
  • 작은 run에는 insertion sort cutoff, 이미 이어진 run에는 boundary skip을 쓰되 threshold를 실제 record와 hardware로 측정한다.
  • external run에는 schema/comparator version, count, min/max key, checksum을 기록해 resume와 corruption 진단을 가능하게 한다.
  • 관측값: rows, comparisons(가능 시), peak bytes, spill bytes, run count, merge passes, duration, cancellation, cleanup failure.

16. Anti-pattern

  • 동률에 오른쪽 우선: 결과 값은 맞아 보여 stability 회귀가 숨어든다.
  • 재귀마다 좌우 slice 생성: allocation·copy churn이 알고리즘 비용을 덮는다.
  • 모든 요청에 전체 sort: top-k, 이미 sorted stream merge, index scan으로 충분한데 Θ(n log n)을 지불한다.
  • Big-O만 비교: aux peak, record movement, comparator 비용, spill pass, p99를 무시한다.
  • temp file을 성공으로 간주: fsync/rename/manifest 없이 crash 뒤 truncated 결과를 정상 파일로 오인한다.
  • 정렬 중 입력 공유: reader나 writer가 동시에 접근해 중간 상태를 관측한다.

17. 대기업 면접 질문 3개와 답변 포인트

Q1. Merge sort가 왜 항상 Θ(n log n)인가요?
두 절반 재귀와 선형 merge로 T(n)=2T(n/2)+Θ(n). recursion tree의 각 층 총 작업은 Θ(n), 높이는 Θ(log n)이다. 입력 순서와 pivot luck에 의존하지 않는다.
Q2. Merge sort의 stability는 어디에서 결정되나요?
재귀가 아니라 merge의 tie rule이다. 두 run의 key가 같을 때 원래 앞 구간인 왼쪽 원소를 먼저 출력해야 한다. sortedness test만으로는 검증 못 하므로 originalIndex oracle이 필요하다.
Q3. 1TB 로그를 4GB RAM에서 정렬한다면?
RAM quota 안에서 sorted run을 만들고 checksum/metadata와 함께 temp file에 기록한다. buffer·FD 한도에 맞춘 k-way min-heap merge, sequential I/O, 여러 pass, crash-safe commit/cleanup을 설계하고 spill bytes·pass·p99를 관측한다.

18. 퀴즈·누적 리뷰

  1. merge loop invariant를 initialization·maintenance·termination으로 말하라.
  2. 동률에 오른쪽을 먼저 고르는 두 원소 최소 반례를 작성하라.
  3. n=8 recursion tree의 각 level merge 원소 수 합을 적어라.
  4. 공유 aux와 재귀별 slice 구현의 peak memory·allocation count를 구분하라.
  5. Day 37 insertion의 Θ(n+I)와 merge의 Θ(n log n)을 nearly-sorted 입력에서 비교하라.
  6. external fan-in을 8→64로 높일 때 pass, RAM, FD, heap cost가 어떻게 바뀌는가?
누적 리뷰 답변 골격: “정렬 알고리즘을 고른다”가 아니라 stable/worst-case/memory/I/O 계약 → representation → invariant와 proof → 실패 원자성 → workload benchmark 순서로 방어한다.

19. 다음 날 연결

Day 39는 quicksort, partition, worst case다. Merge sort의 combine은 별도 buffer에서 안전하게 합쳤다. Quicksort는 같은 배열 안에서 pivot을 기준으로 partition하므로 평균 locality와 in-place 장점을 얻지만 pivot·duplicate·adversarial input에 따라 Θ(n²)이 될 수 있다. partition loop invariant와 introspective fallback을 비교한다.
