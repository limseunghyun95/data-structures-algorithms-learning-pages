WAL → Memtable → Immutable → SSTable → Version → Compaction · 185분

한 줄 요약
LSM tree는 최신 mutation을 WAL과 memory의 ordered memtable에 먼저 기록하고 이를 immutable sorted SSTable로 순차 flush한 뒤, 여러 세대의 최신값·tombstone을 merge/compaction으로 정리해 write locality를 얻는 대신 read·space·background I/O debt를 관리하는 구조다.

1. 초보자를 위한 용어 사전

LSM treeLog-Structured Merge-Tree. memory와 storage의 여러 sorted run을 하나의 최신 key-value view처럼 제공하는 구조.
Mutationput·delete처럼 상태를 바꾸는 연산. delete도 “없애기”가 아니라 tombstone을 쓰는 mutation이다.
WALWrite-Ahead Log. 아직 SSTable에 없는 mutation을 crash 후 재생하기 위한 append-only 복구 로그.
Memtable최근 mutation을 가진 in-memory structure. range를 지원하려면 보통 skip list 같은 ordered 표현을 쓴다.
Immutable memtable용량에 도달해 write를 받지 않고 background flush를 기다리는 고정된 memtable.
SSTable / sorted runkey 순서로 정렬된 immutable storage file. data block·index·filter·footer/checksum metadata를 가질 수 있다.
Sequence numbermutation의 논리 순서를 식별하는 단조 증가 번호. 같은 key의 어느 version이 최신인지 결정한다.
Tombstone“이 key는 삭제됐다”는 versioned marker. 오래된 SSTable의 값을 다시 보이게 하지 않도록 유지한다.
Flushimmutable memtable을 sorted SSTable로 기록하고 serving version에 원자적으로 추가하는 과정.
Level 0 / levelflush output이 먼저 들어가는 L0와 그 아래 크기가 커지는 저장 계층. L0 file은 key range가 겹칠 수 있다.
Compaction여러 sorted run을 merge해 최신 version만 남기고 level/files를 재조직하는 background 작업.
Manifest / Version현재 serving state를 구성하는 SST file, level, key range를 기록한 metadata와 immutable view.
Write stallflush/compaction이 ingest를 못 따라가 memtable·L0가 한계를 넘을 때 write를 늦추거나 멈추는 backpressure.
Amplification논리 1byte/1query를 위해 storage가 실제로 쓰고·읽고·점유하는 배수.
Snapshot특정 sequence 이하의 consistent view. 오래된 version·tombstone·file 수명을 연장할 수 있다.

2. 문제·입출력·제약 mental model

문제: write가 많고 dataset은 RAM보다 큰 ordered KV store에 put/get/delete/range, crash recovery, snapshot을 제공한다. 매 write마다 큰 B+tree page를 random update하는 대신 mutation은 작은 WAL append와 memory update로 받고, 정렬된 큰 batch를 storage에 sequential하게 쓴다.

제약 질문결정되는 것

point:range:write와 overwrite/delete 비율?memtable, Bloom/filter, compaction, tombstone 정책

3. Architecture 그림: write path

① Write batchvalidate → sequence 할당 → batch checksum
↓ WAL append + required sync 후에만 durable ack
② Mutable memtable(userKey,sequence,type) → value; 최신 read 즉시 반영
↓ size/total-WAL/memory trigger
③ Immutable queueactive swap은 짧게, background가 sorted SST temp 생성
↓ file complete·sync → manifest/version atomic install
④ L0 + compactionimmutable SST serving → merge to lower level → safe old-file/WAL GC

write latency가 짧아졌다고 물리 비용이 사라진 것은 아니다. foreground에서 뒤로 미룬 sort·merge·compression·checksum·write를 background가 처리하며, 그 처리율이 ingest보다 낮으면 debt와 stall이 누적된다.

4. Architecture 그림: read path

Newestmutable memtable → immutable memtables
↓ 찾았어도 snapshot sequence와 type 확인
L0range가 겹치는 여러 newest SST; filter → index → data block
↓ 아직 visible version 없음
L1…Lnleveled이면 level당 겹치는 file 최대 하나를 후보로 탐색
↓ 최대 visible sequence의 value/tombstone 선택
Resultvalue 반환 / tombstone이면 NOT_FOUND / snapshot rule 적용

구현은 반드시 현재 version을 pin한다. read 도중 compaction이 file set을 교체해도 iterator가 참조하는 old SST를 즉시 삭제하면 안 된다.

5. KV Store ADT와 durability 계약

  • put(key,value,writeOptions): replace semantics, assigned sequence, ack의 durable 경계를 반환한다.
  • delete(key): 존재 여부와 무관하게 tombstone mutation을 만들 수 있으며 idempotency를 정의한다.
  • get(key,snapshot): snapshot 이하 가장 큰 sequence의 type/value를 해석한다.
  • scan([lo,hi),snapshot): 모든 component를 user-key order로 merge하고 같은 key는 최신 visible version 하나만 노출한다.
  • flush와 compact: admin 요청의 completion·durability·cancel semantics를 분리한다.

ack 전제: sync write이면 WAL record가 검증 가능한 형식으로 durable해진 뒤 성공을 반환한다. async/no-WAL은 더 빠를 수 있지만 power/process crash에서 잃을 수 있는 범위를 API와 SLO에 명시한다.

6. Representation invariant

  1. Global sequence: accepted mutation마다 유일하고 증가하는 sequence가 있으며 같은 key의 version order를 만든다.
  2. WAL-before-loss: 아직 durable SST에 없는 acknowledged mutation은 recovery 가능한 WAL에 존재한다.
  3. Memtable order: 각 entry는 internal key (userKey,sequence desc,type) 규칙으로 검색·순회 가능하다.
  4. SST immutability: 완료된 SST는 byte가 바뀌지 않고 entries는 정렬되며 block index·bounds·checksum/footer가 일치한다.
  5. Serving version: manifest/version은 완전히 생성된 file만 참조하고, 참조된 모든 live file은 존재한다.
  6. Newest-wins: snapshot 이하 후보 중 최대 sequence 하나가 논리 상태이며 tombstone이면 key는 보이지 않는다.
  7. Leveled ranges: L0는 overlap 가능, L1+는 같은 level 안에서 file key range가 겹치지 않는 정책을 유지한다.
  8. Lifetime: pinned snapshot/iterator/version이 참조하는 WAL/SST는 GC하지 않는다.
  9. Tombstone safety: 더 오래된 value가 존재할 수 있는 level/snapshot/replica가 모두 사라지기 전 tombstone을 제거하지 않는다.

7. SSTable은 무엇을 저장하나

point get은 file key range와 filter를 먼저 보고, 가능성이 있을 때만 index와 data block을 읽는다. filter는 false positive 때문에 불필요한 read가 생길 수 있지만 false negative가 없어야 한다. 상세 확률·bit budget은 Day 31에서 증명한다.

prefix/delta compression은 공간과 cache 효율을 높이지만 block 일부만 독립 decode하기 어렵게 한다. block size가 커지면 index·compression은 좋아져도 point read amplification과 cache pollution이 커질 수 있다.

8. Get 정당성: 왜 최신값을 반환하는가

snapshot sequence를 S라 하자. 모든 component에서 user key k이며 sequence≤S인 entry 후보를 모아 sequence 최대 e를 고른다.

  • Completeness: WAL/memtable에서 flush된 mutation은 manifest install 뒤 SST에 존재하고, install 전에는 immutable+WAL에 남는다. serving components를 모두 보면 acknowledged version을 놓치지 않는다.
  • Order: sequence가 mutation의 total order이므로 최대 e보다 나중이면서 S 이하인 후보는 없다.
  • Visibility: e가 value면 그 값, tombstone이면 삭제가 그 이전 모든 value를 가리므로 NOT_FOUND다.
  • Early stop: newest→oldest 탐색은 “이 component의 모든 sequence가 뒤 component보다 큼”이 metadata로 보장될 때만 첫 hit에서 멈출 수 있다.

최소 반례: newest L0에 delete(k,seq=9), L2에 put(k,V,seq=4)가 있다. tombstone을 “값이 아니니 계속 찾자”로 처리하면 삭제된 V가 부활한다.

9. Flush transaction과 crash 지점

  1. mutable을 immutable로 swap하고 새 WAL+memtable이 write를 받는다.
  2. immutable을 internal-key 순서로 읽어 temporary SST를 쓰며 block checksum·footer를 완성한다.
  3. SST를 필요한 durability로 sync하고 최종 이름/identity를 확정한다.
  4. manifest에 “new SST 추가” version edit를 append+sync하고 current version을 atomic install한다.
  5. 그 뒤에만 immutable과 그 mutation을 유일하게 보호하던 old WAL을 제거 대상으로 표시한다.
Crash 시점Recovery의 안전한 결과

SST complete 후 manifest 전orphan SST 무시/GC, WAL replay
manifest install 후 WAL delete 전SST serving; replay 중 sequence/dedup으로 logical duplicate 방지
WAL을 먼저 삭제SST/manifest 실패 시 데이터 유실 — 금지 순서

10. 시간·공간·amortized complexity

flush 비용은 한 memtable의 많은 writes에 나뉘어 상각되지만, compaction은 같은 logical byte를 여러 level에서 다시 쓸 수 있다. foreground put O(log M)을 storage write O(log M)로 오해하지 말고 physical bytes written / user bytes를 측정한다.

11. Compaction은 merge sort이자 부채 상환

각 input run은 이미 정렬됐으므로 min-heap을 이용한 k-way merge로 다음 key를 고른다. 같은 user key의 version들은 sequence로 정렬해 snapshot에 필요한 것만 보존하고, 안전한 tombstone/obsolete version을 버린다.

  • Leveled: level당 sorted run 수를 적게 해 read·space amplification을 낮추지만 기존 큰 run의 겹치는 범위를 재작성해 write amplification이 커질 수 있다.
  • Tiered/universal: 비슷한 크기의 여러 run을 모아 merge해 write를 줄이지만 run 수·임시 공간·read amplification이 커질 수 있다.
  • Correctness: input을 current version에서 제거하기 전에 모든 output을 complete+sync하고 새 version을 atomic install한다.
  • Lifetime: old version을 pin한 reader가 끝나기 전 input SST를 삭제하지 않는다.

구체적 level ratio, selection, write/read/space amplification 계산과 compaction 폭주는 Day 32에서 더 깊게 다룬다.

13. Backpressure: memory가 처리율을 만들지 않는다

지속 ingest λ가 flush+compaction service μ보다 크면 immutable memtable과 L0 file이 계속 쌓인다. 큰 write buffer는 burst를 더 오래 흡수하지만 장기 처리율을 높이지 않고 recovery time·memory·read amplification을 키운다.

  1. soft threshold에서 write delay를 점진적으로 걸어 producer가 feedback을 받게 한다.
  2. hard threshold에서 명시적으로 stall/reject하고 무제한 memory/file 생성을 막는다.
  3. foreground write QPS와 background bytes/sec를 같은 dashboard에서 본다.
  4. tenant/column-family별 quota로 한 hot workload가 전체 flush/WAL retention을 막지 않게 한다.

필수 지표: active/immutable memtable bytes, oldest immutable age, L0 file·overlap, pending compaction bytes, stall duration/reason, WAL retention, write/read/space amplification, p99 get/put.

“write-heavy=LSM”만으로 결정하지 않는다. read/range SLO, key/value 크기, overwrite, compression, device endurance, cache, recovery, 운영 복잡도를 같은 workload에서 측정한다.

15. Snapshot·tombstone·replication 함정

  • old snapshot S는 S 이하 version을 필요로 하므로 최신 compaction이 old value를 마음대로 지울 수 없다.
  • tombstone을 시간만 보고 지우면 아직 compaction되지 않은 lower-level value가 부활할 수 있다.
  • replica가 tombstone을 보기 전에 GC하면 늦은 replica의 old value가 다시 전파될 수 있다.
  • TTL은 wall clock semantics, snapshot, clock skew, compaction 시점을 정의해야 “만료 즉시 disk에서 사라짐” 같은 거짓 기대를 피한다.
  • 긴 iterator/snapshot은 old SST refcount와 disk usage를 붙잡으므로 age·pin bytes를 관측하고 제한한다.

17. Production benchmark 설계

  1. initial load와 steady overwrite/delete를 분리하고 실제 key/value·compressibility·skew를 재현한다.
  2. write buffer가 가득 차기 전 짧은 burst 수치 대신 최소 여러 compaction cycle의 steady state를 측정한다.
  3. sync/async WAL, group size, cache warm/cold, point hit/miss, short/long range를 각각 표시한다.
  4. user ops/sec와 device bytes/sec를 함께 재 write amplification을 계산한다.
  5. checkpoint/backup, snapshot, TTL, disk near-full, compaction thread loss, process kill을 주입한다.
  6. 평균뿐 아니라 p99/p999, stall time, recovery time, peak disk, old-version retention을 보고한다.

Benchmark anti-pattern: WAL 비활성 결과를 durable DB와 비교, cache warm get만 보고, compaction이 시작되기 전에 종료, 데이터가 RAM보다 작음, overwrite 없이 sequential unique key만 사용, output checksum을 소비하지 않음.

18. 실무 Best Practice

  1. durability·snapshot·delete semantics를 먼저 문서화하고 검증된 engine 기본값에서 출발한다.
  2. WAL·memtable·SST·manifest 각각의 checksum, sequence bounds, file identity를 검증한다.
  3. foreground ingest rate를 background sustainable bytes/sec보다 낮게 capacity plan한다.
  4. memory budget에 active/immutable memtable, block cache, index/filter, iterator pin을 모두 포함한다.
  5. filter와 cache는 read debt를 줄일 뿐 compaction debt를 제거하지 않음을 기억한다.
  6. tombstone GC는 oldest snapshot, lower-level overlap, replica/backup 안전성을 모두 확인한다.
  7. disk headroom을 compaction input+output peak와 WAL retention까지 두고 full 전에 throttle한다.
  8. crash recovery와 backup restore 후 full key/version validator를 정기 실행한다.

19. 대기업 면접 질문 3개와 답변 포인트

Q1. LSM write/read path와 durability를 설계해 보세요.
sequence batch를 WAL append+필요 시 sync한 뒤 memtable에 적용한다. full이면 immutable로 swap, complete+sync SST를 manifest/version에 atomic install한 뒤 old WAL을 GC한다. read는 snapshot 이하 newest version을 memtable→SST에서 찾고 tombstone을 NOT_FOUND로 해석한다.
Q2. LSM이 write에 유리한데 왜 write stall이 생기나요?
random update를 WAL+memory로 빠르게 수용했지만 flush·compaction physical bytes는 background debt다. 지속 ingest가 service보다 크면 immutable/L0/read amp가 증가하므로 soft delay·hard stall·quota가 correctness와 bounded resource에 필요하다.
Q3. Tombstone은 언제 안전하게 제거할 수 있나요?
그 tombstone보다 오래된 value가 어떤 lower level, snapshot, iterator, replica, backup에도 다시 관측되지 않을 때다. 단순 TTL 경과만으로 삭제하면 value resurrection이 가능하며 sequence·overlap·retention watermark가 필요하다.

  • RocksDB Live SST Files — immutable version과 reader가 참조하는 old file lifetime.

구현·수치는 교육용 단일 환경이다. production 선택은 WAL 보장, storage, compression, workload skew, cache, compaction policy, snapshot/replica retention과 failure model에서 재검증한다.
