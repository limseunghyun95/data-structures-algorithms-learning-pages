한 줄 요약
Stack은 “가장 최근에 미완료된 일”만 다음에 처리하는 LIFO ADT다. call frame, undo command, parser의 열린 괄호는 같은 push/pop 계약을 쓰지만, 각 시스템의 overflow·실패 원자성·수명·복구 정책은 서로 다르다.

1. 초보자를 위한 용어 사전

Stack한쪽 끝인 top에서만 값을 넣고 빼는 추상 자료형.
LIFOLast In, First Out. 마지막으로 넣은 값이 가장 먼저 나온다는 순서 계약.

Recursion depth동시에 살아 있는 재귀 호출 수. 입력 크기와 frame 크기가 stack memory 사용량을 결정한다.

3. 문제·입출력·제약 mental model

대표 문제: ASCII text에서 ()[]{}의 중첩이 올바른지 검사한다. 다른 byte는 무시하고, 첫 오류 위치와 기대한 닫는 괄호를 반환하며 최대 nesting을 제한한다.

  • 입력: byte string + 명시적 length + caller가 제공한 workspace + max_depth.
  • 출력: OK 또는 INVALID_ARGUMENT, TOO_DEEP, UNEXPECTED_CLOSE, MISMATCH, UNCLOSED와 offset·expected·actual.
  • 성공 계약: 모든 close는 가장 최근 unmatched open과 같은 종류이고, 입력 끝에서 unmatched open이 없다.
  • 실패 계약: out-of-bounds나 allocation 없이 첫 오류에서 멈추고 diagnostic만 반환한다. input과 workspace 밖 memory는 바꾸지 않는다.
  • 제약: n bytes, maximum nesting d, hostile input 여부, Unicode/tokenization 경계, 오류를 한 개 또는 여러 개 수집할지.
  • 왜 stack인가: close가 만나는 상대는 전체 open 중 가장 최근의 unmatched open이다. 바로 LIFO다.

4. Stack ADT와 algebraic contract

Abstract value: bottom부터 top까지의 유한 sequence S=⟨x₀,…,xₖ₋₁⟩. client는 top만 직접 다룬다.

Law / precondition의미
peek(push(S,x)) = x방금 push한 값이 top이다.
pop(push(S,x)) = (S,x)push 뒤 pop은 원래 stack과 x를 복원한다.
isEmpty(empty)=true초기 상태.
pop/peek requires size>0underflow를 sentinel value와 혼동하지 않는다.
push requires resourcebounded면 capacity, dynamic이면 size/byte overflow와 allocation 성공.

중요: stack은 구현 이름이 아니라 interface restriction이다. array, linked node, deque, machine stack 모두 같은 LIFO abstract value를 구현할 수 있으나 complexity와 failure mode는 다르다.

5. Bounded array representation과 RI

Concrete state는 (data,size,capacity)다. AF: data[0:size)를 bottom→top sequence로 읽고 top은 data[size-1]다.

Representation invariant보장
0 ≤ size ≤ capacitylive prefix가 workspace를 넘지 않는다.
capacity>0 ⇒ data!=NULLpush 가능한 stack은 storage를 가진다.
data[0:size) initializedAF가 읽어도 되는 live element.
data[size:capacity) spareabstract stack 밖이며 읽지 않는다.
workspace lifetime ≥ stack useborrowed buffer가 먼저 사라지지 않는다.

6. 직접 구현: allocation 없는 bounded CharStack

#include <stdbool.h>
#include <stddef.h>

typedef enum { STACK_OK, STACK_FULL, STACK_EMPTY } StackStatus;
typedef struct {
    char *data;
    size_t size;
    size_t capacity;
} CharStack;

static StackStatus stack_push(CharStack *s, char value) {
    if (s->size == s->capacity) return STACK_FULL;
    s->data[s->size] = value; // 확보된 spare slot
    ++s->size;                 // write 성공 뒤 logical commit
    return STACK_OK;
}

static StackStatus stack_pop(CharStack *s, char *out) {
    if (s->size == 0) return STACK_EMPTY;
    --s->size;                 // 새 top boundary
    *out = s->data[s->size];
    return STACK_OK;
}

static bool is_open(char c) {
    return c == '(' || c == '[' || c == '{';
}
static bool is_close(char c) {
    return c == ')' || c == ']' || c == '}';
}
static char matching_close(char open) {
    return open == '(' ? ')' : open == '[' ? ']' : '}';
}

이 primitive는 내부에서 유효한 s와 out을 받는다고 가정한다. public boundary는 NULL과 workspace 계약을 검사한다. fixed capacity는 “열등한 dynamic array”가 아니라 예측 가능한 memory와 hard depth limit가 필요한 parser·embedded·real-time path의 의도적 선택이다.

7. 직접 구현: diagnostic을 가진 bracket parser

typedef enum {
    PARSE_OK, PARSE_INVALID_ARGUMENT, PARSE_TOO_DEEP,
    PARSE_UNEXPECTED_CLOSE, PARSE_MISMATCH, PARSE_UNCLOSED
} ParseCode;

typedef struct {
    ParseCode code;
    size_t offset, depth;
    char expected, actual;
} ParseResult;

static ParseResult parse_brackets(
    const char *text, size_t length,
    char *workspace, size_t max_depth
) {
    if ((text == NULL && length != 0) ||
        (workspace == NULL && max_depth != 0))
        return (ParseResult){PARSE_INVALID_ARGUMENT, 0, 0, 0, 0};

    CharStack s = {workspace, 0, max_depth};
    for (size_t i = 0; i < length; ++i) {
        char c = text[i];
        if (is_open(c)) {
            if (stack_push(&s, c) != STACK_OK)
                return (ParseResult){PARSE_TOO_DEEP, i, s.size, 0, c};
        } else if (is_close(c)) {
            char open;
            if (stack_pop(&s, &open) != STACK_OK)
                return (ParseResult){PARSE_UNEXPECTED_CLOSE, i, 0, 0, c};
            char expected = matching_close(open);
            if (c != expected)
                return (ParseResult){PARSE_MISMATCH, i, s.size + 1,
                                     expected, c};
        }
    }

    if (s.size != 0) {
        char expected = matching_close(s.data[s.size - 1]);
        return (ParseResult){PARSE_UNCLOSED, length, s.size, expected, 0};
    }
    return (ParseResult){PARSE_OK, length, 0, 0, 0};
}

API 범위: ASCII delimiter byte만 의미 있게 처리하고 나머지는 무시한다. UTF-8 code point, string literal 안의 괄호, escape, comment를 이해해야 하면 먼저 lexer가 token을 만들고 parser는 delimiter token만 받아야 한다.

8. Correctness proof: prefix invariant

Loop invariant I(i): text[0:i)를 오류 없이 처리했다면 stack에는 그 prefix에서 아직 닫히지 않은 opening delimiter가 등장 순서대로 있고, top은 가장 최근 unmatched opening이다.

  1. 초기화: i=0인 empty prefix에는 unmatched open이 없고 stack도 empty다.
  2. open 유지: c가 open이면 새 unmatched open이 가장 최근 것이므로 push한 stack이 I(i+1)을 만족한다. full이면 resource contract 위반으로 안전하게 중단한다.
  3. close 유지: LIFO nesting에서 c가 닫아야 할 것은 top뿐이다. empty면 상대가 없고, 종류가 다르면 crossing/mismatch다. 일치하면 pop하여 그 pair만 해소하므로 I(i+1).
  4. 기타 byte: delimiter 상태를 바꾸지 않아 invariant가 유지된다.
  5. 종료: 끝에서 stack empty면 모든 open이 정확히 닫혔다. non-empty면 top부터 적어도 하나가 닫히지 않았다.
최소 반례 — 개수만 세기: ([)]는 각 괄호 종류의 open/close 수가 같지만 nesting 순서가 교차한다. counter 세 개는 accept할 수 있으나 stack top은 index 2에서 ]를 기대하고 )를 만나 거부한다.

9. Call stack: ADT에서 machine discipline으로

caller frame
locals · saved state		call f ↓callee f frame
return address · locals		call g ↓active g
top frame
g return: pop g → f resume · f return: pop f → caller resume

MIT 6.004는 nested call의 activation record가 caller보다 먼저 사라져 LIFO에 맞고, frame이 argument·return address 등을 보관한다고 설명한다. 그러나 call stack은 일반 Stack class와 동일한 객체가 아니다. ABI의 register save, alignment, frame pointer omission, exception unwinding, coroutine/continuation, heap-escaped closure가 추가된다.

  • Depth cost: peak memory는 대략 Σ live frame size. 재귀 호출 수만 세면 큰 local array·spill을 놓친다.
  • Stack overflow: 무한 재귀뿐 아니라 유효하지만 깊은 adversarial input도 유발한다. Python 3.14 문서는 interpreter recursion limit이 C stack crash를 막는다고 설명하고 너무 높이면 crash할 수 있다고 경고한다.
  • Iterative conversion: explicit heap/bounded stack으로 바꾸면 depth policy와 error handling을 통제할 수 있지만 총 Θ(d) memory가 사라지는 것은 아니다.
  • Unwinding: exception/cancellation 때 frame별 resource cleanup이 실행되는 언어 계약을 이해하고, C에서는 cleanup path를 명시한다.

10. Undo/redo: 두 stack보다 풍부한 state machine

execute Cdocument를 old→new로 성공적으로 변경
↓ 성공 후 undo.push(C), redo.clear()
undoundo.top의 inverse를 적용 → 성공 후 redo로 이동
↕ redo는 command를 재적용하고 성공 후 undo로 이동
history policyclean index · memory limit · compression · macro · persistence/version

Undo RI: document state는 initial state에 command history의 [0,index) prefix를 순서대로 적용한 결과다. [index,count)는 redo 가능한 suffix다. 새 command를 index에서 실행하면 기존 redo suffix는 다른 미래 branch이므로 폐기한다.

실패 원자성: execute/undo/redo가 I/O·network·validation 때문에 실패할 수 있으면 command를 먼저 stack 사이로 옮기지 않는다. state transition이 성공한 뒤 index/history를 commit하거나, operation 자체를 transaction으로 감싼다. 단순 inverse가 외부 세계를 정확히 복원한다고 가정하지 않는다.

Qt 6.10의 QUndoStack도 command compression, macro, saved document를 표시하는 clean state를 제공한다. 사용자가 기대하는 undo 단위와 memory retention은 raw Stack ADT 밖의 product contract다.

14. Error handling과 production Best Practice

  • underflow를 값으로 숨기지 말기: payload가 0/NULL일 수 있다면 status+out 또는 Result로 empty와 값을 분리한다.
  • hard depth cap: input length와 별개로 nesting·recursion·undo history limit을 두고 TOO_DEEP처럼 관찰 가능한 오류를 반환한다.
  • bounded workspace: request마다 heap allocation을 피하고자 caller buffer를 받을 수 있다. required depth를 알려 retry할지 즉시 reject할지 정책을 정한다.
  • commit order: push는 storage/write 성공 뒤 size를 늘리고, undo는 inverse 성공 뒤 history index를 옮긴다.
  • history budget: command 수뿐 아니라 retained bytes를 제한한다. 오래된 command truncate, snapshot checkpoint, compression 기준을 문서화한다.
  • sensitive data: undo payload와 stack trace가 password·token·PII를 오래 보관하거나 log로 노출하지 않게 redact·zeroize·retention 정책을 둔다.
  • cancellation: macro/transaction 중 cancel되면 이미 실행된 subcommand를 역순 rollback하고 rollback 실패를 별도 escalation한다.
  • metrics: current/max depth, FULL/EMPTY, recursion overflow, undo retained bytes, compression ratio, parser reject reason/offset를 계측한다.

16. Concurrency, persistence, adversarial input

Concurrency: size와 element write는 하나의 원자 operation이 아니다. 일반 ArrayDeque도 thread-safe가 아니므로 producer 여러 개가 공유하면 lock, thread confinement, concurrent deque 같은 명시적 abstraction이 필요하다. fail-fast iterator는 synchronization이 아니다.

Undo persistence: process restart 뒤 redo하려면 raw function pointer나 object address가 아니라 schema-versioned command id, validated payload, target version을 durable log로 저장한다. replay는 idempotency와 migration을 다뤄야 한다. 외부 side effect에는 단순 undo가 아니라 compensating transaction이 필요할 수 있다.

Parser defense: SQLite는 finite machine에서도 명시적 limit이 필요하다고 설명하며 parser/표현식/trigger depth를 낮춰 hostile input의 resource 사용을 제한할 수 있게 한다. “memory가 허용하는 만큼”은 test할 수 있는 계약이 아니다.

17. 현재 구현 문서에서 배우는 선택

  • Java SE 26: legacy Stack보다 일관된 LIFO Deque interface와 ArrayDeque 구현을 권한다. 대부분 연산은 amortized constant이고 null 금지·비동기화 계약이 있다.
  • Python 3.14.7: recursion limit은 interpreter stack의 maximum depth이며 C stack overflow로 인한 crash를 막는다. platform-dependent limit을 너무 높이는 것도 위험하다.
  • Qt 6.10: QUndoStack은 current index, redo suffix, command compression, macro, clean state를 다룬다. 자료구조 하나가 아니라 document state machine이다.
  • SQLite current docs: LALR parser stack과 expression/trigger recursion에 testable limit을 두고 untrusted database에 더 낮은 run-time limit을 적용할 수 있다.

19. 대기업 면접 질문 3개와 답변 포인트

Q1. Stack을 array와 linked list 중 무엇으로 구현하겠습니까?
답변 포인트: peak depth 예측, hard limit, element size, allocation rate, locality, stable address 필요를 묻는다. 보통 contiguous array/deque가 memory·cache에 유리. bounded면 worst Θ(1)+FULL, geometric이면 push worst Θ(n)/amortized Θ(1), linked는 relink Θ(1)이나 per-node allocation 비용.

Q2. 괄호 validator의 correctness를 증명해 보세요.
답변 포인트: 처리한 prefix의 unmatched opens가 stack에 순서대로 있고 top이 가장 최근이라는 loop invariant. open push, close top-match/pop으로 preservation, underflow/mismatch 즉시 reject, 종료 시 empty iff balanced. ([)]가 count 방식의 최소 반례.

Q3. 실무 undo/redo를 두 stack으로 설계할 때 무엇을 더 고려합니까?
답변 포인트: command payload ownership, inverse/redo failure atomicity, 새 edit의 redo suffix 폐기, clean index, command compression/macro, bytes limit/checkpoint, persistence schema, external side-effect compensation, concurrency/observability.

20. 퀴즈·누적 리뷰·다음 날 연결

  1. bounded array push가 worst Θ(1)이고 dynamic array push가 amortized Θ(1)인 차이는?
  2. bracket parser loop invariant에서 top은 무엇을 뜻하는가?
  3. 새 command를 실행하면 redo history를 보통 지워야 하는 이유는?
  4. call depth만으로 stack memory를 정확히 알 수 없는 이유는?
  5. linked stack의 pointer operation이 Θ(1)이어도 latency가 튈 수 있는 이유는?
정답: ① bounded는 resize가 없고 full을 반환, dynamic은 가끔 Θ(n) relocation ② 현재 prefix의 가장 최근 unmatched opening ③ undo 전의 다른 미래 branch이기 때문 ④ frame 크기·alignment·saved register·local/spill이 호출마다 다름 ⑤ allocator/OOM/page fault/contention과 locality.
